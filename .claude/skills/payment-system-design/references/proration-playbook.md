# 折算 Playbook — 升降级 / 月↔年切换的 proration

套餐变更里最容易出错的一档，因为它是**跨周期变更**，且升 / 降在「一次性付费」模型里**严重不对称**。

## 决策表

| 场景 | 生效时机 | 折算处理 |
|---|---|---|
| **升级**（月→年 / 低→高） | **立即** | 抵现金付差价；跨 interval 重置到期 + 锚点 |
| **降级**（年→月 / 高→低） | **周期末**（到期后改买） | **不折算**，旧套餐用满到期，零特殊逻辑 |
| 同档**续费** | 叠加 | 时长叠加、额度按新周期 reset（**不滚存**） |
| 含**不限量 / 企业版** | — | 不参与折算 |

「升级即时、降级周期末」是 Stripe / Chargebee / Paddle / Lago 与行业一致默认。

## 跨周期 vs 同周期

- **只有跨 interval（月↔年）才重算到期**；同周期长度内升降级**不动 `expiresAt`**（Stripe：同 billing period 改价保留原计费日）。
- 升级跨 interval：到期重置为完整新周期（如 `now + 365天`），锚点重置到切换日。

## 折算公式

```
日单价 d   = plan.price / plan.周期天数
剩余天数   = max(0, ceil((expiresAt − now_utc) / 1天))        // 服务端 UTC
剩余价值V = 老套餐日单价 × 剩余天数                            // 基准用老套餐单价（R1）
本次应付   = max(0, 新套餐价 − V)                              // 走支付方下「折后差价」的单
```

> 用量额度本身**不靠 proration 重算**（Stripe：usage-based 不参与 proration）。已用量 forgive、下个新周期按新套餐 reset、**默认不滚存(no rollover)**——「叠加时长但额度按新周期重置」是行业惯例，但要向用户明示「额度不滚存」。

## Worked example（月→年升级）

> 月付 ¥198/月、剩 18 天 → 日单价 19800/30 = 660 分/天 → V = 660×18 = ¥118.8
> 切年付 ¥1980：应付 = 198000 − 11880 = **¥1861.2**，走支付方下这个金额的单
> 新 `expiresAt = now + 365 天`，月度额度子周期锚点重置到切换日。差价恒为正、干净。

## 反套利（必须连同执行，详见 risk-control.md）
