# 风控 / 防套利规则（Risk Control）

支付系统的「风控」≠ 反欺诈系统，而是**不让任何路径凭规则套出钱 / 权益**。每条都要在设计期钉死，否则上线后用户会替你找出来。

## 防套利核心规则

- **R1 折算基准用「老套餐自己的日单价」**，绝不用新套餐单价换算 → 否则「低买高折」套利。
- **R2 剩余价值只抵扣 / 转时长，绝不退现金**（除非走正式退款流程）；`剩余价值 > 新套餐价` 的溢出**作废**，不退差 → 否则「买年付 → 立即降月付套现」。
- **R3 已消耗用量 / 已发一次性 credits 不回收、不参与折算**（用量不参与 proration），只折「未消耗的有效期时间价值」。
- **R4 不限量 / 企业套餐不参与折算**（剩余价值无定义）。
- **R5 降级默认周期末生效**，不开「中途降级退差价」路径 → 从源头消灭套现窗口。升级才即时生效。
- **R6 同一订阅同时只保留一个 pending 变更**；切换**幂等 + 限频**（排期变更相互覆盖，新替旧）。
- **R7 退款 → 回收 / 缩短权益**；若本期不做，**显式记为接受的风险 + 审计**，而非默默漏掉。
- **R8 每笔动钱 / 动权益的操作写一条审计流水**（切换 / 发放 / 退款：来源单号、变更前后值），退款 / 对账时按流水回滚。

## 欺诈 / 竞态向量（设计期逐条排查）

| 向量 | 利用方式 | 缓解 |
|---|---|---|
| 频繁套餐切换 | 反复触发有利折算 | R1 / R5 / R6 + 限频 |
| 退款后仍消费 | 退款不回收权益 | R7 + 退款回调回收 |
| 并发购买 / 消费 | 读判写双花 | 行锁 / 原子自减 / advisory lock |
| 回调重放 | 重复发放权益 | event / 订单号唯一约束 + `appliedAt` 锚点 |
| 时钟操纵 | 客户端时间绕过到期 | 服务端可信时间校验 |
| 边界抖动 | 到期瞬间误判 | 服务端 UTC + 宽限秒 |
| 演示 / 沙箱通道泄漏到生产 | 免费发权益 / 绕验签 | 双控门禁：环境开关 + 鉴权 + 生产拒启 |

## 退款的特别提醒

支付方退款**只退钱，不回收权益**（微信、Stripe 皆然）。退款后是否扣回已发会员天数 / 额度，**完全是商户责任**。最小正确实现：监听退款回调 → 按审计流水缩短 `expiresAt` / 标记权益回收。若延后，必须在决策台账写明「手动退款不回收」这一接受的风险，并保审计可追。

## 一个反例（演示为什么「年→月即时折算」不能做）

> 年付剩 300 天、日单价 542 分 → 剩余价值 ≈ ¥1626，而月付价仅 ¥198。
> 若退差价 = 退 ¥1428 现金 → 用户用 65 天年套餐套现 ¥1428，**严重套利**。
> 即便改成「剩余价值折成月付时长」也劣于继续用年套餐 → 用户根本无动力。
> **结论**：一次性付费下「年→月」无现实需求，降级一律周期末自然到期后改买，零折算逻辑（R5）。
