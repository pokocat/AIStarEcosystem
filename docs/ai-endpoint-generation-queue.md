# 模型接入端点并发与排队

2026-10-09 · v0.220 · 本地实现，未生产发布。

按用户澄清，配置维度是 `AiModelEndpoint.id`，不是厂商名称。一个端点对应模型、地址和 Key。同一端点在多个用途和应用里的调用共用并发名额；不同端点独立，即使属于同一厂商。跨端点共享同一 Key 的总额度暂不合并。

后台「AI 模型与用量 → 模型接入端点 → 编辑」新增「生成任务并发上限」。正整数 1–1000；留空不限制。接口 `concurrencyLimit` 省略/null 保留原值，0 清空限制。调低只限制后续准入，不打断执行中任务；调高或清空后队列自动继续。线程池仍是平台资源上限，因此设定值是最大允许值，不承诺同一时刻一定跑满。

V48 新增 `ai_model_providers.concurrency_limit` 与 `ai_generation_queue`。任务票据唯一键 `(task_type,task_id)`，状态 waiting/running/finished。端点数据库行锁串行化准入，递增票据 ID 确定先进先出；派发短租约避免重复投进线程池。票据不存提示词、媒体、密钥、签名 URL，也不建立第二份积分真值。

覆盖入口：

- Studio 图片、人物提取、剧本、分镜与助手采用任务级排队。等待时退出执行线程，任务中心显示「排队中 · 有空位后自动开始」；停止排队释放原冻结积分，不提交模型。
- 通用 `MaterialVideoJob`（含画布、视频生成区、短剧和带货视频）从开始提交直到上游终态占用一个名额；每个候选单独计名额。配音与口型同步沿用原 IpRun/Job 检查点，跨轮询步骤保留名额。
- 旧应用通过共享 `UpstreamModelHttp` 的 `/chat/completions` 与 `/images/generations` 同步请求也计入同一额度；已有 Studio 任务的内部调用不再占第二个名额。旧同步接口等待发生在原请求内，最长十五分钟；不会在重启后重新发送一个已经失去调用方的同步请求。其他独立供应商协议、音乐生成和真人训练未据此宣称已统一排队。

重启后发现已提交且尚未执行的任务并恢复排队。已受理的视频仅查询原外部任务 ID；本地轮询超时/失败仍保留名额，确认上游成功或失败才释放，避免厂商还在生成却放行下一批。无法确认是否受理、也没有外部 ID 的请求保守保留名额并报告 `VIDEO_SUBMISSION_UNKNOWN`，需运营核对原请求；不能自动重提。此类人工容量解除的管理操作仍待补齐，见 TODO。

排队不计入生成超时，不由孤儿冻结清扫器退款；用户明确停止或任务明确失败才按原账本流程释放。未知视频受理仍沿用原视频失败退款政策，保留容量票据不代表另收一次积分。存在等待/执行票据的端点禁止删除。

验证以数据库并发测试、供应商调用计数和 UI 排队/停止回归为主，不触发收费模型或反复验收图片质量。具体结果见 [统一验收记录](releases/ip-studio-unified-canvas-validation.md) §36。

## 排队位置（v0.221，本地未发布）

`IpRun.queue` 返回实时 `position / waiting / running / concurrencyLimit`，每次项目、运行和历史读取重新计算，不存成第二份调度状态。position 从 1 开始，只计算同一端点的等待票据；正在执行的任务另列 running，不算前面的排队项。取消或开始执行后 queue 为 null。视频每个候选独立返回 `output.videoCandidates[].queue`；整批均等待时，运行级 queue 显示该批最近的一个位置。只返回聚合数量，不公开其他用户的任务或内容。

前端复用原运行轮询，每 1.2 秒刷新一次；网络失败保留原请求和最后状态，延迟重试并显示更新中断提示。任务面板、画布节点、模板及连续制作共用排队文案。节点标题简写「排队第 N 位」，正文采用用户指定的「排队提醒：当前模型请求量较高，你目前排在第 N 位。」；任务面板补充前面等待数量和执行数量。接口未返回序号时仅显示等待空位，不猜数字或倒计时。排队等待可以停止；已受理的视频继续查原任务，不能用停止排队重提。

本轮定向验证记录在统一验收 §37；不追加收费图片/视频生成。

## 图片受理未知的执行名额（2026-10-22）

图片任务已经结束 HTTP 调用、但未确认供应商受理时，`generate + running + image.provider.recovering + STUDIO_IMAGE_SUBMISSION_UNKNOWN` 只保留待核对凭据和原冻结，不继续占用端点执行名额。`countOccupyingSlots` 直接按原运行状态排除这类票据，准入、自动派发、`queue.running` 共用；无需迁移或改写存量任务。票据自身仍为 running，以保留原任务恢复和端点禁止删除的保护。

此调整不证明供应商未受理，也不触发重提、退款或改变企业在途授权。已知图片恢复查询、视频和音频的容量规则保持原样。画布、任务列表和历史显示“受理结果待核对”及联系运营/勿重复生成提示，不显示固定 10% 或无限转圈；正常图片只显示真实阶段。已有后台仍按原请求证据核实结果或确认未受理后释放原冻结。

## 线程池、卡死和上游并发拒收（2026-11-05）

2026-11-06 后续调整（待发布）：共享 `ipRunExecutor` 默认线程数从 24 提高到 30，与用户要求的端点并发上限配套。四个 GPT Image 2/2.5 接入点的并发 30、请求超时 30 分钟已通过线上配置生效；线程池改动需要 server 发布重启后才生效。仍与文字任务共享线程，端点上限不代表供应商一定接受同等并发。

起因：导演台批量出图时，最后 3 张排了 47 分钟，重启才开始。查下来是三件事叠在一起：

1. **Studio 工作线程只有 3 个。** 端点上限写 5，实际最多同时跑 3 个，文字任务也在这 3 个里。现在默认 24（`aep.ipstudio.max-concurrent`），够 GPT Image 2.5 和 GPT Image 2 各跑 10 个，再留几个给文字任务。每个端点的上限仍在后台配置。
2. **等上游没有总时限。** 三个线程发出请求后一直没等到正文，占到服务重启。`HttpRequest.timeout` 只管到响应头，网关先回头、正文不来时会一直等；线上也有 704 秒才回的图，而这个端点的超时写的是 600 秒。现在图片调用带 `ModelCallCtx.boundBody`，到时间就中断，按受理未知处理；同时要把端点的 `requestTimeoutMillis` 配到比真实耗时长（GPT Image 2.5 配 900 秒），否则正常的慢图也会被切断。
3. **同一张票反复进线程池。** 线程全忙时，分发器每 30 秒把同一张等待票再塞一次，塞满 128 条等待后就一直 `TaskRejectedException`。现在线程池没有空位时不派发，等待的真值只在 `ai_generation_queue`。

**上游并发拒收回队列**（只做了图片）：提交时收到 429，或错误内容明确说并发、限流、过载（`ModelQuotaAlerts.isRateLimited`），或网关返回 503 并说「没有可用通道」（`No available channel for model … under group …`，`JusuanImageClient.noAvailableChannel`，只认 503），算没有受理。任务回到等待，冻结不动，已出的图不动，界面照常显示排队位置；等 30、60、90、120 秒（封顶）后用新的请求号重交，因为已被拒绝的旧请求号可能拿回上次的拒绝。同一张连续等满 30 分钟还没成功，按 `STUDIO_IMAGE_PROVIDER_BUSY` 失败并退积分。

这些不回队列：额度用完（排多久都没用）、内容审核和参数错误、没有明确说法的 5xx（可能已经受理，仍走受理未知，不能重交）。任务受理后才失败的也不重交。

截至 2026-11-05，线上 14 天的图片调用没有出现过真实的并发拒收（429 只在测试里），判断依据是常见写法，第一次真遇到时要看 `[ipstudio] 生成服务因并发拒收` 日志核对。2026-11-04 20:38–21:06 的 5 次 503「没有可用通道」（CATech · GPT Image 2，0–14 秒内就失败）在这条规则之前被当成受理未知，退款后让用户重试；现在回队列，通道恢复后自动出图，通道一直不恢复则等满 30 分钟按 `STUDIO_IMAGE_PROVIDER_BUSY` 失败退款。文字任务、视频、配音还没有这条逻辑。

## 导演台的默认图片模型（2026-11-05）

AI 图片和导演台共用 Studio 图片的开放范围和售价，默认模型可以不同：导演台读平台配置 `ai.scene-default.studio.director-image`（`{"endpointId":"..."}`），用模型管理命令 `directorImageDefaultSave` 设置，必须在开放范围内。没配时跟 Studio 图片的默认走。作品设置里明确选过模型的不受影响。Web 短剧（web-drama）走自己的 `IMAGE_GENERATION` 绑定，和这两个都无关。
