# 数字资产中枢 · 产品与前端重构设计

> 状态：**进行中**（P1 开发中）· 2026-08-29 立项
> 来源：与产品负责人的脑爆收敛（本文件是唯一真源；页面草图见 Claude 画布
> 「数字资产新版草图」https://claude.ai/code/artifact/361cb844-fb3e-43cf-8aa8-a2247934e7af）。
> 范围：`apps/web-aiavatar` 产品级重构 + 后续跨 app 资产联动；server 改动在 P2 起逐步落。

## 1. 背景与结论

web-aiavatar 当前是 Figma Make 原型的忠实移植（`src/proto/*`，createElement + 内联样式，
strict off，单页 + hash 覆盖栈）。功能不少但呈"堆积"状：六类资产平级铺开是数据库视角，
不是用户视角；各链路（授权 / 创建 / 合成 / 审核）没有贯穿的故事线。

**结论**：把数字资产从「数字人工具」升格为**生态资产中枢**——全生态可复用数字物
（数字人、明星形象、声音、歌曲、场景、产品、风格、logo、小说/剧本…）在这里
登记身份、管理授权、归集使用记录；下游 app（music / drama / celebrity）从这里取资产
生产内容，产物回流记账。

### 中枢模型：四个动词

| 动词 | 含义 | 现状基础 |
|---|---|---|
| **注册** | 资产在中枢登记统一"档案卡" | dap 域六类资产已有 |
| **引用** | 下游 app 取资产去生产（选择器） | v0.61 import-avatar、v0.60 references |
| **回流** | 下游产物记回中枢，挂"已用于"两清单 | dap_asset_usage（合成线已有） |
| **授权** | 资产与使用者之间的一等合法性对象 | v0.105-107 双证据真人授权、web-star 明星审批 |

**档案卡（统一信封）**：每个资产不论类型共享同一组字段——编号、名称、类型、权属、
来源（实拍 / AI 生成 / 授权引入 / 跨 app 回流）、版本、授权状态、关系（属于哪个 IP /
用了什么 / 被用在哪）。类型只决定专属载荷、能力开关、详情模板。

### 已拍板的产品判断

1. **明星授权分工**：申请与审批走 web-star（明星侧管控），中枢只做用户侧货架 +
   使用入口 + 证书展示。同一条授权记录，两端各看各的视角。
2. **回流第一期范围**：music（数字人 × 歌曲 → MV）+ celebrity（明星形象 → 带货短视频）。
3. **使用量化从第一天记**（usage 事件不可回溯补），展示可后置。
4. **数字人的"资产制作"只在中枢**（形象/声音创建、刷脸授权、训练）；"内容生产"在下游。
   入口到处都是（下游选择器带"＋创建"跳转中枢），流程只有一套。
5. **产物 ≠ 资产**：下游产物默认是"产出记录"，定稿/收藏才晋升为正式资产。
6. **设定卡**（三视图 / 表情 / 服装配件 / 色板 / 人设）并入资产名片：既是展示物
   （可导出整版图分享），更是生产资料（喂生成模型保一致性）。是引导补全的加分项，
   不是出片门槛（保持"一段视频起步"红线）。

### 两条铁律（写给所有后续实现）

1. **中枢不阻塞下游**：回流、记账、晋升全部旁路 best-effort（同 AGENTS §8.0 观测类例外）；
   唯一允许阻塞的是**授权检查**（无有效授权不建单不扣费，既有 `DAP_LICENSE_REQUIRED` 范式）。
2. **联邦不集中**：歌曲真值在 music 域、短剧在 drama 域；中枢只持有注册索引 + 使用边 +
   授权记录，详情页聚合。血缘只做两张表（"用了什么"/"被用在哪"），不做图引擎。

## 1.5 授权市场转向（2026-08-31 决策）

线框图评审后确定：数字资产从「只读的私有资产账本」扩展为**官方资产的授权入口**。

### 已拍板

1. **暂不涉及分成结算**：只做授权链路本身，收款用最简单的支付实现，后续流程（开票、对账）
   先走人工。
2. **供给侧只有官方**：不做用户上架、不做用户之间的授权交易 —— 因此不触碰「本人授权平台使用」
   被扩张成「售卖给第三方」的合规红线。
3. **明星统一为数字资产**：明星形象与官方角色并列展示，卖的是形象授权；点击「去申请」跳转
   既有明星授权端（celebrity 申请 + web-star 审批），**不新建重叠流程**。
4. **授权档位**：标准 / 商业 / 独家三档（价格与范围由业务方最终确定）。

### 设定卡的形态（⑥ 动态杂志版）

设定卡从「资料表单」改为「角色主页」，核心是把已有的衍生物变成可切换的展示：

| 切换组 | 消费的既有资产 |
|---|---|
| 动作（待机 / 说话 / 转身） | 运镜短视频衍生物 |
| 表情 | 表情图集 |
| 视角 | 三视图（多角度图集） |
| 声音 | 绑定音色，带波形试听 |
| 换装 | 换装变体 |

**新增需求 —— 默认待机循环视频**（**已落地 2026-08-31**）：设定卡首图必须是循环视频而非静态图。
**数字人定稿后自动生成一段约 6 秒的待机循环**（复用运镜短视频衍生链路），作为该角色默认首图。

落地约束（`DapWorkflowService.autoIdleLoopAfterFinalize`，挂在 `/avatars/{id}/finalize` 之后）：
- **不阻塞定稿**：内部吞掉全部异常，只记 WARN；生成失败时首图退回定妆图静态展示（§1 铁律 1）。
- **不向用户计费**：系统发起而非用户点按钮，`cost=0` 不走 hold；平台承担成本，
  运维开关 `aep.dap.auto-idle-loop`（默认 true）、时长 `auto-idle-loop-seconds`（默认 6）。
- **不重复建单**：已有或正在生成 video 衍生时跳过；真人线缺已审核素材时同样跳过。

### 合并后的信息架构（2026-08-31 定案 —— 取代 §2 的三 Tab 方案）

**关键判断：这是「个人数字资产页」，不是纯商城**。所以"发现"里同时放自己的资产和官方可授权
资产 —— 于是原先冲突的「工作台/资产/我的」与「发现/制作/设定卡/我的」两套导航合成一套：

```
资产（首页）  顶部两段：我的资产 | 官方资产
              · 我的：自建 + 授权得来的，来源用标签区分（自建 / 官方授权 / 明星授权）
                段顶保留精简状态条（进行中的事：授权待补 / 生成中 / 审批中）
              · 官方：角色名录（B 版形态），可授权；明星形象点「去申请」跳既有明星端
制作          创建数字人（真人复刻 / AI 原创，五步链路换新壳）
我的          账号 · 授权中心（授权给我的 / 我授权出去的）· 算力 · 存储 · 设置
              最近动态并入此处
```

- **设定卡不做 Tab**：它属于某个具体角色，是资产详情页的形态（⑥ 动态杂志版），
  从任一资产卡进入。解决了「设定卡 Tab 指向哪个角色」的问题。
- **已上线的工作台退役**：总览数字与状态条并入「资产 · 我的」段顶，动态并入「我的」。
- 视觉方向：发现 / 详情 / 制作三屏采用 **B 版（角色逻辑）** —— 立绘铺满卡片、名字大衬线、
  性格与一句话介绍代替参数、价格退到角落。

### 官方资产（最小实现）

不新建资产池表。官方资产就是普通资产 + 一个上架标记：

- 资产实体加字段：`official`（是否官方）/ `listingStatus`（上架状态）/ 三档价格（分为单位整数）。
- 来源两条：**管理员账号创建**后上架；**明星端创建**的明星形象上架。二者都只是"创建者身份不同"，
  不改资产模型。
- 用户自己的资产**不可上架**（§1.5 已拍板：不做用户之间的授权交易）。

### 授权购买链路（标准支付流程）

复用 v0.94 多渠道支付基建（`PaymentGatewayRegistry` / `PaymentService`），业务单独立于充值单：

```
选档位 → 建授权订单（created）→ 走支付渠道 → 渠道回调
       → 幂等 settle（条件 UPDATE，同 settlePaidOrder 范式）
       → 生成授权记录（含档位 / 范围 / 有效期 / 订单号）
       → 该资产进入用户「我的资产」，来源标签 = 官方授权
```

- 新增两表：**授权订单**（owner / assetId / tier / priceCents / status / channel / externalOrderId /
  paidAt）与**授权记录**（owner / assetId / tier / scope / expiresOn / orderId / status）。
- **这是真钱，不走积分账本**；但幂等与对账纪律照 AGENTS §4.2 与支付线既有范式执行。
- 未支付成功绝不生成授权记录；授权检查照旧是唯一允许阻塞出片的闸门（§1 铁律 1）。
- 开票、退款、对账等后续流程本期走人工（§1.5 已拍板）。

## 2. 新版信息架构（移动端 H5，保留白底 + 青 #12B3DE + 衬线资产身份令牌）

```
底部三 Tab：工作台 · 资产 · 我的

工作台 /            资产总览数字 + 进行中的事（授权待补/审核中/生成中）+ 最近动态
资产   /assets      人物与形象大卡（衬线名 + 编号 + 授权徽章 + 被使用次数）
                    ↓ 声音与歌曲分区 ↓ 素材库（场景/产品/风格/logo 收纳为"搭配素材"）

                    ↓ 设定卡区（完整度 / 三视图 / 表情 / 服装配件 / 色板 / 人设）

我的   /me          账号 + 授权中心入口 + 算力/存储/设置
```

删除项：手机壳 / 微信 chrome 演示装饰；六类资产平级网格。

## 3. 前端重构策略

### 3.1 双轨迁移（P1 核心决策）

老 `src/proto/App`（hash 路由 SPA）**整体保留并挂到 `/studio`**，继续承载所有"写"流程
（创建链路、真人刷脸授权、素材录制、合成工作台、声音克隆、设置等）——这些链路
（尤其 v0.105-107 授权链）是花大功夫做对的，只换壳不重写逻辑。

新的"读"界面用 **Next App Router 真路由 + JSX + 现有 CSS 令牌**重建（上表 5 个路由）。
新页面需要进写流程时深链到 `/studio#/...`。

**兼容红线**：七牛刷脸回调与历史分享链接都指向根路径 hash（`/#/real-auth/{id}`、
`/#/avatar/{id}` 等）。根路由挂**hash 转发器**：识别旧 hash 前缀一律
`location.replace("/studio" + hash)`。此转发器在 /studio 流程全部迁完前不得移除。

### 3.2 数据层

P1 完全复用 `src/proto/api.ts` 的域 API（AvatarApi / AssetApi / LicenseApi / JobApi /
ComposeApi / VoiceApi / AccountApi / AuthApi），mock/live 双模式行为不变。
api.ts 按域拆文件是 P3 工作项，不与页面重构混做。

### 3.3 诚实数据原则（§8.0 前端版）

新页面只展示真实端点已有的数据：
- 被使用：`/avatars/{id}/references`（music/drama 引用）+ compositions 过滤；
- 进行中的事：running jobs + 待补确认授权（evidenceStatus=legacy_unconfirmed 等）；
- 最近动态：AssetSummary.recent + 最近合成；
- 设定完整度：由已有槽位（标准图/衍生/音色/人设字段）前端推导。
没有的数字不编造；未接通的入口不做假按钮（建设中标注或不出现）。

### 3.4 类型与样式

新代码全部 JSX + 明确类型（实体类型 import 自 `src/proto/data.ts`，它仍是契约真源）；
`tsconfig strict` 全局仍 false（proto 松类型），新目录以代码纪律保平，P3 拆 proto 后再开。
样式沿用 `globals.css` V4 令牌（inline style + CSS 变量，与 proto 同语言，不引入 Tailwind）。
