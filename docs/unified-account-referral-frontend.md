## 最新调整：Studio 品牌邀请页（设计稿）

用户指出直接进入 ID 通用邀请页脱离 Studio。正式分享入口拟改为 Studio `/invite/{code}`，先展示产品品牌、邀请人与创作示意，邀请区直接输入手机号、验证码并注册；取消“接受邀请”和中间弹窗。短信校验、建号与绑定仍归 ID，成功后进入 Studio。邀请关系仍是 ID 唯一真值，不因来自不同应用而另建关系。此调整先交付[独立可交互原型](../prototypes/studio-invitation/README.md)与[设计说明](prototypes/studio-invitation-design.md)，不把设计稿当成已接入功能；下文描述首版现状。

## 1. 页面与入口

后端、原始邀请关系与注册绑定归统一账号中心 `aibuzz-id`。前端同时提供 Studio 内的管理视图和中心的注册落地页：应用内可以操作本人邀请链接、查看邀请人和记录，不必跳出 Studio 才能管理。中心自己的账号门户保留同一能力，二者读取同一份数据。

| 位置 | 已实现入口 | 内容 |
|---|---|---|
| 账号中心概览 | “我的应用”之后的“邀请朋友”分区 | 进入我的邀请；不挤占主要的应用入口 |
| 我的邀请 | `/account/invitations` | 复制邀请链接、查看邀请人和直接受邀记录 |
| 公开邀请落地页 | `/i/{code}` | 邀请人、注册说明、继续按钮 |
| 现有登录/注册流程 | 沿用原路径 | 保留一条“来自某人的邀请”提示，无需重建注册表单 |
| Studio | `/invitations`，桌面账号侧栏/总览与手机“我的”入口 | 应用内生成、复制、预览链接，查看邀请人、直属记录、刷新和分页 |

Studio 使用当前用户 Bearer 令牌直连配置的 ID issuer。`GET /api/me/invitations` 读取视图与 `canInvite` 操作权限，`POST /api/me/invitations/code` 由 ID 生成链接码。请求不带产品 `X-App-Code` 或 Cookie；401 复用现有单次刷新。Studio 后端不新增接口、表或邀请规则。邀请页只要求统一账号登录，不依赖产品开通；未登录经现有 OIDC 回到 `/invitations`。

## 2. 我的邀请

沿用账号中心二级页结构，页首“返回我的账号”。内容按动作优先排列：

```text
← 返回我的账号

我的邀请
邀请朋友注册声量算法账号

邀请链接
https://id.aibuzz.cn/i/……        [复制链接]

我的邀请人
头像  昵称                       邀请记录时间

我邀请的账号                         共 N 条记录
头像  昵称                           注册邀请时间
头像  昵称                           注册邀请时间
                                  [上一页] [下一页]
```

- 未生成链接时显示“生成邀请链接”，通过带 CSRF 的 POST 创建；GET 不悄悄写入。生成后第一主操作是“复制链接”。链接可选中，复制成功显示“邀请链接已复制”；失败显示“请选中链接手动复制”，不能显示假成功。
- 不单独突出一份手输邀请码；本期从链接进入即可，不增加输入邀请码页面、分享海报或二维码生成依赖。
- 默认列表每页 20 条，按邀请时间倒序；使用稳定次序和服务端分页，不一次拉取全部记录。
- “我的邀请人”没有记录时显示“没有注册邀请记录”，不显示“你从未被邀请”。
- 受邀列表为空显示“还没有邀请记录”，下方一句“复制上面的链接，发给朋友即可”。不重复增加同一主按钮。
- “共 N 条”是本人发起的原始邀请记录数，不叫“有效人数”“活跃人数”或“邀请收益”。不需要为页面增加这些新统计。
- 昵称、头像按当前允许展示的资料读取；没有昵称用“用户”，没有头像用现有账号图标；不为了列表强制索取微信资料。
- 已注销账号显示“已注销账号”；已合并记录可标“账号已合并”，不在普通用户页面展示新账号 UID 或跳转到别人的资料。
- 不允许点受邀账号修改其资料，也不提供改绑邀请人按钮。


### 2.1 Studio 内的邀请管理

采用现有 `AccountWorkspace`，桌面侧栏选中“邀请朋友”；账号总览进入同一个 `/invitations`。手机“我的”增加同名入口，页面顶部可返回账号页。内容为：

1. **我的邀请链接**：未生成时显式生成；已有链接时提供只读链接框、复制及预览。所有写入结果来自 ID，不用浏览器临时码。
2. **我的邀请人**：昵称、头像和邀请时间，没有记录则如实说明。
3. **我邀请的账号**：真实总数、直属列表、账号现状、邀请时间、刷新及服务端分页。列表没有资料修改或邀请人改绑动作。
4. **关于邀请记录**：简要说明注册时记录和后续分佣边界。

链接管理本期实现生成、复制和预览，不虚构停用、重置或收益配置。`canInvite=false` 时不渲染生成/复制操作；服务端仍校验权限。旧登录模式说明当前不可用；运营附身状态不将产品侧附身令牌发送给 ID。读取失败不显示假空列表，刷新失败保留上次记录，复制失败选中链接并提示手动复制。

页面复用 Studio 的深墨按钮、纸白内容区、账号侧栏、字体和焦点样式；主链接区优先，记录用行列表，手机输入框独占一行。无新增分享海报、收益卡片或营销图。

## 3. 邀请落地页

品牌统一用“声量算法账号”，不使用 Studio 专属名称、图标或权益承诺。

```text
声量算法账号

某某邀请你注册
邀请人的必要展示信息

注册后，会记录这次邀请关系。
已有账号登录不会改变原邀请关系。

[接受邀请，继续]
不接受邀请，普通登录 / 注册
```

点击主按钮后进入已有注册/登录流程，服务端携带该次邀请码。普通入口清除当前流程的邀请选择，用户可不接受邀请；仅打开链接、预抓取或刷新页面不建立关系。

此页在进入现有微信自动跳转逻辑之前展示。用户做出选择后再继续已有身份验证；不能因已有自动登录逻辑跳过邀请说明，也不要求重写整个扫码过程。

未登录时不猜测用户是不是新账号。身份验证后发现已有账号，正常登录，提示“你已有账号，本次没有新增邀请关系”。不暴露验证前的账号存在性。

## 4. 已登录与异常情况

| 状态 | 页面反馈 | 操作 |
|---|---|---|
| 已登录老账号打开别人的链接 | “你已有账号，本次不会新增邀请关系” | “返回我的账号”；可提供显式“切换账号”，不自动退出当前账号 |
| 打开自己的链接 | “这是你自己的邀请链接” | “查看我的邀请” |
| 邀请码无效或码主不可用 | “这个邀请链接暂不可用，你仍可正常登录或注册” | 普通登录/注册入口 |
| 加载失败 | “邀请信息暂时无法读取” | 重试；普通登录独立可用，不把网络故障当作邀请码无效 |
| 邀请码生成/读取失败 | “暂时无法取得邀请链接” | 重试，复制按钮不可用，不生成浏览器端临时码 |
| 列表读取失败 | “邀请记录暂时无法读取” | 重试；服务端页面保留重试入口，不用空列表冒充读取成功 |
| 注册和关系已提交 | “注册完成，这次邀请已记录” | 继续原流程或返回我的账号；仅根据服务端真实结果显示 |
| 普通注册或老账号登录成功 | 沿用原成功反馈 | 不显示“邀请已记录”，不增加多余成功页 |
| 注册写入失败 | 原注册页明确失败/重试 | 不假报注册或邀请成功，不由前端补写关系 |
| 合并到了已有账号 | 沿用现有合并提示；本次原始邀请保留历史语义 | 不宣称邀请人已绑定到合并后的账号 |

以上使用页面内反馈，不增加每次成功都要确认的弹窗。Studio 的操作错误与列表读取错误分开显示，真实空态只在 ID 成功返回后出现。不在匿名页面显示完整手机号、账号 UID、邀请人数或邀请链。

## 5. 视觉、手机与无障碍

账号中心已有“身份行 → 我的应用 → 登录方式与安全”的信息层级、浅色门户、行列表和二级任务页；本功能沿用这些组件与颜色令牌。邀请落地页是登录前任务，沿用账号任务页的品牌、容器和表单组件，不另起营销长页。

- 桌面：我的邀请沿用门户二级页容器；链接、邀请人、列表纵向排列，不新增仪表盘侧栏。
- 手机：单列，复制按钮在窄屏可独占一行；长链接在只读框内可选中，长昵称换行，不能撑宽页面。
- 沿用本仓现有规则：输入文字 16px、邀请链接框高 52px、按钮和链接可点区域至少 44px。这里是账号中心的设计标准，不将 44px 误称为 WCAG 2.2 AA 的通用最小值。
- 键盘焦点可见，按钮和链接有明确名称；复制成功用 `role=status`，错误使用 `role=alert` 或聚焦错误摘要，结果不只靠颜色表达。
- 无 JavaScript 时仍可查看邀请人、注册、分页和手动复制链接；脚本只增强复制与反馈，不作为保存邀请的真值。
- 不展示“本体”“关系节点”“图投影”等实现术语，不展示用户未获得的奖励、积分和等级。

交互参考：[W3C 目标尺寸说明](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)、[状态消息说明](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)。

## 6. 运营追踪与后期整体链路

第一期已提供运营查询 API，尚无新的运营界面。后续若提供页面，放在获授权的统一运营界面，最小形态是：输入 UID → 查看该账号的原始邀请人及直接受邀列表 → 点“继续向上查询”查看链路。每次请求由账号服务校验权限，不因知道 UID 就可查询。不要为此新建一套运营后台。

后期需要整体关系图时，再增加只读“关系图”视图：节点为账号，边只表示注册邀请；账号合并使用另一类线和明确图例。选中节点查看直接邀请人、直接受邀记录及时间，逐步展开，不能把全生态记录一次下发到浏览器。

本体定义约束图中每条边的含义；前端负责展示，并不推断或回写关系。第一期不做无限画布、关系编辑器、三级团队面板或佣金看板。

## 7. 前端验收

1. 账号中心与 Studio 均能发现入口；Studio 进入应用内管理页，未登录经中心授权后回到原页面。
2. 新用户从链接完成注册，服务端有关系才显示“已记录”；已有账号不误提示成功。
3. 无效码、网络错误、真实空列表、复制失败分别有正确反馈。
4. 两个邀请标签页不串来源，普通注册选择不会偷偷保留本次邀请。
5. 320px/390px 与桌面无横向溢出；键盘和无脚本流程可用。
6. 普通用户无法查看别人的邀请列表，匿名页不泄露联系方式或完整关系网。

本地已验证生成/复制邀请链接、接受邀请、短信新注册的真实成功反馈、双方记录、320px/390px 与桌面、关闭脚本后查看与手动复制入口。专项测试覆盖已有账号、微信网页/扫码和小程序 grant、无效码、CSRF、权限与并发。具体证据及未验收范围见 [验收记录](releases/unified-account-referral-validation-20261017.md)。

实页结构：`aibuzz-id` 的 `invitation.html`、`account-invitations.html`、`invitation-scan.html`，复制增强位于 `invitations.js`，布局位于 `invitations.css`。登录页仅增加邀请提示；公众号扫码在授权建号前增加说明与一次明确确认。

分佣的预留是保留邀请事实的稳定标识和独立业务扩展边界；当前不放收益数字、提现按钮或空的分佣菜单。

Studio 增量验收：真实 OIDC 登录回跳、应用内生成与复制、中心链接预览、新受邀者注册后 Studio 刷新显示一条真实记录、手机账号入口、桌面/320px/390px 无溢出；详见验收记录末节。

## 直接注册接入（2026-10-17）

Studio 新增公开 `/invite/{code}`，按已确认原型直接展示手机号和短信验证码。邀请管理生成的链接采用当前 Studio origin，与 ID 通用 `/i/{code}` 并存。

页面无 Cookie 跨域调用 ID 公共预览（只读展示名）、原有短信发送和 SMS grant；申请 `openid profile phone offline_access`。登录成功整页进入 `/dashboard`，共享令牌存储及刷新继续生效。ID 不建立浏览器会话，跨产品 SSO 仍走原 OIDC 授权码流程。没有新增产品后端邀请接口、关系表或业务规则。

邀请码读取失败时先重试，不允许丢弃邀请继续注册；明确失效时提示并允许普通注册。短信失败/验证码错误保留表单。手机号变更清空验证码，发送期间禁改号码，页面不内置固定验证码。邀请关系只在 ID 首建 UID 事务里记录；已有账号直接登录，不重绑。

ID 注册只写身份及首次邀请关系；进入 Studio 后产品按既有开通和权益策略建档，不因邀请新增赋权。本次现网既有策略为 GRANT_ALL，已在生产记录单独说明。

生产状态：2026-10-17 已完成直接真实短信注册、进入 Studio、双方邀请记录、生成/复制链接及数据库一致性验收，见[发布记录](releases/unified-account-referral-production-release-20261017.md)。
