# Studio 企业积分管理：开发任务

> 2026-10-15 · 对应 [方案 v0.4](ip-studio-team-accounts-plan.md) · 已生产发布，部署与验收见 [发布记录](ip-studio-enterprise-production-release.md)，任务执行状态以 TODO 为准。
> 已确认：企业分配积分仍归企业、可回收；产品开通沿用现有逻辑，不做企业席位。本文描述交付与验收，[TODO](../TODO.md) 统一记录执行状态。

## 1. 开发顺序

| 批次 | 任务 | 可验收的结果 |
|---|---|---|
| 一：基础 | E01 契约 → E02 数据 → E03 权限、E04 钱包 | 企业与个人账户隔离，原个人功能正常 |
| 二：积分 | E05 分配回收、E06 财务充值 | 人工充值后可单人/批量发积分，流水守恒 |
| 三：消费 | E07 生成准入 → E08 结算与退出 | 成员真实使用企业积分，失败和退出不丢账 |
| 四：界面 | E09 企业/成员端、E10 财务端 | 管理、消费、充值能从页面完成 |
| 五：交付 | E11 集成验收 → E12 发布准备 | 通过并发、回归及迁移检查，具备上线条件 |

每个任务建议独立提交，测试随任务完成；前三批可在开关关闭状态合并。E07 未完成 E08 前不得开放收费入口。界面可提前使用契约 mock 开发，完成必须接真接口。

## 2. 任务卡

### E01 · 固定接口和资金语义

**依赖：无。位置：** `packages/types/src`、`specs/openapi.yaml`、`specs/BUSINESS_RULES.md`。

- 定义企业、成员、角色能力、三种余额、充值单、划拨单/批次、消费记录和错误结构；新增接口明确标注计划状态，随实现同步。
- 接口覆盖企业创建/查询、邀请/接受、成员管理、模型/在途策略、余额/流水、分配/回收、充值申请、财务核准、退出/移交/关闭；前台归 aiavatar 产品路径，财务归原后台权限。
- 生成请求增加 `billing.mode=personal|enterprise`；企业账户由服务端解析，不接受客户端任意 walletId。旧请求默认个人，幂等指纹包含付款选择。

**完成标准：** 每个接口都有角色、数据范围、幂等与错误定义；列表服务端分页；不增加席位、配额或共享作品接口。

### E02 · 企业与资金数据迁移

**依赖：E01。位置：** server 新 `enterprise` 域、现有 Wallet/CreditHold/Ledger/RechargeOrder 模型及两处 Flyway 目录。

- 新增 Enterprise、成员与邀请、当前企业归属、历史关系、策略、划拨单/批次、审计。当前归属以 userId 唯一记录保证单企业；停用保留，退出释放；重新加入创建新的关系版本。
- 扩展个人、企业主账户、企业成员账户；企业成员账户按企业与用户唯一关联，历史账户不删除。保存实际操作者、付款账户、企业、成员关系版本和原计费引用。
- 个人钱包 ID/余额/历史账本不变；旧 userId 查询、非空约束、财务关联全部检查，不能用假用户承载企业钱包。新迁移编号开发时查 SQL/Java 两处取得。

**完成标准：** H2/MySQL 均可迁移；两企业并发邀请不能形成双重当前归属；迁移前后个人余额、冻结与开通状态一致。

### E03 · 企业关系与 RBAC

**依赖：E02。位置：** 新企业服务/controller、现有 security、ProductRouteTable。

- 实现企业创建、邀请/接受、成员查询、角色/能力管理、主账号移交；唯一 owner 和单企业关系在事务中保证。
- 集中校验企业、成员、角色及目标对象；管理员不能提权自己、管理 owner/其他管理员或给自己分配积分。受邀用户仍走现有登录、手机号及产品开通规则。
- 写操作审计、接口防越权；角色不塞入长效 Token。状态变更与积分回收的最终接口由 E08 完成，不能先上线只改状态的半条流程。

**完成标准：** 直接调用隐藏接口也被拦截；企业角色不能访问平台财务权限或成员私有画布；并发移交后只有一个 owner。

### E04 · 统一钱包记账核心

**依赖：E02。位置：** CreditService、WalletRepository、CreditHold、LedgerEntry、个人钱包/后台财务查询。

- 增加按钱包 ID 记账的内部核心；原按 userId 的方法保留为个人包装。企业主账户供分配，生成只扣成员企业账户或个人账户。
- 保留冻结、按实际结算、释放和原桶分布；新增划拨出入账类型，明确属于积分面，不伪记充值收入或 SPEND。
- 幂等命中必须核对原钱包/金额/授权；所有余额写入经账本，统一多账户锁顺序。新增账户类型不得导致旧财务统计漏账或空指针。

**完成标准：** 个人消费回归通过；跨钱包引用冲突被拒；充值、划拨、消费、冻结分别可核对，不重复累计收入。

### E05 · 单人及批量分配/回收

**依赖：E03、E04。位置：** 新企业划拨服务/controller、转账及批次模型。

- 企业主账户与成员企业账户等额划拨，保留充值/赠额来源及桶属性；不能转到个人账户或另一企业。
- 批量先返回人数、逐项金额及总额，提交时重新校验；批次幂等、成员去重、限制批次大小。首期整批成功或整批失败，金额变化需重新确认。
- 回收只取可用积分；与生成冻结共用锁规则，禁止回收冻结额。返回双方流水及批次详情。

**完成标准：** 重复点击只转一次；余额不足整批回滚；并发消费/回收不超支；企业全部账户积分总和在划拨前后不变。

### E06 · 财务人工充值、退款和企业报表

**依赖：E03、E04、E05。位置：** RechargeService、AdminRechargeOrderController、RechargeOrder、退款/对账服务。

- 企业发起充值申请；平台财务登记实收金额、入账积分、收款凭据和目标企业快照。核准时复用原订单入账机制；同一逻辑充值请求幂等，重复收款凭据进入核对。
- 扩展现有套餐依赖以支持人工订单；金额和积分固定在订单，不使用赠送入口或修改公共套餐冒充。个人现有充值流程保留。
- 退款关联原订单，先核对并回收可退的企业可用积分；原单存在冻结时先等在途结算，不回收已消费，不动个人余额。提供企业待分配、成员可用、冻结和实耗汇总。

**完成标准：** 重复核准不重复到账；退款/重复回调不重复退；划拨不增加充值收入；owner 变更不改变原订单目标。

### E07 · 全部生成入口接入企业付款

**依赖：E03、E04、E05。位置：** IpRunService、StudioWorkflowService、StudioSpeechService、StudioLipSyncService、StudioVideoService → MaterialVideoJobService 及其上层编排。

- 把实际操作者、资源 owner 与付款钱包分开，原本人画布/素材检查保留；企业资金只开放 Studio 指定用途，其他产品仍走个人逻辑。
- 服务端最终模型须在允许集内；成员在途上限包括排队、运行和受理待核对，零费用供应商任务也计数；平台端点队列继续独立限流。
- 预检后在同事务复核权限、余额、在途数并保存授权/任务/冻结，afterCommit 派发。重试固定原账户、价格和成员关系版本；视频包装与实际 job 只冻结一次。

**完成标准：** 输出所有入口到实际扣费引用的清单；不足额不混扣个人资金；模型降级不绕过名单；并发任务不突破余额/在途上限。

### E08 · 结算、停用、退出与恢复

**依赖：E03、E05、E06、E07。位置：** 各生成 worker、取消接口、IpRunReaper、CreditHoldSweeper、对账服务、新企业生命周期服务。

- 成功/部分成功/失败的任务状态、账本和授权终态同事务；重复终态幂等。未知供应商受理查询原任务，不先退款再重新提交。
- 停用/退出先阻止新企业消费并回收可用额；未提交供应商的任务取消，已受理继续结算。旧任务释放先按原冻结退回，再原子归集至原企业主账户，留下两步流水。
- 用授权保存的关系版本识别“旧成员任务”，成员退出后重新加入也不能拿到旧任务退款。转企业不移动旧冻结；关闭企业须排空在途、处理待付款/未对账订单和余额。

**完成标准：** 停用与消费并发不漏授权；退出/重入/转企业后的退款归原企业；进程重启和派发失败可恢复原任务；没有孤立冻结。

### E09 · 企业与成员前端

**依赖：E01 可开始页面开发，接入依赖 E03、E05–E08。位置：** `apps/web-aiavatar/src/ip`、`src/canvas-bridge`、shell 及共享 API 类型。

- 企业概览、邀请与成员、角色授权、批量分配/回收、充值申请/记录、消费流水、模型/在途设置；停用/退出显示将回收的可用额和在途情况。
- 成员看到个人/企业两份余额；每次生成明确付款选择、预计费用和不足原因；刷新从服务端恢复真值，不自动换账户。
- 复用现有登录/开通提示；隐藏无权按钮但不依赖前端鉴权。不改 vendor 画布引擎，不向企业管理员显示成员私有作品。

**完成标准：** 桌面/手机版均能完成核心操作；刷新、重复点击、多标签页与旧权限状态不能误扣；实际接口无 mock 冒充成功。

### E10 · 平台财务前端

**依赖：E01 可先开发，接入依赖 E06。位置：** `apps/admin` 原财务充值、退款与查询页面。

- 企业收款登记、人工金额/积分、凭据、核准结果、退款及对账；明确区分企业、个人目标。
- 显示企业汇总、划拨流水、最终消费，保留原个人报表；页面权限沿用 FINANCE_ADMIN/SUPER_ADMIN。

**完成标准：** 财务页面完成一次真实接口的人工充值闭环；企业管理员无法通过此入口自行加积分，个人报表结果不变。

### E11 · 集成与迁移验收

**依赖：E01–E10。位置：** server 集成测试、web/admin 测试、独立验收记录。

- 用真实 MySQL 验证并发分配/回收/消费、批量原子性、邀请唯一归属、移交及资金守恒；H2 仅作补充。
- 浏览器验证充值 → 批量发积分 → 成员生成 → 失败退款 → 停用/退出；包含个人自费、未开通用户、跨企业越权和旧账号回归。
- 先用确定性生成/支付测试，无额外授权不发起付费厂商任务。执行仓库编译门和对应测试，记录范围与失败，不把 mock 结果写成线上验证。

**完成标准：** 产品方案 §5 的验收项全部有证据；无资金/权限阻断问题，迁移前后个人余额、历史账本和开通状态不变。

### E12 · 发布准备与受控上线

**依赖：E11。位置：** 迁移/部署配置、发布记录、运维对账入口。

- 新企业功能默认关闭；先兼容 schema/代码，后启用指定企业。开关只关闭新业务，不能关闭已有支付核准、任务结算和恢复。
- 对账覆盖充值、企业主/成员账户、冻结、消费和划拨；异常展示原任务/订单凭据，不直接修改余额。
- 记录可回退最低版本；存在企业资金后不得回退到只认识个人 userId 的版本。生产发布按届时授权执行，核验实际 SHA、配置与业务行为。

**完成标准：** 迁移与回退演练通过；上线时在途/余额可核对，生产验收与本地测试分开记录。

## 3. 执行约束

- E01–E04 已本地实现，验收见 [第一批记录](ip-studio-enterprise-foundation-validation.md)，页面规划见 [前端设计](ip-studio-enterprise-ui-plan.md)。第二批验收另记；后续完整生成、管理与财务页面、生命周期及发布准备已本地实施，见 [完整验收](ip-studio-enterprise-complete-validation.md)。未向实际企业充值或生产发布。
- 不做：月预算、席位开通、多来源产品权益迁移、多企业切换、企业资产接管。
- 需求改变先更新产品方案，再调整任务；工程状态只维护 TODO，避免多份进度互相矛盾。
- 每次实现同步对应类型、OpenAPI、BUSINESS_RULES、README 和版本记录；新增迁移不修改已执行文件。
- 提交前运行：`pnpm typecheck:all`、`pnpm typecheck:admin`、server `./mvnw compile -q -o`、`pnpm check:api-contract`，以及该任务要求的专项测试。
