# 全能创作对话驱动视频复刻方案

日期：2026-10-18。状态：统一产品与开发规格 v4；**S1 / S2 / S3 已于 2026-10-18 本地实现（未发布）**，实现记录见 `apps/server/README.md`「Studio 对话 agent、技能与计划执行」、`apps/web-aiavatar/PRODUCT.md`「2026-10-18 · 全能创作」、`specs/BUSINESS_RULES.md` 同名节；S0 付费实测与据其决定的 `autoFixChecks` 白名单未做（需单独批预算，见 `TODO.md`）。本文是本功能唯一方案真源；前序独立工作树方案已作废删除。

## 用户需求

在「AI全能创作」对话入口中，用户上传参考视频并说明要替换的商品、人物等，AI就能理解原片的主体创意、脚本和表现手法，结合新素材动态编写提示词、搭建并操作画布，完成生成、检查和局部调整，最终交付视频；将这套制作方法沉淀为可复用的Skill，具体方案每次由AI按素材动态决定。

建议沿用现有全能创作入口、同一画布和原生生成链，增加产品内置的视频复刻Skill、画布操作工具和可恢复的执行计划。用户通过对话表达目标，AI在授权范围内推进制作，画布始终呈现真实输入、依赖、参数与结果，用户可直接编辑和接管。

制作策略保持开放：AI分析原片后，结合用户目标、素材和当前能力动态提出推荐方案及必要的替代方案，说明效果与成本取舍；用户通过对话确认具体方案和预算后再执行。Skill中的方法是经验参考，不构成固定选项全集；服务端约束可调用操作、模型合同、素材归属、预算和授权，不按策略名称限制创作。

对话采用连续线程、真实流式正文与可见工具记录。制作中输入始终可用，新消息可调整当前执行；阶段确认留在消息时间线，预先授权范围内连续推进。事件协议和有界agent循环属于S1基础能力，预算审批卡和后台制作执行器在S2一起交付。

## 本次复刻提供的经验

案例为[工厂首播反转带货短剧画布](https://aiavatar.aibuzz.cn/projects/IPP-ab85e0f8)。原片约46.13秒；完成了虚构商品、新人物、三组参考图、四段H3和约49.03秒完整样片，保存为官方模板「工厂首播反转｜商品与人物可替换」v2，共13节点、20连线。此次制作没有修改应用代码。

本次提示词的主要内容来自对原片的理解和针对性改写：会话助手核对画面与烧录字幕，提炼出「紧张开播→商品质疑→年轻主播反转→实用建议」，再根据新商品和人物编写角色、参考图、对白、分段与H3指令。平台助手在收到整理后的文字后提供结构化方案，节点参数与执行继续通过画布完成。

第一次带视频引用的助手提案失败，随后使用已经核对的纯文本提案。此案例证明了理解原片后组织流程并出片的可行性；还没有证明产品内助手能够独立分析并自主执行全过程。编写出的生成指令属于根据原片效果反推的提示词，不能称为恢复了作者原始提示词。

| 环节 | 本次做法 | 可复用经验 |
|---|---|---|
| 分析原片 | 核对画面、烧录字幕和剧情顺序 | 记录可见事实、创意解释和不确定项，区分字幕读取与音频转写 |
| 确定范围 | 保留角色关系、因果链和反转，替换人物与商品 | 显式区分保留项、替换项及替换后的连带变化 |
| 改写脚本 | 调整对白、价格规格、道具和使用建议 | 围绕新素材重写相关内容，检查反转是否仍成立 |
| 准备参考 | 工人及工厂、商品、办公室女观众三组图 | 根据实际产物校正后续描述和引用用途 |
| 生成视频 | 四段H3，全能参考，每段设置12秒 | 分段服从叙事和模型合同；参考用途、对白和动作都需具体 |
| 合成检查 | 按顺序合成，保留新片段对白 | 原片排除出合成；检查可播放性、实际内容和音频策略 |
| 保存复用 | 参数表、说明、脚本、参考、片段与完整样例 | 成熟案例可作为配方和效果参考，供下一次制作选用 |

本次实际消耗2014积分，包含文本提案4积分、三张图90积分、四段H3共1920积分；合成无模型积分。该数值只记录本案例，后续计划按平台当前报价计算。本次未进行收费的内容重生成，不能由此推定重做次数或首轮可用率。

样片有个别模型字幕错字和人物串场。模型任务成功、媒体文件有效、创作效果合格应分别记录。

## Skill与模板的职责

产品内置Skill承载可复用的制作方法；具体创意可保存为配方；执行计划描述本次素材和预算下的实际制作。

| 对象 | 承载内容 | 本案例中的对应物 |
|---|---|---|
| 视频复刻Skill | 触发条件、分析方法、工具使用、生成策略、检查和修正方法 | 从参考视频理解目标并编排制作的方法 |
| 创意配方 | 某种创意的剧情结构、可替换参数、参考组织、样例与适用条件 | 工厂员工第一次直播、身份反转、实用建议收尾 |
| 画布模板 | 可预览、复制和直接编辑的节点、连线、参数与样例 | 当前已保存的13节点画布 |
| 本次执行计划 | 输入版本、步骤依赖、生成参数、费用上限、任务绑定与结果 | 用本次人物和商品生成四段视频并合成 |

同一Skill可分析新原片，也可结合用户明确选择的成熟配方执行。对于同一原片的再次制作，允许复用有效的分析结果，但要检查原片版本与新要求是否变化。配方不能代替对新原片和新素材的理解。

Skill固定的是分析和制作方法，每次动态确定剧情理解、角色关系、保留与替换范围、参考素材、脚本、提示词、分段数量及模型参数。「三张图、四段12秒」仅为本案例的安排。

例如换成洗发水，需要调整展示动作、观众疑问和结尾建议；换成三个年轻人，需要重新设计「厂里最年轻」对应的反差。单纯替换商品名或人物称谓无法完成这种改编。

首项Skill标识为`reference-video-recreation`，由受版本管理的说明文件、输入输出定义、案例和检查规则组成。安装本地Codex Skill不会直接改变线上助手能力，产品需要显式加载并执行这些规则。

## Skill协议与动态制作方案

### 文件和版本

技能文件固定为`apps/server/src/main/resources/studio/skills/reference-video-recreation.md`。第一、二阶段只使用仓内版本化文件，经代码评审与发布生效；通过`GET /api/v1/ip-studio/studio/skills`返回当前可用技能的标识、名称、版本、用途、规划方式、方法示例及能力要求。第三阶段再建设技能表、不可变版本和后台编辑，不在首期创建技能表或管理页面。

Markdown正文供模型理解方法；YAML头声明服务端执行边界及供模型参考的方法示例。字段解析失败或操作未获当前阶段允许时拒绝，不由模型文字扩权。方法示例不作为白名单，方案名称未在示例中出现不构成拒绝理由。技能规划任务保存服务端读取的技能版本、内容快照和摘要，已确认执行使用该快照；部署新文件不改写在途计划。停用技能阻止新受理，已有原生任务仍可查询和结算。

```yaml
---
key: reference-video-recreation
name: 参考视频复刻
version: 1
status: active
planning: dynamic
methodExamples:
  - remap-subject
  - creative-rewrite
  - preserve-audio-rebuild-visuals
  - keyframe-rebuild
operations:
  analysis: [recreation, text]
  production: [text, image, video, check, assemble]
limits:
  maxSourceSec: 60
  maxSegments: 8
  maxSegmentSec: model
  maxSteps: "maxSegments * 3 + 4"
  maxAutoFixPerSegment: 2
checks:
  - subject-replaced
  - old-subject-residue
  - character-consistency
  - product-facts
  - scene-and-action
  - dialogue-and-subtitles
  - duration-and-order
autoFixChecks: []
---
```

正文至少包含适用条件、方案推导与对话确认方法、分析依据、分段规则、参考组织、提示词编写、检查依据、修正优先级及实际案例。`methodExamples`仅帮助模型参考和解释，可以扩展、组合或提出未列名的方法，无需先新增策略枚举；具体步骤必须能编译到已开放操作与模型合法参数。能力和价格从平台当前合同读取，正文不能覆盖服务端合同。`autoFixChecks`必须是`checks`的子集；首版为空，所有内容检查仅提供建议。

### AI提出方案并由用户确认

AI先明确用户更看重什么：创意和剧情、原片动作与运镜、原声、人物商品还原、时长或成本。再根据原片分析、新素材和实际可调用能力提出具体制作方案，不先让用户选择技术路线或固定策略标签。

| 方法示例 | 适用条件 | 生成参考与脚本 |
|---|---|---|
| `remap-subject` | 主要替换商品或人物，要求保留原片动作、镜头运动、接触关系和场景；新主体能够适配原表演与构图 | 原片真实裁切片段连入支持视频参考的全能参考模式，结合新主体图，明确要替换与保留的内容；不承诺像素级一致 |
| `creative-rewrite` | 主要保留主体创意、剧情因果、人物关系或表现手法；换商品、人物或对白后需要重新设计动作、场景和笑点 | 理解原片后重写本次脚本，用新人物、商品和场景图生成；原片及其裁切视频、旧人物旧商品图不作为这段的生成参考 |
| `preserve-audio-rebuild-visuals` | 用户要求保留同一首歌或原对白，允许重新制作画面 | 按实际音轨安排画面和时长，生成后显式合入原声；口型和动作是否需要额外对齐单独说明，未接通的能力不列为可执行步骤 |
| `keyframe-rebuild` | 关键构图、商品外观或人物一致性需要先固定 | 先生成并采用关键画面，再用支持的首帧或首尾帧能力生成动作，最后按计划合成 |

这些是起步经验，同一作品可按段混合或提出其他可执行组合。例如产品展示段保留原动作，剧情对白段重写，再使用独立音轨策略。每段说明做法、选择理由、允许变化和不能混入的旧素材；生成模式按本段目标和实际模型合同决定，不由方法名称固定分派。

分析后先给出一份推荐方案；当存在有意义的效果、风险、成本或时间取舍时，再给少量替代方案，不为凑选项制造差别。每个方案说明保留什么、改变什么、已有素材如何使用、主要步骤、效果限制、当前报价或估算依据。用户确认的是这些实际取舍，无需理解模型模式或策略英文名称。

用户可以回复「按你推荐的做」「更看重动作还原」「保留原声，其他按你说的」「费用低一些」。AI据此调整方案，简短回述最终安排和服务端报价，绑定用户确认的方案修订与预算后执行。方案确认与制作阶段预算确认合并在同一次对话决定中，不额外增加一轮固定审批。若用户已经清楚授权具体方案及预算，不重复追问。

新的方法必须落到当前工具能执行的步骤。涉及尚未开放或未经验证的能力时，说明限制和可行替代，不能因用户认可方案而跳过合同、计费或能力检查。执行中若改变用户已确认的核心取舍，例如从保留原声改成重配对白，必须通过对话重新确认；参数微调在既有授权范围内继续。

工厂首播案例是`creative-rewrite`第一条示例：保留首播、质疑、身份反转和建议收束，用新人物与商品参考重新生成四段；原片只用于分析，不连入H3。它不作为`remap-subject`能力验证。

### 拉片时长约束

既有`operation=recreation, mode=segments`请求在`StudioRunRequest`及Java `RunRequest`增加可选的类型化`recreation: { maxSegmentSec: number | 'model'; videoModel: string }`，旧调用未传时保持原解析行为。技能执行必须提供约束，不复用当前剧本专用的`settings`字段；预检、请求指纹、worker和恢复快照同步支持。

`maxSegmentSec`支持正数秒数或`model`。`model`在服务端读取所选视频模型合同上限，H3当前为15秒；不将15秒设为所有模型的全局上限。显式秒数也不能超过该模型上限。受理时保存有效上限和模型合同快照，引用模型缺失或合同不可用时明确拒绝。

约束接入`StudioFilmStudy`现有的有限段数、连续时间范围、覆盖片尾校验处。超过上限时按叙事边界细分或在真实裁切后再切，重新验证覆盖、段数及实际媒体时长；采用哪种方式由S0长段实测决定，不能仅截断到上限而丢失后半段。若无法同时满足段数、时长和模型条件，返回`STUDIO_SEGMENT_TOO_LONG`，带冲突段落与上限。每段生成时仍执行所选模型的完整preflight，包括最短时长、整数时长和参考素材限制。

## 对话形态

### 连续线程与自动上下文

每张画布默认一条连续主线程，不要求用户在四种模式间切换，也不展示「新对话」与历史下拉。原创、改编、导演等意图由技能内部路由，用户直接表达目标。需要另试方向时，在某条消息上选择「从这里重新开始」形成分支；原消息、原产物与原任务保留，分支不继承执行授权或未结清的付款身份。同一画布跨分支仍受一份活跃执行的约束。

画布默认全部纳入逻辑上下文。服务端维护本人画布的节点目录、关系及摘要，根据当前目标检索相关正文和素材；不把整张画布所有原图每轮都发送给模型。`@`与附件入口保留，`@`表示钉住某对象及其版本，界面显示实际引用。用户无需点击「感知画布」，也无需手工维持16个引用名额。单次厂商或工具的数量、字节及Token限制继续存在，服务端以检索、摘要、分批调用适配，不能悄悄漏掉用户钉住的关键对象。

模型支持看图时默认按任务需要读取画面，读取过程进入工作记录；不支持时明确说明能力边界并选择可用工具，不声称看见原片。读取画面偏好可以修改和记住，不等于默认获得新增收费分析授权。

历史不设16轮的用户硬墙。原始消息分页持久保存，服务端压缩长对话并检索旧内容；已确认方案、预算、付款绑定及输入版本保持结构化原值，用户确认原文和来源消息可回查，不由摘要改写。单次模型请求仍遵守上下文预算，压缩和检索中的模型调用也按既有授权计费。旧四模式和历史记录可通过兼容读取进入线程，保留原任务及采用绑定，不自动重跑。

### 真实流式正文与工作记录

助手回复边生成边显示，正文用自然语言解释所见、安排与结果。模型供应商真实返回的文本增量才可作为`message.delta`；禁止完整回复后按字符切分或延时播放。工具记录仅呈现真实动作、观察和必要的简短说明，不展示内部推理、原始模型JSON、Key或私有请求信息。

工具调用以折叠的「工作记录」卡嵌入同一消息流，例如「正在拉片」「已切成5段」「正在读取第3段」「该段可见主体是水杯」。进度来自实际任务阶段或已取得的产物，不编造百分比或提前宣布完成。卡片以稳定工具调用id更新，显示开始时间、耗时及状态；已结束且完成结算后显示实际积分，运行中显示待结算，不虚构实时消费。消息脚注保留本轮实际积分，并能查看其中子任务明细，避免重复加总。

复用`ForgeController /chat/stream`的SSE传输结构经验；当前`ForgeChatService.streamViaLlm`仍是同步调用后切片发送，不能作为真实流式实现复用。`AiModelInvocationService`需增加供应商流式变体及真实用量处理，支持断流、终止和完成信号。端点不支持流式时明确展示等待状态，不能伪造delta；S1必须至少在一个真实支持的端点上完成流式验收。

### 一轮为有界agent循环

一轮对话由一个父级对话run管理「模型→类型化动作→校验与工具执行→结果回传模型→继续」循环，到自然语言答复完成、等待工具、需要用户决定或达到预算及循环边界时结束或检查点挂起。循环运行在服务端，不能只把原有整包JSON改成前端逐字显示。每次调用与提交前均复用租约、心跳、幂等和预算预检；限制模型调用次数、工具次数与总时长，避免无限循环。

模型输出采用自然语言正文与类型化结构块：制作方案、审批请求、工具调用、文字采用建议等各有正式schema。正文可以先流式呈现，未完整解析的结构块不能执行。端点显式声明`supportsTools`时使用原生function calling；未声明时使用JSON动作协议兼容，将正文与动作分开解析，两条路径归一为同一事件协议。JSON协议是内部兼容方式，不作为用户看到的整包回复。技能正文和结构块都不能自行授权工具。

沿用V53建立的聊天端点能力管理方式增加`supportsTools`及实际流式能力声明，前后端DTO、后台配置、模型调用与工具参数校验共用同一能力真值。字段迁移使用新的空闲编号，不修改已执行V53，也不按模型名称猜测能力。缺少原生工具能力可用受校验JSON动作协议，不允许静默换端点、付款人或价格。

父对话run累计本轮自身多次模型调用的真实Token，按既有费率与预算规则结算。解析、规划、图片、视频、独立`check`等工具动作继续创建各自原生子run，父run只绑定结果，不重复结算子run费用；同一次模型调用只能归父run或子run一处。流结束或循环终止后取得真实用量才结算，断流或用量未知沿用既有失败及恢复规则，不按已显示字符推算费用。`turn.done`可表示本轮已交代清楚但制作仍在后台运行，不能混同为整份作品完成。

### 制作中输入与转向

输入框始终可编辑，不因模型流式输出、调用工具或制作中而整体`locked`。上传、网络故障或消息尚未送达时显示该项状态，保留草稿；已关联成功的附件可继续发送，新素材必须完成上传和归属检查后才能供工具使用。发送采用独立`clientMessageId`，重复发送幂等，不为接收一条转向立即并发启动第二条收费推理。

新消息进入当前线程及执行的有序转向队列，立即回显已收到。执行器或S1的对话循环在下一个工具／步骤边界读取，明确回复已应用、待当前任务完成或需要补充条件。支持「第3段换成这张图」「预算提高到2000」「保留原声」等输入；已经提交的供应商任务保持原快照，受影响的后续步骤重新编译，不偷偷改写在途任务。

明确的停止指令和停止按钮走优先控制入口，不等待下一次模型推理：立即停止新增提交，并请求取消支持取消的排队任务；已交厂商的任务继续原链查询与结算。不能只用关键词子串把「不要停」误判为停止。普通转向在安全边界处理，不中断已受理媒体；纯「暂停后续」按原暂停语义保留已有排队任务，「停止／取消」额外调用现有取消能力，界面说清差别。

预算调整、自然语言批准和付款变更使用正式授权规则。已有具体方案时「按你说的做，上限1500」可直接确认，不能把随口讨论预算或模型生成的同意当作授权。原请求未确认受理时才展示「确认原对话任务」，正常对话不要求用户手动恢复任务身份。

### 时间线中的审批追问与收尾

阶段是后端的预算和执行边界，不做两页审批向导。需要新授权时在消息中显示动作卡，列明范围、当前报价依据、总上限、重做子上限和付款账户，按钮与可拖动／输入的上限共用一份服务端报价。用户既能点按钮，也能直接回复确认；批准后卡片留在时间线，显示确认版本、范围与状态，过期卡不能批准新版本。

示例卡可以是「分析预计不超过30积分，开始分析？」或「4段制作当前报价1000积分，可选重做额度最多480，总上限1480」。数字必须来自服务端真实报价，示例不是固定售价。预先授权已经覆盖范围、额度及付款绑定时，不再插入审批卡；超范围或超额才补充。滑动上限只是编辑草稿，点击开始或发送明确批准后才生效。审批卡与执行器在S2同批实现。

每轮最多追问1至2个真正影响结果的问题，嵌在正文中，可带候选答案；不再单列「还需要你的想法」区块或把`questions`数组直接渲染为问题芯片。常规选择按合理默认处理并用一句话交代，例如画幅跟随原片、时长遵循实际模型合同；缺少价格、功效等事实不能凭默认编造。问题较多时按重要性分轮处理。

完成或部分完成时用一条总结说明实际消费、采用结果、发生过的重做和未通过或无法判断的检查项，链接到成片和画布。随后基于本次产物动态生成2至3条可执行后续建议，如改画幅、保存模板或只改某段；建议不能只是固定文案，也不能点击后绕过报价和授权。

付款账户、模型选择和读取画面偏好保存在本人产品偏好及项目覆盖设置中，不每次询问。偏好只影响默认展示，不能代替本次付款授权；端点停用、企业资格变化或权限不足时重新校验，不静默换模型或扣款账户。用户自己写的文字节点仍要通过明确采用确认后才能覆盖，保留原文快照与冲突检查。

## 对话交互

继续使用「全能创作」与同一画布，附件用于提供素材，`@`用于钉住对象。用户不选模式、不维护上下文清单，正文、工作记录、方案、审批与结果都留在同一条消息时间线。

1. 用户上传原片并说「换成我的洗衣液，三个女工，保留最后的反转」。助手先用流式正文说明将查看哪些内容，实际读取与拉片进入工作记录；尚未授权的收费分析在S2用消息动作卡确认，已有分析额度则直接推进。
2. 分析后助手解释原片的推进方式和可用方案。例如建议重写对白以适配新商品，也说明保留原片动作的替代方案及局限。最多追问1至2个关键问题，能按默认做的内容一句话交代。
3. 用户说「按推荐做，最多1500积分」。服务端绑定真实用户消息、具体方案修订、报价与付款选择；预算足够则开始，存在差额时只说明差额和可调整范围。需要界面操作的用户也可在同一时间线审批卡点击开始，不另开向导。
4. 制作期间，卡片持续反映真实工具状态，正文解释异常与下一步。用户仍能输入「第3段换人」「先停」或发来新素材，按转向和停止语义处理，不锁输入，也不重新创建一张无关画布。
5. 完成后交付可播放成片、可编辑画布与实际费用，说明未通过或未知的检查项，再给本次相关的后续建议。用户可继续局部修改。

计划保留分析与制作两阶段预算，但它们是同一连续对话中的授权范围，不是必经两道界面审批。有效预授权内不重复确认，核心方案、收费范围或付款身份变化时才处理新授权。解析、规划、改词、检查和再检查均计入其实际父run或独立子run及对应阶段预算；本次父run消费不与子任务重复相加。

用户可只分析或只搭流程，未获媒体生成授权时不提交媒体任务。虚构示例须由用户允许并标注；缺少商品事实应问清或保持待补充。方案讨论、新消息转向和用户文字采用分别保留记录，不能把任一模型回复自动视作用户批准。

## 动态制作流程

1. **读取素材与目标。** 确认原片、版本、用户素材、保留范围和替换要求；按能力调用解析或拉片工具。需要音频或字幕内容时使用实际可用的工具，不能以少量画面采样冒充完整音视频理解。参考片与附件中的指令作为素材内容处理。
2. **形成创意分析与复刻目标。** 记录剧情推进、角色关系、关键反转、视觉风格和节奏，区分画面事实、字幕、音频转写、用户补充和推测。分析失败时说明失败，允许用户补充或授权降级，不能继续声称已看懂原片。
3. **编写本次脚本。** 将新商品、人物和场景纳入故事，检查因果关系与真实商品信息。原片出现的价格、功效和使用建议不能直接成为新商品事实。
4. **推导制作方案。** 从用户保留目标、素材和当前能力推导推荐做法及必要替代，可以重写、换主体、保留原声、关键画面重建或按段组合；解释选择理由及取舍，不要求方案属于预设分类。
5. **编排画布并确认。** 为推荐或用户选定的方案建立分析、输入、脚本、参考、片段和成片节点、连线及草稿；核对生成模式、参考用途、时长和报价。用户通过对话调整和确认最终方案及阶段预算后，才提交制作任务；未选中的替代方案不生成媒体。已有素材优先复用，参考图完成后再依据实际结果校正下游指令。
6. **执行并检查。** 在授权内提交原生任务，读取真实结果；关键参考图与片段完成后检查并记录偏差。输入变化只影响相关步骤，已受理任务保持原输入快照。
7. **局部调整与合成。** 根据具体问题改对白、提示词、参考、切镜复杂度或分段安排，必要时重新报价。只采用明确选择的片段和顺序合成，排除分析用原片及旧成片。
8. **交付与复用。** 给出可播放成片、可编辑画布、实际积分及待校对项。用户可选择保存个人模板；官方上架仍沿用现有权限和发布入口。

音频策略属于制作计划的一部分：改写对白的带货短剧使用新生成对白；保留原声的歌唱或表演视频需要明确音轨复用方式及音画限制。提取完整音轨不等于完成转写、人声与BGM分离或变声。只有平台已具备并实际调用相应能力时，才可列为可执行步骤。

## 复刻效果与动态修正

每次制作先生成一份与用户目标对应的检查清单。需要保留的创意应有具体检查项，允许变化的部分不按逐帧相似度判错。

| 本案例复刻目标 | 检查内容 |
|---|---|
| 笨拙首播的真实感 | 开场保留紧张、犹豫和工友配合 |
| 商品质疑与回应 | 观众疑问在新商品语境下成立，并得到回应 |
| 年轻主播反转 | 铺垫与反转完整，人物年龄和组织背景支持笑点 |
| 新人物与新商品 | 检查旧人旧包装回流、变脸、角色串场和价格规格冲突 |
| 实用建议收束 | 建议与商品资料一致，避免编造功效 |

检查分为三个层面：

- **媒体有效性。** 程序检查真实文件、解码、时长、画幅和音轨等，可形成明确结果。
- **内容一致性。** 使用实际可用的图像、视频、字幕或转写能力核对人物、商品、关键动作和台词。首版视频检查复用四帧采样，只覆盖这些采样时刻，无法验证完整对白、短暂人物串场、连续动作和口型；这些项目缺少可靠依据时返回`unknown`，不能判通过。视觉模型读到画面文字不等于已接通完整OCR或ASR。
- **创作效果。** AI评估节奏、反转和表演，用户给出采用或修改反馈。模型自评与用户采用分别统计。

动态调整至少发生在脚本完成、参考图完成和视频完成三个位置。检查判定为`pass | fail | unknown`三态，必须带检查项、目标版本、真实帧时间或其他依据及建议；缺少依据不推断为通过。总体有明确失败项则为`fail`，全部适用项通过才为`pass`，其余为`unknown`。

首版`autoFixChecks: []`，检查仅提供建议，失败不会自行启动收费改词或视频重做。用户可接受当前版本或明确确认局部修改。后续某检查项经S0对应测试证明可靠，经技能版本评审后才加入`autoFixChecks`；仅白名单内明确`fail`的项目能触发自动修正，并同时受阶段总预算、`autoFixCap`和`maxAutoFixPerSegment`限制。`unknown`、白名单外失败及未授权操作始终交用户决定。一次自动修正链中的改词、生成和再检查分别作为步骤记账，不能只计算视频费用。

Skill提高的是制作完整性、问题定位和调整效率，不能保证一次成片。评价有效性需要不同原片与不同替换输入的实测，而不是用一个案例或单一模型评分推出通用成功率。

## 当前基础与实现缺口

以下区分基于当前工作区代码及已有验收记录。已有能力可作为接入基础，具体线上状态以发布记录和上线验收为准。

| 模块 | 现有基础 | 本方案需要补充 |
|---|---|---|
| 全能创作 | 节点引用、步骤建议、前置依赖、节点采用和正文或提示词写回 | Skill选择、动态计划、工具调用和连续执行入口 |
| 解析与拉片 | 专门的全片分析、分段、真实裁切和原声提取链路 | 助手按任务调用，并将分析来源和能力边界带入计划 |
| 图片和视频 | 普通节点、原生生成、全能参考、模型合同、报价和任务恢复 | 将完整规格与精确素材版本绑定到计划，并支持动态调整 |
| 连续制作 | 镜头首帧、视频、合成，保存计划、暂停及继续 | 支持分析、文字、多参考素材和检查修正组成的通用依赖流程 |
| 画布模板 | 预览、复制、版本、说明和样例 | 与Skill及本次输入关联，支持对话替换与影响范围预览 |

现有助手步骤类型主要表达文字、剧本、分镜、图片和视频建议；单独增加一份Skill提示词无法直接表达并执行全部解析、合成和修正操作。现有连续制作仍围绕首帧到视频的流程，需扩展后才能承接本案例。

本次发现的两项产品问题应作为接入前的修复验收项：模板复制后生成模式回到首尾帧，需要手动切全能参考；直接保存合成产物时触发资产归属错误，需要重新上传为干净节点。先针对最新代码复现，若已有修复则验证实际复制、播放和保存。手动切换和重新上传只保留在案例复盘，不纳入标准用户流程。

## 接入结构与执行边界

采用「对话理解→Skill加载→分析阶段→制作计划→原生任务→检查反馈」的结构。AI决定创作内容和参数，应用负责校验、预算与执行。首批工具覆盖读取画布和模型能力、解析、创建或修改节点、连接与排布、报价、生成、查询、检查、合成和保存个人模板。

产品内部调用受控业务能力，浏览器点击只用于人工制作和验收。Skill不携带供应商Key、任意可执行脚本或第三方插件代码。不新建画布库、生成链或账本，不跨入drama、celebrity的页面和表。

### 两阶段计划契约

扩展`packages/types/src/ip-studio-workflow.ts`及对应Java DTO，保留旧建议流程兼容。两阶段计划是agent循环中可多次更新的类型化结构块，正文和过程不等待整个计划生成后才展示。以下为待实现契约：

```ts
type StudioPlanStage = 'analysis' | 'production';
interface StudioProductionApproach {
  id: string;
  title: string;
  summary: string;
  rationale: string;
  preserve: string[];
  change: string[];
  tradeoffs: string[];
  requiredCapabilities: string[];
}
type StudioPlanOperation =
  'text' | 'script' | 'storyboard' | 'image' | 'video' |
  'recreation' | 'check' | 'assemble';

interface StudioPlan {
  // 原有 summary / steps / questions / notes 用于兼容旧记录
  skillKey?: string;
  skillVersion?: number;
  stage?: StudioPlanStage;
  approaches?: StudioProductionApproach[];
  recommendedApproachId?: string;
  confirmedApproachId?: string; // 服务端根据用户对话确认绑定，模型不填
  budget?: {
    estimated: number;   // 服务端计算的本阶段基础步骤报价合计
    autoFixCap: number;  // 本阶段总上限之内的自动修正子上限
    approvedCap?: number; // 用户确认后由服务端绑定
  };
}
interface StudioPlanStep {
  // 原有 id / title / prompt / content / references / dependsOn 等保留
  operation: StudioPlanOperation;
  strategy?: { approachId: string; method: string; reason: string };
  execution?: 'auto' | 'confirm';
  quotedCost?: number;
  settings?: StudioSkillStepSettings;
}
```

`settings`采用按operation区分的类型化结构，不接受未校验的任意JSON。`recreation`包含原片引用、`mode=segments`、`maxSegmentSec`和视频模型；`video`包含完整`StudioVideoSettings`、时长、比例、数量及有序参考绑定；`check`包含更早的视频步骤、精确目标run或候选和检查项；`assemble`包含显式片段顺序、采用版本和音频策略；`text`包含输出用途及可编辑目标快照。

`approaches`描述本次动态提出的推荐与替代方案，按保留项、改变项、取舍和能力需求解释，不设固定策略枚举。`steps`只编译当前推荐或用户选择的一个候选方案，选别的方案时生成新的计划修订和报价，不能执行所有替代方案。`strategy`在视频步骤中记录所属方案、具体方法与理由，相关改词和检查继承同一方案绑定；`method`是说明与统计信息，不能作为调用未开放工具的入口。不同片段可以使用不同方法。

新对话不以`summary + steps + questions`整包JSON作为回复载体。消息包含自然语言正文和按需出现的`plan | approval | tool_call | question | adoption`类型化块，分别绑定计划修订、授权请求、工具参数、正文追问和文字采用。`questions`只兼容旧快照；新追问显示为正文问题及候选答案，不重新生成独立问题区。一个父对话run可多次调模型和工具，阶段计划跨多个turn持续存在，turn不等于阶段，也不等于一次供应商请求。

`StudioPlanValidator`按技能当前阶段白名单校验，分析阶段仅`recreation | text`，制作阶段仅`text | image | video | check | assemble`。保留的`script | storyboard`只供旧建议流程使用，不能绕过本技能白名单。校验方案实际步骤、模型参数组合、能力要求、素材用途和授权，不校验方法名称是否出现在示例中；新名称或混合方案只要能编译到合法能力即可。计划必须是合法依赖图；`check`指向更早的视频步骤，素材引用只能来自本次用户输入或更早步骤的真实产物。

技能计划的基础步骤上限由`limits.maxSegments × 3 + 4`推出，当前8段对应28步，不沿用全局12步；超过时缩小范围或重新编排，不能静默丢步骤。修正以原步骤的有界尝试及关联改词、检查子步骤记录，仍受修正次数和预算限制，不借重做无限扩展基础计划。

模型不能填写`quotedCost`、`approvedCap`、`confirmedApproachId`、`resultNodeId`、执行状态和任务身份。服务端解析后按真实端点合同和定价填写报价，保存规范化计划与指纹。具体方案、保留与改变范围、合法参数或输入变化均产生新计划修订；已经受理的请求不改写。

技能规划使用原生`text`操作，规划请求增加可选`skillKey / skillVersion / stage`及所属执行绑定，由服务端核对有效技能和阶段授权并选择`skill_plan`；普通文本与助手路径不受影响。这些字段用于选择方法和校验范围，不能代替付款或执行授权。

分析阶段授权后可连续完成解析、拉片、制作方案推导和计划编译。实际段落、素材key和模型限制进入计划；用户通过时间线动作卡或自然语言确认具体方案的保留项、变化项、效果成本取舍和阶段预算后，服务端写入`confirmedApproachId`及确认修订。授权块包含`approvalId, stage, planFingerprint, scope, quotedCost, budgetCap, autoFixCap, billingSelection`和确认消息引用，实际授权快照由服务端生成。重复点击或同义确认幂等，旧卡批准不能作用于新修订；预授权覆盖时不再发`approval.required`。

分析结果、新增步骤或模型推荐都不能代替用户授权。制作期范围内的有界动态修正无需逐条确认；核心方案变化、超出授权范围或阶段操作白名单则暂停。制作期新消息进入转向队列：先保存消息、目标输入版本与预期计划修订，到安全边界检查并应用，不能复用旧批准偷偷扩大范围。

### 对话事件协议

在共享类型、Java DTO与`specs/openapi.yaml`定义同一SSE协议，S1实现。前端负责消息、卡片及已授权画布命令的渲染和投影，不重新推导执行步骤、费用或任务状态。事件由服务端从真实模型增量、工具动作及原生run生成，两种工具协议产出一致事件。

```ts
interface StudioDialogueEvent<T> {
  eventId: string;
  seq: number;       // 同一线程单调递增，重放时不变
  threadId: string;
  turnId: string;
  runId?: string;    // 父对话run；工具内另带对应子runId
  executionId?: string;
  createdAt: string;
  type: StudioDialogueEventType;
  data: T;          // 按事件type区分的类型化数据，不是任意JSON
}
type StudioDialogueEventType =
  'message.delta' | 'tool.started' | 'tool.progress' | 'tool.finished' |
  'plan.proposed' | 'approval.required' | 'node.upsert' |
  'check.result' | 'budget.update' | 'turn.done';
```

| 事件 | 数据及前端行为 |
|---|---|
| `message.delta` | `messageId, partId, delta`；只追加真实流式正文，按序去重 |
| `tool.started` | `toolCallId, toolName, safeInputSummary, childRunId?`；建立工作记录卡，不提前声称工具成功 |
| `tool.progress` | 同一`toolCallId`的真实阶段、已完成数量或可核实观察；更新原卡 |
| `tool.finished` | 状态、真实产物指针、耗时、`creditsActual`或待结算标记；错误也正常展示，不假成功 |
| `plan.proposed` | 规范化计划、修订、指纹及服务端报价；可随对话更新，未确认不启动制作 |
| `approval.required` | 不足的具体授权、范围、报价、可编辑上限和过期条件；S2显示时间线动作卡 |
| `node.upsert` | 稳定节点绑定、内容提案或合法应用命令、预期字段或文档版本；用户文字覆盖需采用，不把事件当授权 |
| `check.result` | 原生check run指针及`pass | fail | unknown`，按真实输出展示 |
| `budget.update` | 阶段上限、已消费、在途、剩余额度及差额，注明实际或报价来源，不重复合计父子run |
| `turn.done` | `reason=completed | waiting_user | handed_off | interrupted | failed`，最终消息／块快照和本轮实际消费或待结算标记；不表示后台作品必然完成 |

会话消息、用户确认、事件游标与分支关系在服务端持久保存，原始消息不只留在客户端；事件记录是展示和恢复投影，不成为新的任务、编排或账本真值。父run保存循环检查点和工具调用身份，子run保存执行产物。只发布已持久接受的动作与状态，不能先发成功事件再尝试保存；正文分片可批量持久化，但重连必须能用已保存正文快照和序号对齐，不重复字符。

订阅使用现有认证的同源流式请求，不将token或私有媒体签名放入URL。事件携稳定id，支持`Last-Event-ID`或`afterSeq`继续；SSE断线不等于取消。缺失事件可补放，游标过期时返回线程、消息和run快照及最新游标，前端重建同一结果，不重发工具。SSE不可用时回落到原run与执行投影轮询，轮询本身不触发推理、生成或扣费；恢复流后按seq衔接。连接心跳不展示为工作进展，也不计模型消费。

### 线程转向与兼容契约

每条用户消息绑定`threadId, clientMessageId, pinnedNodeIds, attachmentBindings, expectedPlanRevision?`，服务端返回`messageId, turnId, runId?, queueState`。`queueState`说明已收到、已排队转向或已应用；不因正在执行而拒绝输入。S1将待处理消息与安全边界检查点保存在当前对话run／线程记录，S2的制作转向引用同一用户消息并落在`ip_plan_execution`的编排队列，避免两套消费者同时提交同一动作。

新消息入口受理父级原生`assistant` run时带经归属校验的`dialogue: { threadId, messageId }`绑定，由服务端加载上下文和选择`skill_dialogue`循环；旧`assistant`请求仍按原契约读取和恢复。新入口不让客户端每次拼装完整history或16项context列表，相关摘要、检索、视觉快照及原始引用由服务端保存和追溯。

停止控制与普通转向分流，优先停提交流程；预算批准、步骤修改和方案选择在租约内按消息顺序应用，成功后记录已处理消息及修订。已明确改变未来输入时，原计划快照过期，不能一边排队转向一边继续提交受影响旧步骤。已受理任务仍保留原请求，不以新消息重新提交它。S1覆盖当前对话工具边界和现有原生任务的转向，S2扩展到后台多步执行。

旧模式和对话快照按原顺序导入或兼容投影到主线程的历史区，保存来源映射，不删除旧消息、费用与采用绑定；不把旧JSON问题区继续当主交互。分支由用户从特定消息显式创建，独立保存后续消息和草稿，原父线程只读保留。默认打开主线程或用户上次所在分支，不要求操作历史下拉。

### 提示词接入

新增`dap.ip_studio_skill_dialogue`、`dap.ip_studio_skill_plan`与`dap.ip_studio_skill_check`，通过现有Prompt管理提供版本和后台查看编辑，`dap.ip_studio_assistant`保持旧路径兼容行为。

- `skill_dialogue`驱动父对话run的自然语言、意图路由、有界工具循环和类型化结构块，不要求只返回整包JSON。工具声明与可调用范围由服务端提供，原生function calling与JSON动作协议共用动作schema。
- `skill_plan`接收服务端技能快照、当前阶段、用户需求、分析依据、素材清单、能力合同和允许预算，动态提出推荐方案及有意义的替代方案，返回含取舍、能力需求和当前候选步骤的计划JSON。方法示例只作经验参考，不要求从中选一个。用户反馈进入后续计划修订；分析期编译制作计划与制作期改词均有各自原生`text` run。
- `skill_check`接收检查项、目标版本、真实画面及时间，输出三态判定、逐项依据和建议，不产生执行授权。
- 未配置模型、视觉能力、提示词或售价时沿用现有明确错误，不回退成无依据的文本判定或假成功。

### 三处真值与新执行表

| 位置 | 唯一职责 |
|---|---|
| `ip_plan_execution` | 编排阶段、计划版本、步骤与依赖、每步runId列表及尝试次数、预算与占用、付款绑定、租约、用户决定和执行状态 |
| IpRun及原生媒体任务、原有账本 | 真实请求快照、供应商执行、产物key、检查输出、价格、冻结、结算和退回 |
| 画布文档 | 用户内容、节点、连线、可编辑草稿，以及节点上的`executionId / stepId / runId`绑定；不复制整份执行状态或费用 |

新表建议字段：`id, project_id, owner_user_id, skill_key, skill_version, stage, plan_run_id, plan_revision, plan_fingerprint, status, steps_json, budget_json, spent, in_flight, billing_json, lease_owner, lease_until, lease_version, client_request_id, started_at, deadline_at, created_at, updated_at, finished_at`。状态为`running | paused | needs_user | done | partial | failed | canceled`；唯一约束`(owner_user_id, client_request_id)`，同项目只允许一份活跃执行，以项目行锁及执行状态检查保证。

`steps_json`保存编排步骤、依赖、原任务列表、稳定请求身份、尝试次数和采用指针；计划正文、提示词来源及输入快照由`plan_run_id`指向的原生规划run保存。`spent / in_flight`是供预算校验的持久汇总，从原生任务及其已受理费用上限核对更新，不成为第二套费用结算真值。检查正文保存在原生`output.check`，画布只按绑定读取展示。

线程、消息、分支、事件游标及偏好只保存对话内容和必要指针；转向队列是编排输入，不能复制原生任务状态或费用。父对话run的多轮模型调用在自身`_exec`检查点累计真实用量；子任务费用仍只归子run，预算汇总根据实际收费引用去重。关闭聊天面板不清空消息和转向，不依赖前端事件订阅才能推进。

当前模板执行器把指针保存在独立`templateInstanceJson`，不能将其误作画布文档字段。本执行器可复用其依赖校验、同键恢复、采用和CAS经验，但新执行状态统一落`ip_plan_execution`。

关页后从原生任务快照、成功候选和本人存储key读取中间产物，不依赖前端创建节点。分析、文本或检查服务若原来仅能读取画布节点，需要增加受执行归属约束的内部快照入口，校验owner、project、execution和前置run，不能仅增加操作枚举。前端重新打开后按稳定绑定幂等投影节点和连线，通过原文档保存链保存；不让worker改写用户正文或另存一份可编辑画布。

应用画布变更前核对文档版本或目标字段快照，冲突保留待采用变更。用户在执行中修改提示词或参考，受影响步骤标为`needs_user`，已受理任务继续原快照，旧产物保留。执行关闭或用户删除节点后，重复投影不得无限重建或覆盖其编辑。

### 提交前预算与付款绑定

分析和制作分别确认阶段预算并保留各阶段消费。每次提交新步骤之前，在执行锁内核对：

```text
本阶段已消费
  + 本阶段在途占用（每个已受理未结算run的已批准maxCost）
  + 本步服务端报价
  ≤ 本阶段已批准上限
```

若用户另设整个作品的总预算，还需同时满足全阶段累计上限。`autoFixCap`是制作阶段总上限内的子额度，不能额外叠加到总预算。改词、检查、再检查与媒体生成分别作为收费步骤；文本按Token上限报价、实际用量结算；视频多候选按整批报价。各run的`maxCost`使用本步被批准的费用上限，不使用整阶段上限；若原生批次拆出多个任务，预算按其同一收费引用计算一次。

不满足时不提交、不冻结，该步进入`needs_user`、整体暂停自动推进，返回`STUDIO_PLAN_BUDGET_EXCEEDED`，包含`stage, spent, inFlight, quotedCost, approvedCap, shortfall`；`shortfall = spent + inFlight + quotedCost - approvedCap`。用户补充授权或缩小计划后再继续。

报价检查、准备请求身份和原生受理按同一串行推进与事务边界衔接；结果未知时保留原请求及保守预算占用，先回查，不能按未受理释放额度后继续提交。每次唤醒先刷新原任务结算和在途占用，避免重复计入同一run或漏掉尚未结算的run。

确认阶段计划时将付款模式、企业id与授权快照写入不可变`billing_json`。每步原样携带确认时的`billing`选择，与原生任务同一付款人校验一致；授权快照由服务端取得，不信任模型或客户端伪造。制作阶段确认、暂停恢复、原请求重放都不能换付款人；授权撤销或失效时停止新增提交，不静默改扣个人账户。若用户要换付款人，结束原执行并新建授权执行，允许引用已完成产物，旧run仍按原付款绑定结算。

执行器自己不冻结一分钱。冻结、实际扣费和释放仍由被调用的原生任务与CreditService完成；编排层只管理用户批准的预算占用。模型合同或当前报价变化先重新preflight，未经新确认不扩大原授权。

父对话run也计入所属阶段的已消费或在途，工具子run独立占用；其循环不能绕过同一公式。父run只为自身模型调用保留批准上限，不能把整个制作预算当作自己的Token冻结；自身余额不足则结束或请求新授权，不静默提高maxCost。消息脚注可展示本轮总消费与分项，但预算汇总只按真实收费引用计一次。

### 检查作为正式原生操作

将`check`正式加入`StudioWorkflowService.OPERATIONS`、能力返回、共享类型、Java DTO、worker分派和任务展示。它属于文本类run，使用支持看图的端点，按Token定价和实际用量结算，不借`assistant`对话操作执行。

原生请求增加类型化`check: { targetRunId: string; targetStorageKey?: string; checkIds: string[] }`及执行绑定；候选key只能选择目标run实际成功输出，检查项必须属于本技能清单。扩展`validateCreativeRequest`的专用检查分支，由服务端构造视觉快照，不要求客户端假装发送`assistant + readVisuals`。

服务端从目标步骤已成功且明确选定的run或候选获取成片key，核对本人归属与版本，抽帧生成`visualContext`，与检查清单共同保存输入快照。`visualContext`由服务端生成；关闭画布也能基于目标原生run工作。结果写`output.check`：

```json
{
  "status": "unknown",
  "targetRunId": "目标原生run",
  "items": [{
    "id": "dialogue-and-subtitles",
    "status": "unknown",
    "evidence": [{"kind": "frame", "timeSec": 3.1, "observation": "该采样画面可见人物"}],
    "reason": "四帧画面不能核对完整对白和口型",
    "suggestion": "试听核对，或在接通转写后检查"
  }]
}
```

证据的帧时刻、目标key和采样数量由实际媒体产生，模型不能编造来源。前端标注「AI判断」，逐项展示`unknown`。首版检查建议不驱动自动重做；建议失败或未知时可由用户`accept`当前版本、确认修改或暂停，不能显示成所有内容已通过。

### 服务端推进与恢复

服务端执行器按依赖推进，调用现有`StudioWorkflowService.submit`及原生任务；保留owner、enrollment、phone、企业授权、preflight、账本和afterCommit规则。每次新尝试先持久保存稳定的`clientRequestId`及请求指纹，形式可由`executionId + stage + stepId + attempt`派生为满足现有长度限制的标识。网络错误和刷新沿用原身份；只有确认新尝试才递增attempt。

所有启动扫描、定时唤醒和用户继续共用同一推进入口。推进前以条件更新抢占租约：只在租约过期或同持有者续租时更新`lease_owner / lease_until`并获得版本；后续写回携租约版本做CAS，失去租约的旧worker不能继续提交或覆盖状态。受理和状态落地后通过`afterCommit`唤醒，重复唤醒不会产生第二份任务。

| 状态或动作 | 新任务提交 | 已受理任务处理 |
|---|---|---|
| `running` | 在依赖、授权、预算及租约均有效时推进 | 按原run查询、结算并推进 |
| `paused` | 不提交任何新步骤，包括改词、检查和下一段 | 仅刷新已有run状态和结算；启动扫描不自动恢复执行 |
| `needs_user` | 暂停，等待预算、输入、采用或范围决定 | 继续查询既有run，不自动增加尝试 |
| `cancel`或明确停止 | 走优先控制入口立即停止新增提交，不等普通转向边界 | 请求取消支持取消的排队任务；已交厂商的按原链查询结算 |
| `partial` | 不再新增提交 | 保留成功部分，继续查询与结算未完成的原任务 |

`resume`只恢复用户明确确认的阶段及范围，仍核对计划指纹、付款绑定、输入、价格和租约。若预算或来源变化，返回对应错误并停在`needs_user`，不能以继续操作绕过重新授权。

整份执行从开始起设置90分钟`deadline_at`。到点标为`partial`并列明已完成、在途及尚未执行的步骤，不能将超时等同供应商失败或释放仍由原任务拥有的冻结。定时恢复在`partial`、`paused`和取消状态下仍跟踪已有run至终态，原生任务结算不因编排超时停止。

创建请求包含`stage, planRunId, planFingerprint, budgetCap, autoFixCap, billing, clientRequestId`；确认制作阶段时另外带已有`executionId`、`approachId`、预期修订及对应用户对话确认引用，避免建立第二份活跃执行。服务端将实际用户确认与计划指纹绑定，不能把模型生成的「用户已同意」当作确认。使用新确认身份记录阶段授权，同键不同正文拒绝。暂停、继续、取消、采用也需幂等身份与预期状态或版本；`accept`只接受当前步骤所属成功产物。

S2的审批按钮和自然语言批准都进入同一授权命令，绑定`approvalId`、用户确认消息、报价与计划指纹；已经覆盖的授权不再触发审批事件。自然语言对账目含糊、指向多个方案或实质改变付款人的情况先明确，而非猜测批准。对话消息、SSE和控制接口均执行owner／项目／线程校验，不通过订阅连接本身授权写操作。

调整预算或确认局部修改通过同一个POST提交现有`executionId`和新计划修订，再由`resume`推进，不新增隐含的收费接口。模型生成的计划不等于用户确认。原生`studio-runs`契约增加`check`与拉片约束，仍是每步执行的唯一生成入口。

## S0实测矩阵

S0使用现有能力验证方法和质量，不以付费生成代替功能测试。开始前单独确定测试素材、总预算、重做次数和人工判定标准；本次文档修订不授权执行付费测试。

S0按用户目标、素材条件及实际能力组合选择案例，不以固定策略分类限定测试范围。原有换主体与创意重写各5条作为起步样本，覆盖有人及无人、对白及纯展示、不同商品和人物；再按预算补充保留原声、关键画面重建或混合方案，检验AI能否提出不同做法并解释取舍。新增方法只要落到已验证的合法能力即可纳入，不要求先注册策略名称。

对有足够样本的方法，可建议至少4/5条在两次生成内达到事先约定的人工可用标准，门槛在测试开始前固定；小样本只决定适用范围，不作为普遍成功率承诺。某种做法不过线只限制对应能力组合或素材类型，其他可行方法和组合继续保留。S0执行前统一列出实际用例、基础生成和可能重做调用数，不因新增方案自动扩大测试预算。

Seedance 2.0按现有方案信息已配置端点且协议支持参考素材，但尚无本轮付费验证。`remap-subject`的5条用例用H3和Seedance 2.0配对验证，两家各占该策略测试调用的一半：5条用例对应10次基础生成，预算不能只按5次计算。模型合同、端点可见性和实际售价在S0开始前重新核对；未知能力不得当作已经验通。

| 项目 | 测法 | 记录和决策 |
|---|---|---|
| `remap-subject` | 相同原片片段和新主体图分别给两家视频模型，检查主体替换及动作、运镜保留 | 按模型和素材类型记录首轮结果、两次内可用性、残留及失败原因；只收窄未达标路径 |
| `creative-rewrite` | 5条原片动态分析、重新编写脚本，使用新参考图，原片不连入生成 | 检查创意因果、人物关系、对白改编及旧主体回流；工厂首播是首个已有案例，单独注明已有实测与新增测试 |
| 动态方案与混合制作 | 选择需要保留原声、先定关键画面或不同片段采用不同方法的素材，检查AI提出的方案与必要替代 | 方案可以超出起步示例，但步骤必须可执行；用户选择或修改取舍后重新编译，只运行确认版本 |
| 长段比例 | 统计实际拉片段中超过15秒的数量及比例，同时按所选模型上限统计 | 决定`maxSegmentSec`在原分段约束中完成还是增加真实再切；无论采取哪种方式都验证连续覆盖及实际时长 |
| 音频默认 | 对适合的素材比较不传音频、合规片段原声作参考、成片后原片音轨覆盖三种方式 | 按策略和场景选择默认；改写对白不能默认覆盖旧音轨，记录模型时长限制及口型边界 |
| 检查可靠性 | 为每个检查项准备成功、失败和难判断样例，AI与人工逐项比对 | 记录误报、漏报、unknown比例和真实证据；只有可靠性通过预设门槛的项目才能进入后续版本`autoFixChecks` |
| 完整费用 | 汇总分析、规划、图像、视频、检查、改词和再检查的实际费用 | 对比报价与占用，记录每次尝试，不把旧案例支出当作本次固定价 |
| 模板模式回退 | 保存带完整全能参考规格的模板，复制、刷新、打开生成参数并提交预检 | 模式、有序参考、用途和规格一致，不需要用户手动切回；若已有修复，以最新实测验收 |
| 成片归属保存 | 合成结果直接保存为模板，预览、套用、播放及查询归属 | 无需下载再上传，素材权限正确；禁止为通过保存放宽归属校验 |

后两项产品问题是接入前修复验收项。S0结论回填本节，保留真实输入条件、产物、版本、人工判断与实际费用，不预填通过结果。

## 实施顺序

### 第一阶段 S1 对话规划与画布

完成真实流式调用、父对话run的有界agent循环、自然语言与类型化块、SSE事件及断线恢复。原生function calling和JSON动作协议共用工具schema和事件，能力配置沿用端点真值并新增字段；不能将整包JSON回包拆字冒充流式。事件协议和循环是S1交付前提，不后置到S2。

同时完成一画布一主线程、自动上下文与摘要检索、`@`钉住、默认按能力读画面、旧四模式与历史兼容、输入不中断及转向队列。接入仓内技能文件和`GET /studio/skills`、两阶段计划数据、动态方案、提示词key、报价及拉片`maxSegmentSec`，能够生成普通节点与完整草稿；用户自写文字仍需明确采用。

S1的循环只运行当前已授权的工具。新增收费动作尚未授权时沿用可用的费用确认路径，不为演示循环绕过授权；时间线中的两阶段审批动作卡及后台自动制作在S2同批接入。当前turn工具边界和已有原生任务上的转向在S1验证，后台多步编排的转向在S2扩展。此期不建设技能表或编辑后台，不把流式对话或计划卡当作整条后台制作已实现。

S1必须通过三条形态验收：

1. 一轮对话在供应商真实回复完成前显示流式自然语言正文，并至少出现一张对应真实工具调用的工作记录卡；有耗时、实际积分或待结算状态，卡片与工具结果一致。
2. 制作或工具运行期间输入框与附件入口可用，新消息幂等接收并在下一工具边界作为转向处理；明确停止走优先控制。消息不会被`locked`丢弃，也不并发重提已受理媒体任务。
3. 取消四模式、历史下拉及新对话入口后，旧对话仍能打开，消息、任务和采用绑定保留；长历史自动压缩可回看原文，16轮或16节点不再是用户硬墙。

另核对SSE断线切轮询、事件去重与快照重建，原生工具和JSON动作两路的相同事件输出；准确模式和素材引用、计划指纹、用户手改保护与预算仍按原要求验证。375px窄屏上输入区、工作记录和内嵌问题可用。开发前完成对应能力组合的S0方法验证，并处理两项产品问题。

### 第二阶段 S2 服务端连续制作

新增`ip_plan_execution`、租约与统一推进入口，同批交付时间线中的分析／制作审批动作卡、自然语言批准、上限编辑及预授权免重复审批。接通付款绑定、原生`check`、暂停恢复、停止优先控制、后台转向、关页继续和局部采用。检查默认只建议；用户明确确认的重做走同一计划和预算，后续经验证的检查项才允许开启有限自动修正。所有步骤依赖真实产物，前端幂等投影，不复制执行状态。

S2验收审批卡留档、过期及重复确认幂等，卡片与自然语言批准产生相同授权；新消息变更输入或提高预算在安全边界生效。任务推进不锁输入，父turn结束、SSE关闭或面板关闭都不丢失后台执行，收尾提供实际成本、未完成项及动态后续建议。

### 第三阶段 S3 版本管理与经验积累

再建设技能表、不可变版本、后台查看编辑及试跑，扩展其他技能和意图选择。经检查项实测及版本评审后更新`autoFixChecks`。从成功画布整理方法草稿，由人审查后发布，不把单次输出或私人素材自动变成全平台规则。

先覆盖短视频创意与脚本复刻，音频增强按实际已接通能力扩展。不同时建设第三方插件市场、Skill交易或全模态无限编排。

功能端到端至少覆盖：

1. 同一原片换两组商品和人物，相关脚本、价格、动作和建议同步变化；另一条不同原片不会套用工厂剧情。能提出起步示例之外的合法方案并按段组合，不受两种策略或固定枚举限制。
2. 分析授权不能启动制作；分析后AI说明方案与取舍，用户通过对话选定或调整，确认具体版本与制作预算后再按依赖执行。未选替代方案、模型自行声称获批、只讨论做法都不能触发制作；未获自动修正授权时检查失败不增加收费任务。
3. 预算恰好满足、差1积分、已有在途任务、多候选、改词和再检查都正确占用；个人与企业付款不混用，撤销授权后不新增提交。
4. 暂停、关页、重启、重复唤醒、未知受理结果和租约失效不重复提交；paused只刷新，partial继续旧run结算。

6. 检查逐项三态且有真实依据；用户接受失败或未知版本不篡改检查结论；自动修正只有白名单项、次数和双重预算同时满足才可执行。
7. 成片播放、文件解码、画幅、时长和音轨有效；模板复制模式不回退、合成结果可直接保存且归属正确。
8. 一轮真正经历模型、工具和结果回传，用户在结束前看到真实正文增量和工作记录；制作中发送变更被应用到后续步骤，停止优先生效，SSE重连或重复发送不重复扣费。
9. 分析与制作不是两页向导；同一时间线中按钮和自然语言确认一致，预授权内不出现重复审批。仅拖动额度不自动批准，过期卡和含糊讨论不能授权。
10. 完成消息展示实际积分、重做与未通过项，出现2至3条基于本次内容的后续建议；偏好保留且不代替授权，用户自写文字只有明确采用后才覆盖。
