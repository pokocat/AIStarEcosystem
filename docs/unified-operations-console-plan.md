## 1. 诉求与结论

用户的核心诉求是有一个好用的运营、管理后台。现有 AIStar admin 入口与配置分散，另起 aibuzz-platform 全面重写又会重复已有业务建设。

建议保留 aibuzz-platform 作为统一运营入口，逐项接入 AIStar 已有管理能力。优先统一操作流程、配置归属和视觉规范，已有任务、订单、权益和积分账本继续由原业务服务执行。管理界面整合与模型运行链路迁移分开推进。

交付标准是运营能独立完成日常工作，不以菜单数量、页面数量或基础框架完成度代替业务完成度。

## 2. 当前基础与问题

本轮依据两仓当前源码及 AIStar 已提交的发布记录判断；未重新进行线上全量验收。

| 系统 | 可复用的基础 | 当前不足 |
|---|---|---|
| AIStar admin | 用户、激活码、订单、账本、模型配置、业务模板、分发和审计等既有能力 | 不同产品与开发阶段的入口混杂；积分配置分散；产品术语与操作路径不统一 |
| aibuzz-platform | OIDC 员工登录与权限、应用目录、模型管理、成本与定价、经营指标接入基础 | 用户查询、业务订单、应用钱包等仍有待建设页面；已有菜单不代表接入完成 |
| 两仓接入 | Studio 配音已实现通过 Java SDK 获取发布价格和报告采用回执 | 生产平台定价尚未启用；图片、视频、口型等未统一接入 |

平台部分本地文档仍保留早期“未发布”描述。Studio 配音发布状态以本仓已提交的 [studio-platform-pricing.md](studio-platform-pricing.md) 发布章节为依据；实施前须重新核对运行版本和生效配置。

## 3. 系统分工与唯一真值

| 范围 | 推荐归属 |
|---|---|
| 统一运营界面、员工授权、跨应用查询与经营汇总 | aibuzz-platform |
| 统一成本与积分售价发布 | 平台管理；逐场景接入后成为该场景的唯一价格来源 |
| 用户业务档案、产品权益、订单、退款、作品和模板 | 所属业务应用 |
| 用户积分冻结、结算、释放与账本 | 原业务服务，如 AIStar CreditService |
| 登录身份与 UID | aibuzz-id |
| 模型调用、队列及供应商任务 | 当前业务执行服务；迁入 Runtime 另行验收 |

新后台通过受控管理 API 查询和执行业务操作。平台校验员工及管理范围，业务服务校验调用权限和数据范围，记录操作者与执行结果；SSO 不替代业务授权。禁止跨库直写和复制一套用户钱包。

品牌员工权限、品牌应用开通与终端用户产品权益是不同概念，接入时分别映射。现有渠道/租户也不能直接充当品牌。

同一业务配置只能有一个有效编辑入口。迁移前原配置有效；完成切换后旧入口改只读或引导到新入口，并标明生效来源。历史任务保留提交时的价格快照。

## 4. 按运营工作组织导航

顶部提供应用范围选择并记住当前范围；跨应用查询明确统计口径，不能把各应用用户数相加后宣称全平台去重用户数。

| 一级入口 | 核心工作 |
|---|---|
| 工作台 | 新增、活跃、付费、收入与应用表现；异常进消息中心并关联处理入口 |
| 用户与权益 | 用户查询、产品开通、套餐、积分、订单、生成历史、授权与补偿 |
| 内容与模板 | 官方画布模板、IP 资产、推荐位、版本、发布与上下架 |
| 生成任务 | 排队、执行、供应商状态、失败原因、冻结与结算结果 |
| 模型与定价 | 供应商、端点、应用场景、并发限制、成本、售价、试算与发布 |
| 订单与财务 | 充值、退款、积分流水与对账 |
| 系统管理 | 员工权限、应用接入、配置发布和操作审计 |

短剧、音乐、带货等特有能力在对应应用范围呈现，不强行塞进一套通用表单。未接入能力不作为可操作功能展示。

## 5. 首轮只交付三个完整流程

### 5.1 模型定价

两套独立配置：模型接入/端点维护供应商成本；应用模型定价维护客户积分售价。客户结算沿用原业务服务。

- 分开显示供应商成本、用户积分售价和实际采用范围。
- 成本按供应商账户/端点、模型和必要规格维护，不按应用重复配置同一成本。应用售价按应用、模型配置，只有实际存在价差时才展开场景、清晰度、模式。
- 此前“聚算积分暂按 1:1 换算，再加 50%”降为可选的填价辅助，计算后确认成独立售价；成本变更不自动改客户价，报价和客户价生效不依赖成本版本。Studio 剧本/图片的独立配置和平台固定价解耦已在本地实施；其他业务仍按各自接入进度。
- 计量单位明确为次、张、秒或 Token，规格维度包括模型、模式和清晰度。
- 成本与售价分别保留历史依据；保留价格快照、变更审计、并发保护与回滚能力，常规界面简化为填价、试算、保存/生效反馈。成本未知不记零成本，售价未配置不冒充免费。
- 配置成本提供核算依据，真实供应商对账还需要供应商任务号、实际用量、账单或实扣记录。客户售卖单位可以不同于供应商计费单位，各自计量。
- 验收：后台试算、用户端报价、任务采用版本和最终结算一致；已受理任务不随改价变化。

#### 应用场景的模型开放策略（已确认，首轮开发范围）

模型端点目录描述平台能接入什么；应用场景配置描述某个功能允许用什么以及向客户收多少积分。配置多个模型不代表所有应用自动开放全部模型。

| 场景示例 | 管理端配置 | 用户端行为 |
|---|---|---|
| Studio 写剧本 | 固定一个文本模型与每次积分售价 | 使用指定模型，不显示模型选择器 |
| Studio 生成图片 | 开放两个图片模型，各自售价，指定默认模型 | 只显示这两个可选模型，按所选模型报价 |

- 策略键为应用 + 场景，支持固定模型或指定候选列表；默认模型必须在列表内。用途绑定继续负责能力适配，场景策略在其范围内进一步收窄。
- 后端在报价/提交、冻结积分之前校验模型范围；隐藏前端选项不能代替后端校验。模型停用或指定候选不可用时明确报错，不绕过策略切到未开放模型。
- 场景候选保存独立客户积分售价和单位；缺价不能当免费，明确填写 0 才表示免费。供应商成本只用于核算，不参与固定客户售价的运行时计算。
- 已提交任务保存端点与价格快照，后续修改策略不重算其费用。前端重新加载配置后清理不再允许的旧模型选择。
- 尚未配置场景策略时保留原用途绑定和既有价格。首轮真实接入 Studio 剧本（含同一文本能力的改写、分镜和创作助手）及图片；其他应用场景没有接入前不显示为已生效。
- 新平台通过专用管理接口操作 AIStar 原记录，不另存一份模型目录，也不迁移供应商调用、队列或用户账本。

### 5.2 任务排查

输入用户或任务编号，关联参考素材、供应商任务、排队/执行状态、价格快照、积分冻结与退款结果。供应商状态未知先核查，不因后台重试造成重复生成或扣费。

验收：一条真实失败或待核查任务能从查询走到明确处理结果；权限、操作回执和账本可追溯。

### 5.3 模板运营

支持官方模板预览、发布、版本与上下架。用户端继续遵守“只读预览 → 保存个人副本 → 编辑与运行”，不因反复预览产生草稿。

验收：运营发布后用户可见，停用后新使用入口正确限制，已有个人副本保持独立。

## 6. 渐进实施与复用

1. 按上述三条流程盘点现有页面和 API，标记直接复用、补接口、需重做；明确权限与数据归属。
2. 在 Platform 完成一条流程的界面与业务接入，复用原业务服务；验收通过再进入下一条。
3. 迁移完成后收起对应旧编辑入口；未迁移功能保留明确的过渡入口。跳转只作过渡，不把多个后台永久拼成门户。
4. 后续再接用户权益、充值订单及经营数据。不以全量模型调用迁入新 Runtime 作为后台可用的前置条件。

Next.js 老 admin 与 Vite 平台不直接复制整套页面和运行时；优先复用业务 API、字段语义、流程和视觉规范。不为管理页面重写账本、任务状态机和供应商协议。

验证集中于本轮改变的流程：权限、价格、状态和结算做必要回归；视觉先检查代表页面，集中修正，再确认一次。文档修改不触发全仓构建或付费生成验证。

## 7. 视觉建议：保留 Ant Design 能力，沿用原 admin 的视觉气质

用户反馈：Platform 当前 Ant Design 后台不够紧凑，视觉不如原 admin。本节为建议，尚未改界面或完成视觉验收。

### 7.1 源码观察

- Platform AppShell：顶栏至少 64px，内边距 16px 24px；内容区 padding 24px、maxWidth 1440px；面包屑另有 16px 下间距。
- Platform PageContainer：标题为 Typography level 3，纵向 gap 为 large；叠加页签、卡片、筛选会进一步占用纵向空间。
- Platform 主题主要设置蓝色主色、6px 圆角和 14px 字号，尚未配置紧凑算法和系统性的组件密度。
- 原 admin 已有灰绿背景、低饱和青绿强调色、深色文字、细边框和克制阴影；好看不只来自尺寸小，色彩与层级更完整。原 admin 自身也有较大横向留白，不应机械复制所有尺寸。

以上是代码证据，不能替代同数据、同视口的浏览器对照。

### 7.2 推荐调整

保留 Ant Design 表格、表单、选择器和反馈组件；沿用原 admin 的配色、层级与克制风格，重整页面外壳和信息密度。不整库替换、不用全局缩放或堆叠 CSS 覆盖压缩页面。

| 项目 | 首版建议值/规则，待代表页面验证 |
|---|---|
| 顶栏 | 48–52px；管理范围、消息和个人入口一行排布 |
| 侧栏 | 208–216px；菜单行高约 34–36px；保持折叠能力 |
| 内容区 | 外边距约 16–20px；数据表格利用可用宽度，长表单控制阅读宽度 |
| 页面头 | 标题与主操作同一行；面包屑弱化，避免说明/标题/页签各占大块空间 |
| 字号 | 正文保持 14px；次要元数据可 12–13px；标题约 20px |
| 控件与表格 | 常规控件约 30–32px，单行数据约 36–40px；多行信息和校验消息允许增高 |
| 分组间距 | 同组约 8–12px，跨组约 16–20px；重要分组仍保留可辨识边界 |
| 卡片与状态 | 减少卡片套卡片；用分隔线和分组标题组织设置，状态色只承担语义 |

使用统一主题 token 和组件配置；可先试 Ant Design compactAlgorithm，再独立调整布局间距。紧凑算法不会自动消除 AppShell 的固定 padding，也不会解决重复标题和多层卡片。

不要把所有控件设为最小号：密度优化靠结构与空间分配，保留正文可读性、点击范围、焦点提示和错误信息。

### 7.3 最小视觉验证范围

先用“模型与定价”作为样板，覆盖数据列表、配置表单/抽屉、价格试算和发布确认；方向认可后扩展为全站页面规范。

使用相同数据对照 1440×900 和 1920×1080 桌面视口，确认首屏能看到关键筛选与业务数据、按钮不堆叠、文字不为追求行数而截断、表格滚动和弹层正常。本轮不另起移动端改版。

## 9. 当前实施记录（2026-10-10）

用户已确认保留 Ant Design 的紧凑灰绿/青绿方向，并授权优化模型管理。平台本地界面收拢为“模型接入”和“应用功能”，供应商成本跟随端点，用户售价复用同一功能记录；不直接连库、不复制配置权威。Studio 新端点可在功能内补候选能力，明确选择开放模型、默认项和独立积分价。价格专用命令不允许改模型路由，Runtime 草稿/发布和旧规格价格保留。

本地集中验收覆盖新增图片端点→候选能力→开放及售价、独立调价、成本保存、停用状态，并做针对权限与状态的代码复审。没有真实供应商调用或生产部署，测试夹具重启后数据会丢失。当前真实接入范围仍是 Studio script/image，不把其他应用目录登记等同真实调用接入。

详细实现与验收见 [平台优化记录](/Users/donis/dev/aibuzz-platform/docs/reviews/2026-10-10-model-management-optimization.md) 和 [第一轮迁移](/Users/donis/dev/aibuzz-platform/docs/aistar-model-migration.md)。原 admin 未删除，上线前仍需验证生产配置、服务密钥及目标环境回读。
