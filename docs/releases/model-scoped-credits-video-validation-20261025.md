# 通用视频模型计费增量验证 · 2026-10-25

状态：`codex/model-scoped-credits` 的本地开发增量，未发布。完整任务仍未完成，见 [模型专享额度](../model-billing-design.md)。

## 本次实现

- `MaterialVideoBilling` 按实际产品、模型、渠道、生成模式、清晰度、画幅和参考素材数量构造范围。种子、提示词和素材 key 不影响优惠资格，也不写入范围。按次计费还限定请求时长；按秒计费使用秒数和单位售价，保留生成区的规格加价。
- 新接入的收费通用视频都在受理时固定默认或选定渠道，并保存调用地址/视频协议规格。任务 payload 的 `_model_charge` 仅供结算，不进入公开 MaterialVideo 卡片。用户无法通过透传 variant_config 指定计费用途。
- Studio 企业视频将相同用途交给原付款授权服务，保存成员消费账户，不走个人余额。DAP 子视频继续由父收费项持有积分，避免重复扣费。
- 供应商请求发送前，在同一事务中核对渠道、实际型号、地址和协议快照，写原路由并标记资源已派发。排队期间配置变更不静默替换，按原来源释放客户冻结。
- 成功和查询恢复按原冻结的价格/折扣及累计用量结算。轮询临时故障保留供应商 ID 和冻结，只查询原任务，不再生成一遍。未知上游资源用量保守耗用预占，不因客户退款恢复资源。

## 真实数据库场景

`MaterialVideoScopedBillingIntegrationTest` 使用独立 H2（MySQL 模式）、真实仓库、钱包、专享批次、冻结/消费/释放流水及事务。模型边界为测试替身，不调用付费供应商；这些结果不代表模型生成质量验收。

1. 原价 100，八折应付 80，视频专享额度 50，普通余额 100。提交后普通余额 70、pending 30、专享冻结 50。随后将折扣改成五折并新增更高标准价，原任务成功仍只消费原专享 50 和普通 30，pending 归零；资源计 5 秒。再次运行已完成任务不重复提交或扣费。
2. 受理后，提交边界报告另一个模型：派发前拒绝，普通余额恢复 100，原专享恢复 50，供应商资源未派发且已用为 0。
3. 模型受理后第一次轮询失败：任务保持 generating、原冻结 ACTIVE。再次恢复只调用原供应商任务 ID，最终成功；真实 submit 仅一次，仍消费原 80。
4. 供应商称成功但未交回产物：客户冻结原路释放，供应商资源仍保守记为已用 5 秒。后续对账发现了产物，因原模型冻结已释放而返回 `VIDEO_MODEL_RECOVERY_REQUIRES_REVIEW`；没有创建新的恢复 hold、使用新批次或额外扣余额。

`MaterialVideoBillingTest` 另外验证规格/参考数量隔离、换素材 key 和 seed 不改变范围、按秒/按次和时长语义、DAP 父子不重复收费、零价模型不绕过限额、排队地址与协议变更拒绝。Studio 服务测试验证企业成员账户及相同精确用途传递，未触碰个人扣款路径。

## 回归与检查

分批运行了通用视频全部测试、Studio 模型选择接线、核心专享账本和模型计费 MVC 场景；后续对变更的场景再次定向重跑。当前报告合计 204 项通过、0 错误、0 失败；其中新增视频账本场景 4 项、范围单测 5 项。测试替身首次配置和原默认端点断言曾失败，修正为固定实际默认渠道并重跑，以上为最终报告结果，不将最初失败隐藏为通过。

覆盖既有视频提交、请求组包/协议、轮询、镜像与封面、取消认领、队列、原任务对账、提示词并发写回；本地 HTTP 协议测试只连它们自己的回环测试服务器。角色/配置接口回归包括版本冲突、原子审计、发放及企业成员查询。

四门通过：`pnpm typecheck:all`、`pnpm typecheck:admin`、后端 `./mvnw compile -q -o`、`pnpm check:api-contract`。契约检查保留原仓既有未落地接口警告，不是新增视频路径失败。`git diff --check` 通过。分套件结果见 [检查记录](model-scoped-credits-video-validation-20261025/checks.json)。
