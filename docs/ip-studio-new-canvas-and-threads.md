# Studio 新建画布、多段对话与卡片精简（2026-10-20）

> 现行设计真源。取代 `docs/ip-studio-conversational-video-recreation-plan.md` §对话形态里「每张画布一段对话、没有新对话和历史」那一句，
> 以及 AGENTS.md「创作助手改版」里确认卡「调整上限」「直接回复「可以」也行」的写法（§4）；
> 其余对话规则（事件流、执行、计费）不变。

## 1. 用户反馈

1. 「新建」的体验各处不一样：项目页点「新建创作」先跳到「画布·自由创作」页，那页又要在「全能创作 / 图片 / 视频 / 剧本」里选一个，填想法，再进画布。
   用户要的是：**新建 = 新建一张画布，直接进画布页**。画布页左边是画布，右边是创作助手，一眼就知道去对话框里说。
2. 空白画布没有任何提示（助手默认打开时，旧的空态被藏起来了）。要在画布中间给一组能直接点的入口：点「图片生成」就放一个图片生成节点，点「视频生成」就放一个视频生成节点。
3. 创作助手没有「新对话」和「历史对话」。

## 2. 新建画布（只改 web-aiavatar 前端）

### 2.1 规则

- 所有「新建创作 / 新建画布 / 新建空白画布 / 创建空白画布」都走同一个函数 `startNewCanvas()`（`src/ip/studio-entry.ts`）：
  免费建一张画布（名字「空白画布 · 新画布」，属于 `studioCanvasHasDefaultTitle`，第一条消息后按消息改名），然后进
  `/projects/{id}?start=assistant`：桌面上助手停靠在右边打开（不看用户上次关没关），画布在左边。
- **复用没动过的空白画布**：用户最近一张画布如果名字仍是「空白画布 · 新画布」、2 小时内建的、文档里没有节点也没有 `assistantConversations`，
  就直接打开它，不再建新的（反复点「画布·自由创作」不会堆出一串空画布）。判断失败（读不到）就照常新建，不报错。
- 进行中防重复：同一个按钮连点、React StrictMode 双跑副作用，都只建一张。

### 2.2 各入口

| 入口 | 改成 |

形态判断用 `useLayoutMode()`（`html[data-layout]`），不写媒体查询（AGENTS.md「一个应用两套形态」）。
`studio-creation-brief.tsx`（那个切换框）删除，样式一并删。

### 2.3 空白画布引导

画布没有任何节点、在「画布」视图、没有创作浮层（导演 / 配音 / 口型 / 解析 / 模板 / 素材库）打开时，在**可见区域**中间（让开左栏和停靠的助手，
用 `.studio-flow-shell.has-docked-panel` 与 `--studio-docked-panel`）显示一张卡片：

- 标题「这张画布还是空的」
- 一句说明：助手开着时「在助手里说想做什么，它会把每一步放进画布。也可以自己选一个开始：」；助手关着时同样的话，并多一个 AI 渐变主按钮「和助手开始」。
- 五个入口（白底细边卡片，图标 + 名称 + 一行说明），点了直接建节点，和左栏「＋添加」完全同一条路径：
  - 文字：写设定、剧本或提示词 → 建文字节点并进入编辑
  - 图片生成：写一句描述出图，可以加参考图 → 建图片节点并打开它的生成面板
  - 视频生成：用描述或一张首帧出视频 → 建视频节点并打开它的生成面板
  - 配音：选一个声音，把台词念出来 → 打开配音
  - 上传素材：图片、视频或文档 → 打开上传
- 底部一行小字：「双击画布空白处也能添加 · 从模板开始」（「从模板开始」可点，打开画布模板）。

卡片外层 `pointer-events: none`、卡片本身可点，不挡画布拖动和双击。一有节点就消失。手机宽度下入口两列。
旧的空态（`studio-workspace.tsx` 里只在助手关着时出现的「画布还是空的 / 和助手开始」）合并进这张卡片，不再保留两套。

## 3. 多段对话（server + web-aiavatar）

### 3.1 现状

服务端早就支持一张画布多段对话：`ip_dialogue_thread` 按 `project_id + owner_user_id` 存，`GET /conversation` 返回「最近打开的那段」
（`last_opened_at`），「从这里重新开始」就是建一段新的分支。缺的只是：列出全部、建一段空的、打开指定的一段。**不需要迁移**。

### 3.2 接口（`StudioDialogueController`，路径前缀 `/api/v1/ip-studio/projects/{id}`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/conversations` | 这张画布里本人的对话列表，按最后活动时间倒序，最多 50 段。只列有消息的对话，加上当前那段（哪怕是空的）。 |
| POST | `/conversations` | 新建一段空对话并设为当前，返回它的 `State`（同 `GET /conversation`）。请求 `{clientRequestId}`，同人同键幂等。本人在这张画布已有一段没有消息、没有进行中回合的对话时，直接复用它（设为当前）而不是再建一段。 |
| GET | `/conversations/{threadId}` | **只读**：校验本人与画布，对齐状态（`reconcile`）后返回它的 `State`，不改「当前对话」。断线重连、轮询、补拉都用它。 |
| POST | `/conversations/{threadId}/open` | 用户主动切到这一段：校验后设为当前（`markOpened`），返回它的 `State`。 |

> 2026-10-20 评审修正：最初 GET 会顺带 `markOpened`，后台补拉旧线程的快照时会把服务端的当前对话偷偷改回去（刷新后回到错误对话、多个标签页互相抢）。读和切换从此分开。
> 前端所有线程归属的异步请求（分页、执行查询、快照）都带发起时的线程与切换代次，回包对不上就丢弃；确认制作在途时不能切换，切换在途时不能确认。
> 确认请求结果不明（断网、网关超时，不是明确拒绝）时，不读快照猜结果，而是用**同一个请求编号**按 2s / 4s / 8s… 封顶 30s 重发确认：服务端按编号幂等，
> 要么拿回第一次已建的执行，要么现在才建，执行只有一份；期间这段对话不能新建或切换，提示「正在核对确认结果，请稍等」，卡上有「现在再查一次」。明确拒绝才解锁并在卡上报错。重发暂无次数上限（TODO.md）。
> 2026-10-21 评审修正（Codex P2）：**打字确认**（回复「可以」）是服务端在回复里确认的，回复结束时前端还不知道它建的执行。从收到「确认卡已确认」（`approval.required` 事件，或快照里本来待确认的卡变成已确认，带 `executionId`）起，
> 到读到这份执行（或读执行明确返回 400 / 403 / 404）之前，这段对话一样不能新建或切换（`DialogueStore.awaitingExecutionId`，计入 `dialogueThreadBusy`，提示沿用「这段对话还在进行，等它做完或先停止」）；
> 读失败按上面的 2s / 4s / 8s… 封顶 30s 重读，切走画布或卸载就停。第一次打开对话时卡早已确认，不算。按钮确认的路径不变（`confirming`）。

都先 `ensureMainThread`（保证主线程和旧记录导入在前）。新对话不继承技能，`title` 用默认值；不复制任何消息；不触发任何模型调用、不扣费。

列表元素（TS 真源 `packages/types/src/ip-studio-workflow.ts`，Java `StudioDialogueDtos.ThreadSummary` 同名同字段）：

```ts
export interface StudioDialogueThreadSummary {
  id: string;
  /** 显示名：第一条用户消息（压掉空白，最多 24 字，超出加「…」）；还没说过话是「新对话」。 */
  title: string;
  /** 从「从这里重新开始」分出来的那段才有。 */
  parentThreadId?: string;
  messageCount: number;
  /** 最后一条消息时间与这段对话创建时间取较晚的那个（空对话即创建时间；刚分出的分支排在原对话前面）。ISO 8601。 */
  lastActivityAt: string;
  createdAt: string;
  /** 是不是 GET /conversation 现在返回的那段（最近打开的）。 */
  current: boolean;
  /** 有回合正在回复，或有执行在跑 / 暂停中。 */
  active: boolean;
}
export interface StudioCreateThreadRequest { clientRequestId: string }
```

错误码沿用：`clientRequestId` 不合法 400 `STUDIO_INPUT_INVALID`；对话不存在或不属于本人 404（与现有 `requireThread` 一致）；
同键不同内容不适用（请求只有一个键）。

### 3.3 前端

- 创作助手头部（标题右边、停靠 / 关闭按钮左边）加两个图标按钮：「新对话」、「历史对话」。`StudioFloatingPanel` 加一个 `actions` 插槽。
- 「新对话」：调 `POST /conversations`，用返回的 `State` 替换当前时间线（和「从这里重新开始」同一种切换方式），重新订阅事件流。
  输入框里的字、引用、附件、模型都保留（不丢用户正在写的东西）；技能选择回到「自动」；开场卡片重新出现。
  当前就是空对话时按钮不可点，提示「现在就是新对话」。
- 「历史对话」：antd Popover 列表，每行：名称（单行省略，全名在 `title`）、`formatDateTime(lastActivityAt)` · `N 条消息`、标签「当前」「进行中」「重新开始」（有 `parentThreadId`）。
  顶部也有一个「新对话」。点一行 → `GET /conversations/{threadId}` 切过去。读取中 / 失败可重试 / 只有当前一段时写「还没有别的对话」。
- **当前这段正在回复或有执行在跑 / 暂停时，不能新建也不能切换**（按钮不可点，原因写在提示里：「这段对话还在进行，等它做完或先停止」）。
  原因：画布节点是前端按当前对话的事件流写进去的，切走会漏掉还没收到的节点。
- 切换后 `?start` / 自动发送逻辑不受影响（只在空线程、首次打开时发）；按对话记的画布游标照旧按 `threadId` 存。
- Esc 在 Popover 里只关 Popover，不关助手（沿用浮层的 Esc 规则）。
- 演示模式（`NEXT_PUBLIC_USE_MOCK=1`）的 `src/ip/mocks/studio-dialogue.ts` 照服务端补齐三个接口（§8.0.1 ⑦）。
- 头部注释与 `docs/ip-studio-conversational-video-recreation-plan.md` 里「No history picker, no 新对话」改为指向本文。

## 4. 助手卡片与文案精简（2026-10-20 用户反馈）

原话要点：卡片废话太多；制作计划里只要把需求变成要生成的描述、跟用户确认就行；「用户需求完整且无真实取舍，直接按规格出一张图即可满足」是系统的判断过程，不该给用户看；
确认卡把积分上限、对话预留、超过会停下这些计算逻辑都摆出来了，用户只需要看到要花多少积分然后确认；「直接回复「可以」也行；说「再想想」就不会开始」没必要；
功能在那里用户自己会用，不用什么都提醒。整个助手界面按用户视角重新过一遍，去掉 AI 腔，用语要准确、顺、好读。

### 4.1 原则

- 卡片只回答三件事：做什么、花多少、按哪个按钮。其余（结算方式、上限、预留、过期时间、可以打字确认、重做额度、版本号、技能版本）不显示。
- 不给操作提示：用户看得到的按钮和输入框不用再用文字教一遍。
- 模型的判断过程（`approaches[].rationale`、`tradeoffs`）永不显示。
- 服务端行为不变：打字「可以」照样能确认（`StudioNaturalApprovals`），确认卡照样 24 小时过期，上限照样按服务端提议，只是界面不说。

### 4.2 制作计划 + 确认卡合成一张

同一条回复里同时有方案（`plan` 块）和待确认的卡（`approval` 块）时（直达技能每次都是这样），只渲染**一张卡**，方案卡不单独出现：

```
确认制作                                   （分析阶段：确认分析）
一张 1:1 的末日英雄形象图，写实偏插画的废土风     ← plan.summary，有就显示
┌ 末日英雄形象图                          图片 ┐ ← 每一步：标题 + 类型
│ 要生成的描述（step.prompt，最多 3 行，「展开」看全文）│
└──────────────────────────────────────────┘
30 积分
[开始制作]  [先改改]
```

- 多个做法（`approaches` > 1，复刻常见）：在步骤上方列做法，每个只显示 标题 + summary + 「推荐 / 已选」标记，有 `preserve` / `change` 时各一行「保留：…」「改变：…」；非推荐的有「改用这个做法」。`rationale`、`tradeoffs` 不显示。
- 只有一步时不写「共 1 项」，直接显示这一步。多步时是有序列表，每步的描述默认收起（「查看描述」）。
- 卡上不显示每步报价、预计、重做额度、上限；价格只有一个大数字。
- `scope`（确认卡自带的范围清单）在合并卡里不显示（步骤已经说清了）；没有对应方案时（单独一张确认卡）才显示 scope。
- 单独的方案卡（没有确认卡跟着，比如改了方案还没报价）：同样的结构，没有价格和按钮。
- 头部不要「等你确认」「第 N 版」「按技能：xxx」。

确认卡各状态：

| 状态 | 显示 |
|---|---|
| 待确认 | 上面那张卡 |
| 已确认 | 收成一行「已确认 · 30 积分」，点开看步骤和「确认于 yyyy-MM-dd HH:mm:ss」 |
| 已过期 | 标签「已过期」，一行「报价已过期」+ 文字按钮「重新报价」（作为用户消息发出「重新报价」） |
| 已被替换 | 标签「已更新」，一行「已有新的报价，见下方」，不再显示步骤 |
| 预算不够（shortfall） | 一行「积分超出上限，还差 N 积分」+ 一个输入框「新的上限」（默认 = 原上限 + 差额）+ 按钮「提高上限并继续」；只有这时才出现上限输入，重做额度不再给输入框（沿用服务端值） |
| 方案还没到（planReady=false） | 按钮不可点，一行「方案还没到，稍等一下」 |

### 4.4 制作完成总结与「放进画布」

用户反馈：制作完成后那条「这次制作完成了。实际花费：制作 30 积分。做完的步骤：…。每一步的结果都在画布上。」下面也有「放进画布」，点了只是把总结放进画布，没有意义。

- 「放进画布」只给真正的内容回复：执行完成总结（`completionExecutionId`）、system 消息、本条已经建 / 改过节点的回复一律不显示；正文至少 80 字。
- 完成总结（服务端 `StudioExecutionSummary`）只说一句结果和总花费：「做好了，花了 30 积分。」/「没有做完，花了 N 积分。」/「已停止，花了 N 积分。」/「做了 90 分钟还没做完，先停在这里，花了 N 积分。」；
  不分阶段列花费，不写「其中对话」，不复述做完的步骤（时间线里的逐步清单已有「在画布上看」）。没做完的步骤、检查没通过的原因各一行。
- 完成后的建议从实际产物来：出了图给「用这张图做一段视频」「换个风格再出一张」；兜底不再是「重新开始这次制作」，有产物时「把这张画布存为模板」，什么都没做成时「再试一次」。

### 4.5 模型侧（提示词，`PromptTemplateSeeder.SEED_VERSION` 必须升版）

- `dap.ip_studio_skill_plan.md` 规则 2、新增规则 7：summary / title 只写要做出什么、一句话、限长；不写判断过程、积分和流程；rationale 必填但不展示。
- `dap.ip_studio_skill_dialogue.md`：调用工具前不预告；不主动讲计费；发了卡时正文最多一句、不复述卡片、不报价、不给操作提示、不写判断过程；不用「好的 / 收到 / 我将为您」开头。
- `RequestApprovalTool` 的 `scope` 说明：每条一句、不超过 20 字，写画面、规格、风格，不写计费、上限、流程。

## 5. 新对话的四个快捷入口（2026-10-21 用户反馈）

用户原话：新对话里的快捷选项不够易用，换成「制作个人 IP（真人照片做成数字 IP，多视角图）、写剧本、做个短视频、复刻视频」，按网上热门好用的做法设计好。

### 5.1 做法

参考现在常见的做法：AI 写真类应用先讲清照片要求再选风格，即梦 / 可灵这类生成工具用选项按钮代替空白输入框，复刻类工具先把「参考 + 你的素材」两样收齐。落到我们这里就是**填空卡**：

- 开场（空对话、没有引用节点时）只有这四张卡，2×2 排列：图标、标题、一行「会得到什么」、一行小字「需要：…」。有引用节点时的那组卡（修改节点内容 / 优化提示词 / 整理所选内容…）不变。
- 点一张卡，开场区换成这张卡的**填空卡**（顶部「← 换一个」回到四张卡）：
  - **素材位**：每个位写清要什么、齐没齐（✓ / 还缺），按钮「从画布选」（走输入框的 @）和「上传」（走输入框的附件）。画布上正好只有一个合适的素材时自动选上。
  - **选项**：每组单选按钮，默认值预先选好；用户不点也能直接发。
  - **文字位**：需要用户自己写的一两句话（梗概、画面描述），单行输入，有示例占位。
  - **生成的话**：按素材、选项、文字实时拼成一句话写进输入框（引用用 @ 标签，和手动 @ 一样）。用户手动改过输入框后选项不再覆盖，出现小链接「按选项重写」。
  - 发送仍用输入框的发送键（一条路径），缺必填项时按钮不可点，旁边写缺什么（「还差照片」「先写一句梗概」）。
  - 发送时把技能显式设成对应技能（不靠关键词路由）。
- 只是前端引导：服务端报价、确认卡、计费都不变。演示模式照样可用。

### 5.2 四张卡

| 卡片 | 会得到 | 需要 | 技能 |
|---|---|---|---|
| 制作个人 IP | 真人照片变成数字形象，出多角度设定图 | 1–3 张照片 | `image-generation` |
| 写剧本 | 一句梗概写成能拍的分场剧本 | 一句梗概 | `script-writing` |
| 做个短视频 | 一句描述出视频，也可以从一张图动起来 | 画面描述 | `video-generation` |
| 复刻视频 | 照爆款的节奏和镜头，换成你的商品或人物 | 参考视频 + 你的素材 | `reference-video-recreation` |

**制作个人 IP**
- 素材位「你的照片」（必填，1–3 张图片）。下面一行小字：「正脸清晰、光线均匀、只有一个人，效果最好。只用本人或已获授权的照片。」
- 选项「风格」：写实（默认）/ 3D 卡通 / 日系动漫 / 国潮插画 / Q 版。
- 选项「要出的图」：多视角设定图（默认，正面、侧面、背面加几个表情）/ 只要三视图 / 头像。
- 生成的话：「用 @照片 做一个我的数字 IP 形象，保留脸型、发型和主要特征，{风格}风格，出一张{要出的图描述}。」

**写剧本**
- 文字位「一句梗概」（必填），占位「比如：外卖员送错一单，意外救了老板的女儿」。
- 选项「类型」：短剧（默认）/ 广告片 / 口播 / 微电影；「时长」：30 秒 / 60 秒（默认）/ 3 分钟 / 分 3 集；「基调」：有反转（默认）/ 搞笑 / 温情 / 悬疑。
- 生成的话：「写一个{时长}的{类型}剧本：{梗概}。{基调}，分场写清画面、台词和时长。」

**做个短视频**
- 文字位「画面描述」（必填），占位「比如：女孩在海边回头微笑，风吹起围巾」。
- 素材位「首帧图」（选填，1 张图片）：有图时从这张图动起来。
- 选项「画幅」：9:16（默认）/ 16:9 / 1:1；「时长」：5 秒（默认）/ 10 秒；「镜头」：自动（默认）/ 缓慢推近 / 环绕 / 跟拍。
- 生成的话：「做一条{时长}、{画幅}的短视频：{描述}。」有首帧图时加「从 @图 开始动起来。」，镜头不是「自动」时加「镜头{镜头}。」
- 所选模型不支持的时长 / 画幅照现有规则在确认前就地报出，不静默改（AGENTS.md「生产问题五项」）。

**复刻视频**（原复刻清单 `studio-assistant-checklist.tsx` 已并入同一种填空卡并删除）
- 素材位「参考视频」（必填，1 条）；「换进去的商品或人物」（必填，1–3 张图片）。
- 选项「保留」：节奏和镜头（默认）/ 节奏、镜头和口播 / 只保留节奏。
- 文字位「要讲的卖点」（选填），占位「比如：保温 12 小时，一键开盖」。
- 生成的话：「照 @参考视频 的拍法，把里面的商品或人物换成 @素材，保留{保留项}{，口播改成介绍：卖点}。」
- 首页那句话需要参考视频时（`studioBriefNeedsReference`）照旧打开这张填空卡、保留用户原话、不自动发送。

### 5.3 实现说明（2026-10-21，与上文的细化和偏离）

代码在 `apps/web-aiavatar/src/ip/studio-assistant-starters.tsx`（四张卡的配置、填空卡组件、拼句纯函数 `composeStarter`），接入在 `studio-assistant.tsx`。

## 6. 执行结果落到助手准备的节点、首帧比例（2026-10-21 用户反馈）

- 视频文件 768×1344（9:16），首帧 1024×1024（1:1）。逐点对照：太阳、高楼的相对位置与首帧完全相同，厂商把正方形首帧非等比拉伸成竖屏，画面纵向拉长约 1.78 倍。9:16 是助手按技能默认写的，没看首帧比例。画布结果节点是 320×240 的 4:3 框，也没按视频比例。

### 6.1 结果落到已有节点

- 方案步骤可带 `targetNodeId`（模型填）：画布上已经有为这一步准备的对象时（助手刚用 `create_nodes` 建的，或用户放的空图片 / 视频 / 文字对象），结果放进它，不再另建。规划提示词写明这条。
- 服务端编译方案时校验：节点在文档里、类型与操作对应（image→图片、video→视频、text/script→文字）、还没有产物、没被同一方案里别的步骤占用；不满足就去掉这个绑定（不报错，写进日志）。
- 模型没填时自动绑定：本对话里助手建的（`metadata.studio.spec.source === 'assistant'`）、还没有产物的同类型对象，**唯一**一个对应**唯一**一个同类型步骤时绑定；有歧义就不绑。
- 绑定后执行步骤的 `nodeId` = 这个节点（前端 `stepNodeId` 已经优先用 `step.nodeId`），生成任务的 `node_id` 也是它；`node.upsert` 对它是更新而不是新建：写入产物、状态和执行信息，保留它的标题、规格和连线。恢复逻辑（`missingExecutionNodes` 等）不能再补一个重复节点。
- 每个结果节点（新建的或绑定的）都写上这一步实际发给模型的提示词（`metadata.prompt`）；绑定节点上用户自己改过的提示词不覆盖（照现有 keepText 规则），实际发出的仍记在请求里。

### 6.2 首帧比例不再拉伸

- **默认跟首帧**：出视频技能与对话提示词写明——有首帧图、用户没说画幅时，画幅跟首帧图一致（取最接近的支持画幅）；用户明确说了画幅才用用户的。
- **服务端兜底**（图生视频的所有入口：对话执行与手动生成面板，都经 `StudioVideoService`）：首帧图的宽高比与请求画幅相差超过 2% 时，先把首帧**居中裁剪**到请求画幅（等比，不拉伸），存成本人的派生图再交给厂商；任务输入里记 `_exec.firstFrameAdjusted {from, to, mode:"crop"}`，日志记一行。不改请求画幅、不静默换规格。
- **生成面板提示**：手动出视频时首帧比例与所选画幅不一致，就地一行：「首帧图是 1:1，会按 9:16 居中裁剪」+ 按钮「改成 1:1」。不挡发送。
- **画布显示**：视频（和图片）结果落进节点时，节点按产物的实际宽高比调整高度（宽度不变，高度有上限）；视频元素 `object-fit: contain`，任何情况下不变形。
- 已经生成的那条变形视频无法回改，重新生成即可。

### 6.3 实现说明（2026-10-21，与上文的细化和偏离）

- **在哪一步绑定**：规划（`StudioPlanValidator.validateSkillPlan`，对话 `propose_plan` 与原生规划 run 共用）只做形状检查——`targetNodeId` 在素材清单里、这一步的结果是一个图片 / 视频 / 写稿文字、同一计划里一个对象只给一步，不合格就去掉并写日志；真正的绑定在**确认时**按已保存画布做（`StudioPlanValidator.bindTargets`，在建执行、确认制作阶段、确认改过的方案三处调用；面板确认前先存画布，打字确认的发送链路也先存）。绑定结果是执行状态里步骤的 `nodeId`，不改计划，指纹不变。
- **「本对话里助手建的」**：取这段对话最近 200 条消息里已完成的 `create_nodes` 工作记录的 `result.nodeIds`（`StudioDialogueConfirmations.assistantNodeIds`）；只有来源不知道对话时才退回 `studio.spec.source === 'assistant'` 标记。文字对象没有 spec，所以按对话记录判断而不是只看标记。「还没有产物」另外排除正在生成（`status=loading`）和已是别的执行输出（有 `studio.execution`）的对象。
- **改过的方案**：重做的同一步沿用它原来绑定的对象（除非新方案给它点名了别的对象），新增的步骤照常绑定。
- **读步骤节点只有一处**：`StudioPlanExecutionIds.stepNodeId`（`nodeId` 优先，否则 `<执行>-<a|p>-<步骤>`），执行器的任务 `node_id` / `node.upsert` / 依赖连线 / 检查节点的来源、`StudioPlanOutputs.outputNodes` 与引用解析（绑定对象还没被画布保存时从 run 读产物）、`StudioWorkflowService` 的步骤校验、执行接口的 `steps[].nodeId` 都用它。前端 `stepNodeId` / `missingExecutionNodes` / `executionRestoreUpserts` 本来就按 `step.nodeId`，恢复不会补重复节点。
- **提示词**：服务端从任务输入取实际发出的提示词（视频绑定 run 的 `prompt`，图片 run 的 `studioRequest.prompt`，取不到用步骤自己的），新节点直接写上；绑定对象上已有提示词时按 keepText 保留，发出的那句作为可采纳建议出现（设计写「照现有 keepText 规则」，原样执行）。
- **规划模型看得到什么**：素材清单（`DialogueCanvasDigest.line`）在画布记录了真实尺寸时写「1024×1024（1:1）」，在没画面的草稿上写它的设定「设定 9:16、5 秒」；同一轮里刚 `create_nodes`、画布还没保存的对象另列在「本轮刚新建、画布还没保存的对象」下面；`view_images` 的结果给每张图的 `size` 与 `aspectRatio`。规划提示词的 JSON 形状写了 `targetNodeId?`，`skillPlanConstraints` 加了 `targets` 一行。
- **裁剪**：尾帧同样处理（`lastFrameAdjusted`）；单首帧旧协议（没有视频模式设置的模型）也经 `alignFrame`。JDK 读不了的格式（WebP）先用 ffmpeg 转 PNG 再裁；结果不透明的写 JPEG（质量 0.95），有透明的写 PNG，存储层再按字节判类型。记录字段 `{from, to, mode:"crop", sourceKey, croppedKey, sourceSize, croppedSize}`，在绑定 run 的 `_exec`（出 wire 时 `_exec` 照旧去掉）。
- **恢复按「是否已回填」判断**（2026-10-21 Codex P1，web-aiavatar）：制作中关页、换设备打开时，绑定的准备对象在画布上但还是空的。`missingExecutionNodes` / `executionOutputMissing` / 恢复回放（`projectStudioNodeUpsert` 的 `missingOnly`）原先只看节点在不在，于是结果永远补不进去（任务成功、积分已结算，画布仍是空的）。现在：节点在画布上时，只要它没有这一步的结果、也没有别的内容（`nodeHoldsResult`：媒体 / 文字 / 剧本、生成中、已带执行绑定，对应服务端 `emptyObject`）就补进去，与本浏览器的投影记录无关（准备对象在助手建它时就记下了）；节点不在画布上时照旧看投影记录（删掉的不重建）。补的方式与实时事件相同（标题、尺寸、规格、连线保留，已有提示词 / 文字按 keepText 保留，恢复不出采纳建议），补进去的对象和新建的一样可以接上这次的依赖连线。已绑定到这一步的节点（哪怕之后用户手动重新生成过）算已回填，不覆盖。
- **节点比例**：结果落地时打一次性标记 `studio.mediaFit {storageKey, aspectRatio}`（执行投影与手动生成 `applyStudioRun` 都打），先按任务画幅定高度（宽度不变，媒体区 = 宽 × 比例，上限 640，加 38px 卡片头），媒体加载后（图片 `onLoad`、视频 `loadedmetadata`）按真实尺寸再定一次并去掉标记；之后用户自己拉的尺寸不再被改。卡片同时把所显示媒体的真实尺寸记进 `naturalWidth/Height`（旧画布打开时会为此保存一次）。视频元素本来就是 `object-fit: contain`。
- **面板提示的首帧**：原生视频模式取请求里的首帧（`videoSettings.firstFrameKey` 对应的图），单首帧旧协议取第一张参考图；尺寸用画布记录的真实尺寸，没有就从图片地址量一次；「改成 X」只在所选模型（当前清晰度档）的画幅里有首帧那个比例时出现。
- **演示模式照服务端补**（§8.0.1 ⑦）：出图 / 出视频的演示先 `create_nodes` 建好对象（写画幅、时长、首帧），方案步骤带 `targetNodeId`，确认时按同样规则绑定，结果以 `op=update` 落进同一个对象，带提示词和 `mediaFit`；有首帧图且用户没说画幅时演示画幅跟首帧。
- **真模型**（本机开发凭据，聚算 `qwen38-27b`，按 `propose_plan` 的规划请求）：画布上一张 1024×1024 的图 + 助手建好的空视频对象（首帧连线），用户说「用这张图做一段视频」：新提示词调用 7 次、5 次有回复（另 2 次厂商 503），5 次全部填了 `targetNodeId` 指向那个对象、`aspectRatio` 为 1:1、i2v 首帧绑定那张图；旧提示词 + 旧素材清单对照调用 5 次、3 次有回复（2 次 503），3 次都没填 `targetNodeId`、画幅都是 9:16（即线上那次）。旧提示词下服务端的自动绑定仍会把结果放进那个对象。
