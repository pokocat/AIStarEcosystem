## 为什么编译快照会显示 Git dirty

Git dirty 的含义只是“当前文件与此目录的 HEAD 不同”，不能证明差异在 Mac mini 上产生。开发机带未提交改动的工作树若连同 Git 元数据同步过来，编译快照天然就是 dirty；旧快照也不会随主线推进自行变干净。本次已有 337 个版本可与当前/历史主线或三方合并对应。

本审计没有逐个文件的写入审计日志，不能证明所有改动都来自同步，也不能归咎于编译步骤。仍应核对每次同步的来源 HEAD、dirty 清单/内容哈希与编译前后哈希，才能区分源端改动、生成器改写和编译机人工编辑。

## 方法与边界

- 原样保留基线到快照的文本差异，不把冲突解决成猜测版本。补丁依赖各自清单里的基线，不是面向当前 main 的一组可顺序应用补丁。
- 当前/历史判定依据文件内容 Git blob；124 个历史版本另按同一文件路径核实主线提交记录。
- 三方合并使用原快照 HEAD、快照文件、上述 main 文件，仅文本比较，不运行应用。
- 不包含 `.env*`、凭据、缓存、编译产物、安装目录、素材和非代码文档。同步排除导致的 `.env*` 缺失不是删除凭据的代码意图。
- `.release-readonly/AistarReleaseReadOnly.java` 仅记清单，不上传临时运维源码；其原件留在 mini。不能据此 PR 认为所有个人/运维文件已归档。
- 这是存在内容版本审计，不覆盖仅文件模式变化、文件删除、被忽略文件或无法读取文件。原始目录均保留，**不能仅凭此 PR 删除全部快照**。
- 不包含本机绝对路径、请求正文或真实素材地址。测试中的 example.com / 8.8.8.8 带 signature 的 URL 是测试夹具，不是实际授权链接。
