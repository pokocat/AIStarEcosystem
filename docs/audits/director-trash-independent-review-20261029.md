## 结论

当前改动未发现遗留的阻断问题。回收站仅列本人已删除作品；恢复原 ID 和内容，保持停止，不自动生成、不重提、不扣费。保留既有删除在途检查，不增加永久删除、清空或到期清理。恢复不拦数量，新建仍按当前未删除作品数量执行既有 200 部门槛。

## 审查发现及闭环

1. **恢复后隐式付费续跑**：终态但未回投的手动视频提示词改写，原先会在恢复后的首次读取中提交视频或自动重试改写。已以 `restoredAt` 区分恢复前任务：结果照常回投，后续付费派发关闭；恢复后明确提交的新任务仍正常。Codex 在独立 Java 探针中实际调用 `delete → restore → reconcile`，成功、失败两种旧改写均通过，成功结果保留、无新提交。
2. **恢复后自动开场**：非企业模式的创意对话原先会在打开作品时自动提交。恢复过的作品现在等待用户点「开始聊」，正常新建作品保留原体验。Claude 的本地浏览器验收检查了请求记录：恢复后打开没有任务 POST，点击开始后才提交。
3. **恢复后的迟到 404 清草稿**：仅 GET 的请求顺序保护不足以覆盖旧 PATCH / 生成请求。API 现记录请求发出时的恢复代次，恢复成功或响应带回新的恢复标识后推进代次；旧代次的 404 只提示操作没有生效，不标已删除、不清草稿。Codex 的独立前端探针通过「旧保存挂起 → 发现删除 → 恢复并重新加载 → 写入新草稿 → 旧保存返回 404」；同一探针还验证恢复后新请求真 404 仍触发已删除状态。
4. **恢复页重新加载失败无反馈**：已增加忙态、重试反馈和最新 GET 请求结果保护。旧 GET 的 404 不覆盖恢复后较新的读取。

恢复、删除和后台推进使用同一作品行锁；恢复只用本事务、本连接，不调用另开事务读取任务的 `view()`。正常作品重复恢复不写内容、修订号或更新时间，不干扰当前任务。
