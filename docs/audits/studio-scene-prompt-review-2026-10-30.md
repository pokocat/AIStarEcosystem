# 场景化创作提示词审查与优化方案

日期：2026-10-30（北京时间）。状态：**审查与方案完成，未改业务代码、配置或部署；未新增付费生成。**

> 范围修正：用户随后明确要求所有内置图片、视频生成流程都顺畅，同城只是举例。本报告的“团购/促销优先”实施顺序由 [全量生成流程审查与方案](studio-built-in-creation-flow-review-2026-10-30.md) 替代。以下提示词证据与逐场景内容策略保留，不代表只做同城优化。

## 1. 结论与证据边界

客户反馈有实现层面的依据。当前场景视频具备不同的名称、素材要求和一句拍法，但还缺少“业务事实收集 → 按场景组织卖点 → 明确行动目标 → 保留信息生成 → 检查成片”的完整约束。同城团购应当帮商家卖出套餐并促成到店，现在更容易停留在门店展示和氛围描述。

优先解决四件事：收齐团购信息；把各场景的业务结构写具体；修正脚本与视频改写的格式衔接；让价格、地点、套餐和购买动作成为可检查的交付内容。增加“高级感”“电影感”不能解决这些问题。

本轮证据：

- 新版源码基线：`/Users/donis/dev/AIStarEcosystem-release-scene-home`，`c095ae31d`，审查开始时干净。当前主工作目录是较早的 `codex/ai-director` / `39fe31c9c`，不能当作新版功能基线。本报告只写入主工作目录文档。
- 完整阅读随包目录的 **21 个视频场景、17 个图片场景**，追踪 `compose → textEdit → 采用脚本 → video → H3 rewrite`，以及长视频/复刻交给助手的分支。
- 线上原生 Chrome 只读核对同城团购页，以及当前账号中已有的品牌故事验收草稿。没有提交文字或视频生成，没有上传或新建项目。没有取得客户反馈那一单的原始请求、最终供应商提示词和成片，因此不能把某个代码问题断言为客户那一单的唯一原因。
- 同城团购线上仍提示“不写也行，编导会先看照片”，要求先放门店照片；当前可见 H3 配置为 15 秒，场景期望时长为 25 秒，可交给助手分段做。
- 已有品牌故事初稿实际出现“做杯子三十年”“摔了三千次”及摔杯画面，输入只给了虚构白瓷杯品牌和“简单耐用”。后续已有人工改稿将这些删除。此证据证明已有样本出现事实扩写，不代表所有场景都会如此。
- 发布记录 `docs/releases/studio-scene-backend-production-release-20261030.md` 记载后端仍为 `80edade0f` 构建，较新的事实约束未发布；本轮线上看到的品牌故事拍法也仍是旧文案。本轮未重新读取服务器 SHA 或生产数据库，部署事实以该记录为依据。
- 运行了一个零模型调用的 Java 正则探针：从新版 `H3PromptRewrite.java` 提取实际匹配式，对比场景规定格式和 H3 既有格式。场景格式的镜头头、代码填台词匹配均为 0；既有格式均为 3。仅证明格式衔接问题，不是生成效果实验。

## 2. 当前链路与可保留的基础

```text
场景目录（后台配置优先，随包 JSON 兜底）
  → 用户一段文字 + 素材 + 场景选项
  → StudioSceneCatalog.scriptBrief
  → 普通文本任务（通用助手 system + 文本编辑输出契约）
  → summary / content（自由文本分镜）
  → 用户采用 content 作为视频 prompt
  → 按视频模型能力选择实际参考素材
  → H3 可选再改写
  → 视频生成
```

场景规则已经集中在服务端，后台可配置，原生任务、素材归属、费用确认、同键恢复等链路也可继续复用。优化应集中在内容契约及其传递，不需要另起一个生成系统。普通场景可以共享执行引擎；问题在于共享引擎收到的业务要求不够具体。

## 3. 审查发现

### F01 · P1 · 同城团购没有收齐成交所需信息

证据：`scenes.json:742` 附近的 `local-groupbuy`，`StudioSceneCatalog.java:195` 的 ComposeRequest、`:262` 的 videoInput，前端 `scene-video-studio.tsx:311` 的 blocker。

同城团购与门店发现、到店实录、招牌体验共用输入示例和四条 ideas。只要求门店照片，`textRequired=false`；接口没有地点、套餐、原价、团购价、购买渠道、使用条件等字段，也不检查这些信息是否已从自由输入提供。9 个电商/同城场景都允许不写文字。

照片可以提供环境、外观和部分可辨认文字，不能可靠提供当前活动价、套餐规则和购买路径。只补一句“不要编造”，结果就可能从“编优惠”变成“避开优惠”，依然没有完成团购任务。

建议：保留自然语言输入，自动提取后展示轻量确认卡。团购成片至少需要商家/套餐、可到店位置、团购价、包含内容、实际购买方式；原价有则比较，无则省略比较，不要求商家编一个。时间限制、预约、周末/节假日规则要标为已知、未知或不适用，未知不能写成不限时、不用预约。

缺关键项时一次集中补齐；允许先看创意草稿，但必须标出未完成的业务信息，不能把它当作完整团购广告直接交付。

### F02 · P1 · 场景有一句拍法，但缺业务完成条件

证据：全部 21 个 VideoScene 只有 8 种 placeholder；只有 5 个视频场景有 options；`scriptBrief:308–324` 通用拼接。

团购拍法已写“价格、套餐、怎么买”，所以不能说它完全没有团购指令。缺的是必须出现哪些信息、开头怎样识别附近顾客、怎样说明原价与现价、什么 CTA 与发布渠道一致，以及如何判断这条片做完了。

示例：团购的常用开头仍有“突出排队和热闹的氛围”。点击后它成为用户要求，模型可能优先花时间展示热闹，而不是解释套餐价值。引导按钮本身就是提示词的一部分。

建议：每个场景补 `目标 / 必需事实 / 内容顺序 / 话术风格 / 参考素材用途 / 收尾动作 / 完成检查 / 正反例`，同步修改 placeholder、ideas 和示例。不要只改隐藏提示词。

### F03 · P1 · 促销指令与事实边界存在冲突，且缺信息时降级过于笼统

证据：`ecom-promo.structure` 要求强调时间有限；`ecom-talking.structure` 要求讲优惠。新版 `StudioSceneCatalog.FACT_RULE:254` 禁止无依据的优惠、限时等，却将缺失情况统一处理为“只引导关注或下单”。

新版事实边界值得保留，但“团购缺价格 → 引导关注”会丢掉场景目标。已有品牌故事的虚构年限/测试次数也说明事实约束需要覆盖生成结果，不能仅依赖 prompt 中的一句话。

建议：改为条件分支。有原价才比较，有实际截止时间才催截止；只缺原价可继续，没有团购价就询问，不能自行换成关注。按本次需求明确 CTA：购买套餐、预约、到店、关注各有不同条件。虚构剧情与真实商家事实分开；生成的人物不能自动被写成真实顾客证言。

### F04 · P1 · 场景脚本绕过了已有的确定性镜头与台词保护

证据：`StudioSceneCatalog.java:319` 要求 `镜头N（起–止秒）…；台词：…`；`H3PromptRewrite.java:280` 只匹配 `第N镜（…）`；`:92` / `:94` 的代码填台词只匹配 `某人说：「…」` 或旧版特定格式。`H3StudioPrompt.java:36–41` 用这些解析结果决定固定镜头及代码填台词。

因此严格照场景要求生成的脚本，通常进入“由模型定镜头、写台词”的路径，而不是复用已存在的固定镜头和台词占位填充。Java 探针对三镜样本验证了这一点。

注意：系统仍有 `spokenLines` 等后验检查，不能说台词完全无人保护，也不能说改写必然丢词。确认的问题是场景输出与更强保护路径不兼容，增加了再次解释内容的空间。

建议：短期统一渲染格式，让场景脚本接上现有保护；长期使用结构化镜头与对白，再由适配器生成各模型 prompt。价格、地点、购买动作应属于锁定文案，改写只处理画面、运镜和模型语法。不要让 H3 技术改写承担营销策划职责。

### F05 · P1 · 脚本成功只检查格式，没有检查场景任务是否完成

证据：`StudioTextRevision.java:33` 只检查 summary/content 的类型、非空和长度；worker `StudioWorkflowWorker.java:230` 一带直接采用该验证；`scene-drafts.ts:145–162` 视频请求只有 prompt、素材与媒体规格，没有独立事实表或业务覆盖结果。

一份 JSON 正确、文案流畅、没有地址和团购价的脚本，也会成为可采用的成功结果。现有场景测试主要检查 compose 含预期文字、素材和字段，不能证明实际模型输出完成了业务目标。

建议：校验“哪些已提供的必要事实出现在口播、字幕或镜头中”，并验证金额、单位、使用条件、CTA 一致。不可用标题或 summary 冒充脚本覆盖。画面里安排门头，也不等于最终片中可辨认地表达了位置。

建立生成前内容检查与成片后抽检两层；前者先做，避免把明显缺信息的稿子送去花费更高的视频生成。

### F06 · P2 · 单条时长有约束，但信息优先级和改规格后的复核不足

证据：`scene-video-plan.ts` 的 clampSceneDuration 将场景时长限制到模型范围；线上团购为 15 秒/期望 25 秒；`scriptBrief:320` 统一规定每镜 2–5 秒、台词约每秒 4 字。`useScript` 复制文字后，出片可再改模型和时长。

缺少“15 秒团购到底先说什么”的策略。把探店、制作、套餐逐项展示、地址、原价、优惠、使用规则全部平均分配，容易既超载又讲不清重点。改成更短时长，也未见场景级的对白时长和事实覆盖重新检查。

建议：15 秒版保住地点/商家、套餐价与核心内容、购买动作；真实原价和关键限制按可容纳程度进入口播或可读字幕。信息仍放不下就明确建议分段，不静默删掉。语速按数字真实读法、停顿、语言估算，最终以音轨时长实测；4 字/秒只能做初筛。

### F07 · P2 · 编导写稿时没有完整考虑最终素材和声音能力

证据：`scene-video-studio.tsx:332–344` 按当前全部图片编号给编导；`:428` 与 `scene-video-plan.ts` 出片时再决定实际保留哪些图和声音。后者能给出丢弃说明，这是已有的正确处理。

不足：若换到只认首帧的模型，脚本仍可能依赖图2、角色图或专属声音。接口虽提示部分素材不使用，稿子却没有同步重新规划。不支持看图的文字端点会收到“先看图/已附图片”的 compose 文案，而前端只是不传 imageIds 并提醒用户不看图，任务要求本身也应随能力修正。

建议：先计算有效素材，再交给编导；模型或素材变化后标记脚本需复核。人物身份、商家门头、专属声音等用户明确要求的要素不能仅靠“不使用”提示就视为完成。

### F08 · P2 · 通用文本节点契约不适合作为场景编导的长期唯一契约

证据：`StudioWorkflowService.java:220–221` 将 operation=text 路由至 `dap.ip_studio_assistant`，再于 `:305` 追加 StudioTextRevision.CONTRACT。随包助手模板要求计划 JSON，文本契约再覆盖为 summary/content；后者明确覆盖，所以不能直接判定 JSON 契约必然冲突。

主要问题是任务身份仍偏“通用创作/编辑”，业务必需项都藏在一段用户 prompt，没有独立场景结果模型。生产 `prompt_template` 可以覆盖随包模板，本轮未核对数据库实际 system，故不能把随包身份文案说成已确认的线上最终 system。

建议：复用现有任务执行，但增加场景专用编导契约与结果字段；基础指令保持短、稳定，具体业务规则来自场景目录。不要继续给所有文本编辑任务堆营销规则。

### F09 · P2 · 只修改随包文件不保证生产提示词更新

证据：`StudioSceneCatalog.catalog:118` 后台配置优先；`PromptService.java:243–268` 启用的数据库模板优先，且 system/user 分别回退。发布记录已有“事实边界代码完成、后端未发”的区分。

建议：发布前核对目录来源与版本、启用模板版本、已受理任务的实际提示词快照。针对运营改过的目录做带版本号的合并，保留运营素材和自定义场景；不要为更新几个场景整份恢复内置。验收依据是实际组装内容与最终有效 prompt，不是只看文件 diff。

## 4. 全部视频场景的内容改造矩阵

下表是每个场景应补的业务职责，不要求所有场景都强行卖货。

| 场景 | 必须问清/确认 | 应强化的内容顺序与收尾 |
|---|---|---|
| 口播带货 | 商品、受众、真实卖点、购买路径 | 人群痛点 → 一项核心利益 → 演示证据 → 明确购买动作；优惠有才讲 |
| 促销转化 | 现价、可比较原价、优惠条件、活动时间、购买路径 | 直接报利益 → 解释买到什么 → 条件/截止（有依据才写）→ 下单 |
| 场景种草 | 使用者、具体时刻、需求、可见体验 | 生活小困扰 → 自然使用 → 具体变化 → 轻量推荐；避免强促销套话 |
| 痛点解决 | 真实问题、适用条件、解决机制、可展示结果 | 痛点动作 → 使用过程 → 有依据的结果；不自动编前后对比效果 |
| 功能演示 | 1–3 项功能、操作步骤、限制 | 一个镜头讲清一个动作与可见结果；结尾给下一步，避免只拍外观 |
| 门店发现 | 城市/商圈、店名、位置、到店理由 | 地域识别 → 一项特色 → 环境 → 位置/导航；不默认塞团购 |
| 到店实录 | 实际体验记录/素材、服务步骤、可说的评价 | 进店 → 体验细节 → 有出处的感受 → 到店建议；纯生成时不冒称真实探店 |
| 招牌体验 | 招牌名称、制作/服务特点、实际卖点、门店位置 | 招牌诱人细节 → 特点 → 体验 → 到哪里获得；不要只拍环境 |
| 同城团购 | 地点、套餐、现价、内容、购买入口、使用条件；原价选填 | 附近人群 + 套餐利益 → 原价/现价（有则比较）→ 内容 → 怎么买/怎么用 |
| 品牌主张 | 核心立场、受众、支持立场的产品/行为 | 具体选择或行动 → 品牌态度 → 可记住的一句话；不硬促单 |
| 品牌故事 | 可验证的经历；允许虚构哪些人物/情节 | 人物目标 → 具体困难/坚持 → 品牌落点；无史料不造创始人历史 |
| 生活方式 | 目标人群、一天中的具体时刻、品牌角色 | 有特点的生活片段 → 产品自然参与 → 情绪记忆；别泛化为咖啡馆风景 |
| 创意概念 | 主张、产品关联、视觉母题 | 一个可执行的视觉隐喻 → 清楚揭示与产品关系；记得品牌而非只记得特效 |
| 对话剧情 | 人物关系、目标、冲突、结局 | 第一轮对白进入事件 → 关系变化 → 收束；对白有动机而非互相讲设定 |
| 反转剧情 | 初始认知、伏笔、真正真相 | 误导 → 可回看的伏笔 → 反转兑现；短时长限制人物与事件数量 |
| 悬疑剧情 | 核心谜题、已知线索、是否本条揭晓 | 异常 → 线索 → 揭晓/明确悬念；不要为了吊人省掉必要因果 |
| 情感剧情 | 关系、具体事件、情绪转折 | 一件小事与行动 → 情绪变化 → 克制收束；不统一套吵架和身份反转 |
| 剧情植入 | 故事、商品真实能力、植入边界、转化目标 | 商品参与因果 → 情节继续 → 合适的购买/记忆动作；避免无功能关联的露脸 |
| 数字人口播 | IP 身份、受众、主题、核心观点、声音要求 | 具体问题 → 一个核心答案/少量论据 → 对应 CTA；口型/音色由真实能力兑现 |
| IP 日常 | 固定人设、标志习惯、当天事件 | 有人物特征的一天 → 小变化/情绪 → 人设记忆；不只保持脸一致 |
| 爆款复刻 | 借鉴结构、替换商品/人物、真实卖点、保留/改变项 | 拆结构 → 重写成本商家内容 → 替换核查；原片价格、优惠、证言不得沿用 |

## 5. 同城团购的具体优化稿

### 5.1 输入与缺失处理

建议从用户一句话中提取以下字段，不要求一开始面对大表单：

| 字段 | 处理方式 |
|---|---|
| 店名与城市/商圈/可到店位置 | 核心项；允许已确认的简短位置，精确地址可分配到字幕/发布说明 |
| 套餐名称、适用人数、包含项目与份数 | 核心项；防止把单品价写成套餐价、把单人写成双人 |
| 团购价 | 核心项，带币种/计价单位；不得从氛围或包装推断 |
| 原价 | 有依据才用；缺失时用现价与套餐价值，不能生成“原价” |
| 活动时间、核销有效期 | 区分售卖截止与使用期限，不能混成一个“仅限今天” |
| 预约、节假日、门店适用范围等限制 | 明确状态；重要限制不能在压缩脚本时被反转 |
| 购买入口 | 具体到本视频团购、门店主页、其他真实路径；没有挂载就不能说“点下方链接” |
| 素材 | 门头/位置、套餐全貌、招牌细节，分别标用途；图片识别的价格与条款须确认 |

缺项例：“套餐价、到店位置、怎么买还没写。这三项补上，我就能写成可直接带团购的版本。”已有资料只确认缺的，不反复问。

### 5.2 可先落入现有后台的拍法与输入文案

输入提示建议：

> 写清店名和位置、套餐包含什么、几个人用、团购多少钱、怎么买；有原价、活动日期或预约限制也一起写。门店照片负责还原画面，价格和活动按你提供的信息来。

拍法建议：

> 目标是让附近顾客购买套餐并到店使用。开头尽快说清附近位置、套餐和团购价；有已确认原价时做明确比较。中间展示套餐实际包含的核心项目与份量，让顾客知道花这笔钱得到什么。结尾清楚说购买入口、到店位置及关键使用条件，发出直接行动邀请。不要把主体篇幅用于环境空镜、排队或泛泛夸好吃；只有用户提供真实截止时间才使用限时催单。未提供的价格、赠品、地址和限制不补造。

常用思路改为：“先报位置和套餐价”“原价与团购价对比（需提供原价）”“把套餐内容拍清楚”“结尾说怎么买、怎么到店”。

上述修改能立即改善方向，但只改后台文字不能实现缺项检查、结构化覆盖校验和 H3 解析修复，不能把它当作全部改造完成。

### 5.3 场景专用提示词骨架（待实现）

```text
你为本地商家制作能推动团购购买与到店使用的短视频。

输入：
1. 已确认业务事实：{facts}
2. 实际发布渠道与购买入口：{cta}
3. 素材及用途：{effectiveReferences}
4. 时长、语言、比例和模型实际能力：{generationSpec}

结尾给出真实可执行的购买动作与必要使用条件。

事实规则：
原价、团购价、份数、地址、活动日期和使用限制只能来自已确认事实。
未提供原价就不作原价比较；未提供截止时间就不用限时话术。

内容规则：
口语短句，每个镜头对应一个业务作用；画面与口播表达同一信息。
有限时长优先留给套餐利益和购买动作，环境镜头只用于识别门店与建立可信感。
对白、画面、字幕分别输出；对白逐字保存，技术改写不得擅改。

输出：
missingFields、factsUsed、shots（时间/画面/原样对白/字幕/引用）、cta、coverage。

```

### 5.4 15 秒示例（虚构商家与价格，仅示范，不是生成实测）

假设商家确认：巷里火锅在万达广场东门旁；双人牛肉套餐，牛肉一份、蔬菜两份、饮品两杯；原价 158 元，团购 99 元；周末可用，需预约；实际发布会挂载本视频团购入口。未提供限购数和截止日期。

| 时间 | 画面任务 | 口播 |
|---|---|---|
| 0–5 秒 | 用真实门头参考识别店铺，转到套餐全景 | 万达东门巷里火锅，双人餐九十九！ |
| 5–10 秒 | 展示牛肉、两份蔬菜、两杯饮品，不新增菜品 | 原价一百五十八，牛肉、双蔬、双饮。 |
| 10–15 秒 | 套餐与门头收束，为真实购买入口作引导 | 周末能用，提前约。点本视频团购，走起！ |

该例让地点、价格、内容、使用条件与 CTA 都进入可听内容。最终仍需测实际语速和停顿；过长先精简表达或延长，不加速到听不清。若要求价格卡与地址字幕准确，应用确定性文字叠加；当前场景出片不能因 prompt 写了字幕就宣称具有独立字幕合成能力。

## 6. 图片场景的关联问题（17 个均已阅读）

图片模板总体比视频具体：已经明确主体、参考图、构图、保留/改变项，无需一起重写成营销长文。优先补这些边界：

| 范围 | 优化重点 |
|---|---|
| 自由出图 | 明确期望用途、主体与画幅；保留自由，不强行套商业模板 |
| IP 设定图、脸部三视图、人物四视图、表情包 | 明确这是“一张拼图”还是可分别使用的资产；检查视图/格数、身份、服装一致性，少靠“完全一致”一句话 |
| IP 写真 | 场景、身份气质与使用用途；默认咖啡馆只能是兜底，不作为统一风格 |
| 模特换脸、人脸融合、服装上身 | 区分哪张负责身份、哪张负责姿态/服装；检查实际对应，不能只检查图片数量 |
| 商品白底图、图片精修 | 包装文字、标识、颜色、形状是保护项；生成式处理仍可能重画，检查真实结果 |
| 商品使用、商品卖点图 | 提供真实卖点及使用动作，避免由外观推断功效；卖点图目前明确不生成文字，是留白配图，若目标是完整详情图还需单独排版步骤 |
| 服装改款、人物入景、商品入景 | 第二参考图缺失时，必须有可用的新面料/场景描述，不能让“按补充要求”指向空文本 |
| 人物真人感 | 允许纹理变化，但身份特征与年龄感受保护；不用“更真实”默认改变脸型 |

图片问题为模板/契约层审查，未逐个执行生图效果验证。

## 7. 花叔 skill 库的借鉴与取舍

本轮阅读了 [huashu-douyin-script](https://github.com/alchaincyf/huashu-skills/blob/master/huashu-douyin-script/SKILL.md)、其 [品类公式参考](https://github.com/alchaincyf/huashu-skills/blob/master/huashu-douyin-script/references/proven-formulas.md)、[huashu-script-polish](https://github.com/alchaincyf/huashu-skills/blob/master/huashu-script-polish/SKILL.md) 与 [huashu-video-check](https://github.com/alchaincyf/huashu-skills/blob/master/huashu-video-check/SKILL.md)。作为方法参考，没有安装或运行其下载/模型脚本。

- 借鉴脚本 skill 的“明确产品/人群/目标 → 文案钩子与视觉钩子配合 → 分镜 → 转化动作 → 审校”。将它改成我们的场景字段、模板和验收规则，避免直接把整篇 SKILL.md 塞给生成模型。
- 借鉴口语审校：短句、实际可说、内容与演示对应；不要为了“像真人”编第一人称使用经历。该 skill 的字速建议与本产品当前估算不同，应以实际音轨校准。
- 借鉴封标检查中的承诺与内容一致性。它大量面向分钟级内容，不能把“结尾再兑现核心信息”照搬到 15 秒团购广告；团购利益应尽早出现。
- 品类公式以口腔护理、美妆为例，不能当成已经验证有效的本地生活团购模板。外部库中的涨点击率案例、粉丝量阈值、审核经验不能直接当成本产品保证。
- 不采用“换成模糊体感即可可信”的思路。真实来源不变，不能把无依据数据改成“我亲测好用”就视为解决问题。

## 8. 分阶段落地

### 第一批：直接解决同城团购和促销转化

1. 先用现有后台更新团购/促销的 placeholder、structure、ideas；保留其他运营配置。
2. 增加最小事实收集与缺项提示。自然输入仍然可用，提取结果一次确认。
3. 将场景稿渲染为能被已有 H3 解析器正确识别的镜头/台词格式，并验证代码填对白实际生效。
4. 在采用脚本前展示简明核对：位置、套餐、价格、购买入口、使用条件分别是否已覆盖。缺项给具体原因，不写笼统“质量不佳”。

### 第二批：统一内容契约，覆盖全部场景

在服务端目录中增加版本化的业务目标、事实要求、节奏策略、正反例与验收项；基础参数继续复用现有场景配置。新增字段必须同步后台编辑器、类型与 compose；不要分别在前后端维护两份规则。

草稿文档保存事实及脚本版本；服务端受理时保存已确认输入、模板来源/版本、有效素材、输出规格和实际拼装提示词快照。继续遵循客户端拥有 doc 的约束，服务端不回写或擅改用户画布内容。

商业事实与业务覆盖是独立数据。最终发送给模型的形式仍可按能力变成文本，但不能仅凭一段自由文案恢复全部业务状态。手改脚本、换模型/时长/参考素材后重新核对；已有受理任务保持原快照，不自动重跑。

### 第三批：高准确商业成片

对于必须逐字正确的价格、地址、条款，逐步支持画面生成、固定配音、确定性字幕/价格卡合成；这属于能力建设，不是单靠 prompt 已经实现。先复用已支持的配音/总装能力并核实调用范围，不能直接把其他产品域的实现当成本入口可用。

若暂时只交付模型原生音视频，明确依靠人工检查最终对白/字幕，不宣称价格文字有确定性保证。

## 9. 评测与验收方案

先做零视频费用的确定性校验，再做少量经授权的真实模型对照。内容效果不能用 HTTP 200、JSON 合法、通用单测通过代替。

| 层次 | 必测内容 | 通过条件 |
|---|---|---|
| 输入/组装 | 信息齐全、缺原价、缺现价、无活动截止、预约限制、仅照片、参考片旧价格 | 提供的事实原样保留；缺必要项提示；未知不变成肯定承诺 |
| 场景区分 | 同一商家分别做门店发现、招牌体验、同城团购 | 三稿主体不同：找店理由 / 招牌价值 / 套餐成交；不只是替换标题 |
| 格式适配 | scene 编导输出 → H3 build；带多句对白、数字、引号 | 镜头起点正确、对白可精确填回，价格与地点不因改写丢失 |
| 改稿/换规格 | 99 改 89、只改语气、换购买入口、15 秒改 10 秒、换首帧模型 | 旧事实不复活，未要求改的保留；超载和引用不支持被识别 |
| 脚本评测 | 每场景至少完整/缺项/冲突三类样本，关键场景多跑几次 | 事实准确和必要信息覆盖为硬项；风格、自然度与镜头可执行性另外评分 |
| 成片抽检 | 团购、促销、品牌故事、数字人口播四类代表样本 | 实际听到/看到关键业务信息；字幕金额、口播金额与输入一致，入口能兑现 |

同城团购建议评分：业务覆盖 35、事实正确 25、购买路径 15、镜头与文案配合 15、口语与节奏 10。80 分可作为候选阈值，但编造价格/地址/活动、漏购买路径或关键限制讲反，一律不得被总分掩盖。该阈值是待校准的产品方案，不是已经验证的效果指标。

A/B 以相同模型、相同素材、相同规格、相同业务资料比较旧/新提示词；评审者尽量不知道版本。先比较脚本业务完成度，再少量出片验证，最后有实际投放数据时再比较购买/核销结果。当前不能承诺转化率提升幅度。
