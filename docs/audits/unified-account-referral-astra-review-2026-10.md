## 1. 评审结论

**有条件通过方向，初稿尚不具备直接开发条件。** 全球唯一“注册来源”可以成立，但它必须被严格命名为“账号注册邀请关系”，不能成为会员推荐人、企业成员关系、活动推广、渠道成交归因的通用真值。

推荐首期使用账号中心内有边界的 `referral` 模块，同库事务只负责保存注册决定及身份变更事实；邀请图使用独立异步投影。暂不拆独立服务，也不引入图数据库、闭包表、跨服务注册事务。这个选择需要在账号中心 README/AGENTS 中正式记录一次职责扩展，而不是借“与 UID 有关”默认获得任意业务权限。

以下四项是实施前必须补齐的 P1：首建事务和上下文消费、扫码确认时点、合并投影的一致性语义、私有事件分发。存量基线、后续商业归因和生命周期也必须明确，不能留给开发人员临场判断。

## 3. 问题及具体修正

### R1 · P1：建号提交与邀请消费不在同一事务会永久漏归因

**触发例**：短信首建的 REQUIRES_NEW 已提交 UID，外层写邀请失败；下次重试看到已有账号，“老账号不补绑”又阻止修复。另一个竞态是有邀请和无邀请两条请求同时首登，失败请求重查到赢家后再补写，反而改掉赢家的决定。

**修正**：在 `createByPhone` 和微信 resolver 的实际 create 事务内，通过同一数据库事务保存 UID、凭据、不可变 registration decision、context 消费结果与私有事件。唯一键至少覆盖 `decision.original_uid` 和已消费 context 的唯一关联。赢家提交什么就是什么；输家只读取原决定，不覆盖，包括 NONE。外层参数应是已校验的 `RegistrationAttempt`，不能由任意调用方传 inviterUid。

context 不得先从 Redis CAS 删除后再提交 MySQL 注册：事务回滚会烧掉上下文。若上下文落 MySQL，同事务条件更新并记录 `consumedByUid`、结果和流程；同流程重试可读原结果，不可给第二个 UID 使用。失败重试不得依赖重放一次性微信 code，应该让用户重新完成凭据认证后读取已提交结果。

**必须决定**：邀请数据持久化故障是否允许注册。建议“已选择邀请的新注册”在无法可靠保存决定时明确失败/可重试；不能降成 NONE。已有账号正常登录不依赖图投影。这里与“图重建不阻身份合并”是两种不同要求。

### R2 · P1：PC 会话上下文不能直接解决手机建号与扫码投毒

当前手机回调在确认前建 UID，而 PC 的邀请上下文不在手机 session 内。若在 PC `/finish` 写归因，已经错过创建事务；若直接信任 PC 票据携带的邀请，又会让被诱导扫码的人在尚未确认时永久绑定攻击者来源。

**修正建议**：邀请注册流程在首次创建 UID 前提供明确继续动作。扫码链在换到经验证的微信身份后，将最少身份解析结果存短期服务端待办，在手机确认“继续注册/登录这台电脑”时才调用建号漏斗；确认页同时展示脱敏邀请来源。context 由 PC 发票据时绑定，手机只能按票据读取，不能用 query 参数换 inviter。票据状态、有效期、流程、context 在建号前和提交时复核。PC finish 仍只认原 PC session 的票据，并沿用现有登录确认防护。

这是对扫码链的明确增量，不是说当前实现已经如此。若决定保留“回调即建号”，必须承认取消扫码也可能已经固定注册邀请；本评审不推荐把它包装成“确认后绑定”。

web context 绑定稳定的 flowId/受控浏览器流程，不直接依赖会轮换的原始 session id。`WebLoginSession.java:75–113` 和 `AccountManagementController.java:225–230` 都会轮换 session。既不能因安全轮换丢归因，也不能放开跨任意 session 兑换。

### R3 · P1：同步迁移整棵图与“不阻登录”不能同时承诺

一个有大量下游的 UID 合并，会影响下游父节点、祖先与循环检测。把这些放在现有身份行锁事务中，会扩大锁等待、死锁与重试范围；全局图锁更会把无关用户的首登一起串行化。捕获异常后继续提交则会留下无法确定的半张图。

**修正**：身份事务只保存固定大小的必要事实与可靠待处理记录，图计算由单独投影器完成。数据库本身故障仍可使身份事务失败；正确承诺是“关系冲突、图规模和投影器故障不阻断身份合并”，不是“任何故障都绝不阻断”。不要吞掉 outbox 写失败，现有 `PhoneBindingService.java:595–602` 明确要求回滚。

`id_user.merged_into_uid` 已是身份合并真值。新增 alias 若有需要只能是投影缓存，不能产生第二个可独立修改的合并真值。图读取遇到尚未应用的身份变更，返回明确 `RECONCILING` 及版本，不返回旧链冒充当前关系。鉴权始终用原始 token sub，不能借 alias 给旧 UID 扩权；证据 `config/CurrentUser.java:12–17,25–31`（账号仓）。

### R4 · P1：现有 outbox 会把邀请关系泄露给全部产品

初稿“复用现有 outbox”缺少投递对象限定。新 UID 尚无产品链接，调用 `fanOut` 会写 NULL，现有查询使任何合法产品客户端都拿到 payload。客户端忽略未知 eventType 只是容错，不是保密。

**修正**：首期邀请变更使用专用私有 feed/持久任务，不调用产品 `fanOut`。可以复用已提交事件发布游标的算法，但需要独立的查询、授权与默认零订阅；若共表也必须先完成强制 audience 隔离并验证旧产品查询绝不包含私有行。专用表对当前结构更容易审查。现有 `USER_MERGED` 的 from/to 身份事件照旧，不向它塞邀请人、上下游或商业字段。

服务读取不仅要 scope，还要已登记的 client、目的和主体范围。拿到 `referral.read` 不等于可以枚举全生态关系。账号中心运营权限应单独授予，不能因为某产品具有 OPERATOR 或企业 owner 就获得跨产品关系。

### R5 · P1：全球一个邀请人不能覆盖已有会员/商业归因

已核对的兼容事实：军师 `../ai-pilot/server/src/services/referral.ts:232–309,357–371` 有自己的绑定、窗口和运营补绑；`referralCapture.ts:1–5,47–67` 有自己的捕获凭证。公社 `../ai-society/server/src/main/java/com/fenglema/scp/identity/ReferralService.java:14–16,32–85` 按 member 建关系并保存 projectId，`:87–100` 已关联成长值；`ops/InviteCodeService.java:25–56` 的码还具有 project_scope 和轮换语义。这些不是账号中心注册来源的同义字段。

**修正**：统一字段/接口使用 `account_registration_referral` 语义。保留产品现有外键和逻辑，不将旧 member/user 邀请人批量回填为全球 inviter，不用全球 NONE 关闭既有产品的活动邀请，不将全球关系事件直接用于佣金或成长值。未来 activity/partner/conversion 归因分别带自己的主体、业务域、窗口与证据，不受全球注册邀请唯一键约束。当前不需要提前实现这些表，只需禁止复用注册关系承载它们。

### R6 · P2：NONE、旧账号、导入与异常不能混成“没有邀请人”

建议不可变决定使用 `REFERRED`、`NONE`、`LEGACY_CLOSED`、`IMPORTED_CLOSED`、`SYSTEM_CLOSED` 等可区分原因；这些名字是建议，核心是语义必须可区分。普通新注册在无有效邀请下明确 NONE 并闭合，老账号没有数据代表未完成基线或未知，不能解释为可补绑。过期/撤销码由用户看到失效结果并选择普通注册；系统存储故障不能伪装成“用户没受邀请”。

部署时先建立存量 UID 清单/基线，并让所有新建路径保存决定，再开放入口。不能只用 createdAt 与发布时间比较：老用户可能在上线后才导入成新 UID。导入路径显式标 `IMPORTED_CLOSED`，体验/系统账号不得发邀请或成为新客。滚动升级期间旧实例仍能裸建 UID，所以要有切换屏障和缺事实扫描；缺记录只能补基线原因，不能从此后浏览器 cookie 猜回历史邀请。

注销后现有逻辑允许释放凭据并创建新 UID，见 `IdUserService.java:118–145` 和 `WechatIdentityResolver.java:128–145`。因此“新 UID”不是“从未来过的自然人”。首期不做奖励可按新账号记录，但必须在统计中说明口径；以后做奖励另设反重复参与政策，不能拿本链直接发钱。

### R7 · P2：合并中的“取消”和“当前抑制”是不同合同

存活方决定优先（含 NONE/LEGACY）合理，但“来源账号下游迁给存活方，环冲突不迁移”还不足以唯一确定结果。若遍历顺序不同，保留哪条边可能不同；后续再次合并又可能让原来冲突的边恢复。

**修正**：明确选择可恢复的投影抑制或永久取消。推荐首期采用下节的确定性抑制，并把原因展示为“身份合并后的关系冲突”；原始事实不变，未来身份变化可能解除抑制。若业务坚持永久取消，必须持久化每次合并的边处置结果并在重建时重放，工作量和规则明显增加，不能只凭最终 alias 全量重算。

### R8 · P2：公开链接、后台链路查询还缺少可执行权限合同

随机码只解决可猜测性，不解决合法码被嵌入页面、自动预取或第三方脚本植入。公开 GET 只预览，不创建关系、不消费 context；用户明确继续后才冻结这次注册尝试。流程开始后不被另一个标签页的链接覆盖，切换邀请需要重新开始尚未提交的流程。建议采用“本次明确选择”，不要混用全浏览器最后点击 cookie。

页面只返回必要脱敏来源，不泄露 UID、手机、上下游数；no-store/noindex、Referrer-Policy、最小脚本依赖、限频、撤销与有效期是接口设计要求。return target 只取受信客户端的已登记路径/白名单，不能把公开参数变成任意跳转或 OAuth client 身份。scope/客户端不能靠请求里的 `entryApp` 自报获得。

用户只读直属并做分页，默认不展示电话、完整 UID 或跨产品活动；运营祖先/后代查询限制深度、总节点数、耗时，带截断标记与审计。不能把“最多查 N 层”用于证明全图无环。停用/注销邀请人应冻结新邀、保留或脱敏历史事实，不自动把其下游提升给祖先；详情政策需定稿。

## 4. 建议的合并投影算法与一致性边界

### 4.1 首期算法

1. 注册决定按原始 UID 永久保存，一人一行；关系方向统一为“被邀请 UID → 邀请 UID”。新注册只能指向已经存在的 UID，且普通注册/存量基线也闭合，因此未规范化的原始图天然有时间方向。导入旧关系、管理员任意补绑都不属于这个证明。
2. 投影以一致性快照读取决定和身份合并映射。每个最终存活 UID **只保留自身原始决定作为父边来源**；被并 UID 的父边不继承给存活方，哪怕存活方是 NONE。其他存活 UID 的原始邀请人则沿身份 alias 规范化，形成迁移下游。
3. 自环标 `SUPPRESSED_SELF`，不形成当前边。对候选图求强连通分量；每个非平凡 SCC 内，抑制“原始 inviter UID 与规范化后 inviter UID 不同”的迁移边，记 `SUPPRESSED_CYCLE`。原始未迁移边是原 DAG 的子集，因此删掉这些 SCC 内迁移边后不会残留环。
4. 此算法保守，可能比只去掉一条边删除更多当前关系，但不依赖处理先后或遍历顺序，适合先保证可解释性。原事实仍显示真实注册邀请；当前图和原事实的计数不得混算。后续图变化解除冲突时，投影可以恢复该边，必须按此口径命名。
5. 注销节点不合并到祖先；可保留内部不可登录历史节点供审计，但对普通用户隐藏可识别资料。停用不删除历史邀请边。是否对已注销邀请人继续显示“已注销账号”由隐私/产品政策确定。

例：B 原来由 A 邀请、C 由 B 邀请，之后 A 合并进 C。C 保留自己的 B 父边；B 的原父 A 规范化成 C，形成 B↔C，抑制 B→C 这条迁移边；不会把 C 的原父边改写为 A 的父边。若 C 原来是 NONE，则它仍无父边。

### 4.2 为什么首期可用后台全量重建

只存邻接关系的图可以按节点/边线性扫描及 SCC 处理，不必先做闭包表。建议首期采用单投影写者的数据库租约、后台全量重建、校验后原子发布 `projectionVersion`。读者只见完整版本；失败保持旧版本用于内部诊断，不把旧版本当“当前结果”。旧版本按保留策略清理。

全量重建是小规模 MVP 的推荐，**本次未测规模、内存和耗时，不能把它说成已满足容量要求**。开发前给出目标节点数、峰值注册/合并量、重建预算及积压告警；全量超预算后按受影响连通分量增量计算，仍保持同一纯函数结果与版本合同。不要从第一版就实现分布式图锁。

### 4.3 不丢事件、不读半张图

- 身份事务保存可恢复的必要事件/任务；派发可 afterCommit，但不能只有内存回调。合并操作以来源 UID 等稳定键幂等（一个原始 UID 只能终态合并一次），避免把原产品定向+广播当成多次图操作。
- pending/已应用状态与已发布版本必须可持久核对，重启可恢复。原始事件插入 ID 不作完成水位；复用当前发布算法也只解决送达，涉及因果依赖的缺失事实需等待或从身份真源重建。
- MVP 可以接受“有未应用合并时，全局关系查询暂为 RECONCILING”的简单策略；这牺牲短暂可用性，避免漏掉远端下游影响。不得未经用户认同承诺所有直属查询始终实时。
- 查询在同一数据库一致性快照内读待处理状态与已发布图；发布后才到达的新事件不得被旧批次误标已处理。构建快照之外的新变更必须留下 pending。并发持续写入时要测饥饿和延迟。
- 注册原始决定可以立即查到；当前关系图何时可读取由 projection 状态明确表达。认证、绑号、产品授权均不等待图投影器。

## 5. MVP 数据与边界

五个逻辑对象可以保留，避免再加路径表、层级冗余和奖励表：

| 对象 | 最小责任 |
|---|---|
| code | 随机码、码主原 UID、有效/撤销状态；禁止把目标应用放入全球关系唯一键 |
| context | 单次注册流程、经确认的 code、受信 client/入口元数据、到期、消费 UID/结果；不是跨浏览器永久 cookie |
| registration decision | original UID 唯一；REFERRED/NONE/基线原因；原邀请 UID、证据来源与策略版本；不可更新邀人 |
| current projection | projectionVersion + 存活 UID 的邻接关系或抑制状态；可全部重建 |
| audit | 码管理、流程决定原因、运营读取、投影冲突与版本发布；禁止保存凭据/完整手机号/微信 code |

私有事件/待处理记录、投影元信息和租约是可靠运行所需的配套，不能为坚持“五张物理表”把它们挤进不受约束的 JSON。已有事件发布机制可借鉴，不意味着可复用原产品广播权限。

首期不做独立增长服务、不做多级奖励、不迁移旧产品关系、不做运营改邀请人、不给第三方开放全图。未来拆服务时，账号中心仍在首建事务写不可变注册事实/可靠私有事件，外部增长服务消费并自建投影；不能把新注册变成同步远程调用成功才能建 UID 的分布式事务。

## 6. 实施前必须定下的决策

| 决策 | 推荐 | 不决定的后果 |
|---|---|---|
| 全球唯一关系的名称与业务含义 | 仅账号注册来源 | 被误用为所有产品终身商业推荐人 |
| 首次扫码的确认时点 | 邀请流程在创建 UID 前确认 | 未确认扫码已永久归因 |
| 多入口/多标签归因 | 本次明确选择并冻结；创建事务赢家优先 | first/last touch 在端和服务端各说各话 |
| 普通注册与失败 | NONE 是有效决定；存储故障不得冒充 NONE | 故障永久吞掉用户选择 |
| 合并冲突 | 采用可恢复投影抑制；若永久取消则持久处置记录 | 后续重建改变历史含义 |
| 投影滞后 | 显式 RECONCILING；先确定允许延迟与容量预算 | 把旧链当当前，或重建长期卡查询 |
| 存量与导入 | 全部闭合，有原因分类，不补全球邀请 | 已有业务用户冒充生态新客 |
| 已登录用户点邀请 | 不改注册关系，清理本流程；以后可独立记录活动触达 | 后绑绕过/共享设备污染下一账号 |
| 停用/注销/合并后的码 | 停用注销暂停新邀；旧码合并后的解析策略明确且不复活旧主体 | 旧码静默换主人或永久悬空 |
| 用户与运营可见字段 | 直属最小资料；运营独立权限、审计及范围 | 关系枚举和跨产品隐私泄露 |

这些是设计决策，不构成本轮修改运行时代码或生产环境的授权。

## 7. 必要验收矩阵

以下是待实现后的验收要求，**不是本次已通过测试**。

| 场景 | 必须观察的结果 |
|---|---|
| 短信首登：有码/无码 | UID、凭据、REFERRED/NONE、context消费、事件同事务；中途注入异常无半成品 |
| 同手机号并发不同邀请、邀请与普通入口竞速 | 仅一个 UID/原始决定；失败方不能改赢家，重试读同结果；真 MySQL REPEATABLE READ 验证 |
| 微信 openid/unionid 并发首登 | 唯一 UID、唯一决定；新事务重查赢家不补绑 |
| grant/sms、grant/wechat、网页短信/微信 | 入口全覆盖；非法/重复 context 参数不能绕过；刷新令牌不创建新决定 |
| PC有码、手机无同域cookie，跨设备扫码 | 手机首建事务拿到 PC 绑定的合法 context；手机参数不能替换来源 |
| 扫码取消/过期/重复确认/PC刷新码 | 按定稿的确认时点执行；旧票据不可创建错误归因，不能跨 PC session 完成登录 |
| 会话轮换、重启、跨实例、微信资料授权失败 | 受控 flow 保留；无任意session转移；归因不依赖资料授权成功 |
| 已登录账号直接点邀请、自动SSO、换账号 | 原决定不变；旧 context 不泄露给下一账号，仍能正确回应用 |
| 微信先建A后首绑B | B的REFERRED/NONE/LEGACY均优先；A事实保留；旧A token仍被拒绝 |
| 两个有不同邀请人的账号合并 | 父边只取存活方自身；下游按alias规范化，不继承来源父边 |
| 自环、长度大于3的环、连续合并、重复事件 | 无当前环；抑制原因与版本可解释；乱序/重放不改变确定性结果 |
| 超大下游、重建失败/崩溃/租约切换 | 身份合并可完成；图明确RECONCILING；不出现部分发布或重复处理 |
| 旧UID/导入/体验账号/注销后重注册 | 基线原因正确；无按手机号猜回旧邀请；新UID口径不宣称新自然人 |
| 所有既有产品拉取outbox | 不含任何新邀请详情；原合并/注销事件仍按原合同可达 |
| 用户越权、普通产品机器令牌、运营越权 | 用户仅本人直属，scope不足/主体范围不符拒绝；查询、导出审计齐全 |
| 公开码扫描、嵌入页面、恶意回跳、跨标签污染 | GET不建关系；不可任意跳转/冒充client；开始后context不可覆盖 |
| 邀请人停用/注销、码撤销、合并后旧码 | 新邀策略与展示一致，已提交事实不被撤销码改写 |
| 业务隔离 | enrollment、企业归属、积分、作品、军师/公社既有邀请与奖励均无非授权变化 |
| 全量重建/数据恢复/切换上线 | 从原始事实和身份真源重建同结果；缺事实扫描、旧实例屏障、版本切换有证据 |
