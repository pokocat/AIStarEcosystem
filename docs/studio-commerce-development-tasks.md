### 两项前置适配

1. `enrollment/config/ProductRouteTable.java` 当前将 `/api/products/**`、`/api/me/products/**`、`/api/me/social-accounts/**`、`/api/me/publish-jobs/**` 固定给 celebrity。不能通过伪装 `X-App-Code: celebrity` 复用。计划将适合共享的精确路由登记为 celebrity/aiavatar 共用，并保持当前用户归属检查；管理端写权限不扩大。
2. `PublishJobService.createBatch()` 会创建 QUEUED 任务，`PublishJobScheduler` 会扫描执行。发布草稿必须是独立、不可执行的记录，保存草稿不得调用现有创建发布任务接口。共享客户端部分“失败不退”的注释已落后于服务端 hold/commit/release 实现，后续计费按实际服务端和验收结果对齐，不从旧注释复制规则。

## 数据和接口设计草案

以下名称为开发建议，实施前需要以完整仓库契约核对，不代表已存在接口。

### 画布内的商品与参考

继续使用 `IpProject.doc.nodes[]` 和 `connections[]`，不添加新的带货项目域，也不要求 doc 根部 commerce 数据块。优先复用现有图片/文字节点：商品图为图片内容，名称、来源、商品 id/链接、用户核对的事实放该节点 metadata；无图商品可先用文字参考承载。具体扩展类型实施时统一到 `packages/types`，不改 vendor 节点体系。

用户把商品连到剧本或显式选中后，提交当前剧本快照、引用节点、商品事实、修改范围与用户指令。`StudioGenerateRequest` 已有 `references/contextNodeIds/scriptEdit` 等基础字段，但当前 `studio-script-editor.tsx` 的改稿请求没有装配商品参考，不能把界面连线当成已经生效；需核对前后端取上下文的实际链路并适配。只需文字植入时不强制图像理解，产品外观需要参与时再引用图片。

修改范围优先复用编辑器的选区或场景定位；请求接受后保留原文快照，复用现有 proposal、预览、采纳、放弃和撤销。期间用户改了正文时走原冲突保护，不覆盖新输入。换商品不自动重写剧本，不自动重生成下游图片/视频。

商品图需通过已有受控导入/本人素材流程变成可验证存储 key，不能复制外链绕过归属闸；复用能力不足时只补这一小段适配。只存 key，不持久化短期签名 URL。原 doc 版本控制与保存规则继续使用。

爆款复刻同样只保存参考节点和用户要求：参考视频、截图或文本、拆解要点、要保留的结构与要改编的主题。不把“复刻模板”当成已经有全视频理解、一键链接抓取或自动批量重做；自动拆解另按实际模型支持范围接入，不成为模板开用的前提。

### 发布草稿

草稿是项目之外的发布准备数据，建议新增 `studio_publish_draft` 记录并配服务；不向现有 PublishJob 枚举随意加入“draft”。它需要跨项目查询、分页和独立保存。

| 数据组 | 规则 |
|---|---|
| 归属 | ownerUserId、sourceApp=aiavatar、Studio projectId |
| 成片来源 | 源合成 nodeId/runId、确定的结果引用及媒体 key、封面 key；原作品被替换不偷换草稿视频；普通作品允许不绑定商品 |
| 商品 | 选定商品版本、展示名称和链接快照 |
| 发布信息 | 标题、正文、话题、每个目标的平台/可空 socialAccountId/意向时间/明确时区 |
| 生命周期 | 草稿、已归档；“信息完整性”实时计算，不把草稿标成 queued/live；真实提交后关联独立发布批次 |
| 幂等与并发 | 创建 clientRequestId、保存 version；相同来源首次进入重复点击复用本次草稿，显式“新建发布草稿”才创建另一份 |

拟新增 `/api/v1/ip-studio/distribution/publish-drafts` 的创建、分页、本人详情、版本更新、删除；具体路径写入 openapi 后才进入实现。分页返回 PageEnvelope，单资源返回 ApiResponse。

B 允许账号未选、标题未完成的草稿保存；“保存成功”只表示持久化成功。意向时间显示“计划”，不出现“已预约发布”。

C 新增显式提交动作，服务端重新校验本人项目、精确作品、账号归属/状态、平台能力、商品信息与价格，事务内保存原提交快照和批次关系，派发挂 afterCommit。前端请求失联后查询同一次提交；没有查询到明确未受理结论时不换键重提。

### 真实发布复用前的兼容处理

- 账号默认沿用当前同一 uid 下本人记录，不复制 cookie 或新建假账号；是否允许该产品使用由产品路由明确授权。
- 现有 PublishJob 的 projectId 同时承担批次聚合用途，不直接把一个画布 id 当成全部发布批次。新增明确的 Studio 来源关系和独立批次标识，使同一成片能发布多次，历史记录互不合并。
- 新草稿和记录按来源应用隔离；扩展共享接口时确保 celebrity 原列表不会突然混入 Studio 任务。旧任务无来源字段时按明确的兼容规则归到原入口，不能猜成 Studio。
- 不把 Studio 的短期预览 URL 当作长期定时派发来源。服务端保存可验证媒体引用，执行时重签并复用原允许域名检查。
- 发布价格可能仍来自 celebrity 命名的现有配置。C15 必须确认适用 Studio 的配置口径和实际账本行为，再显示报价；不硬编码免费或继承旧客户端注释。
- 企业积分目前不能据 Studio 生成支持 billing 就推断发布也支持。B 不产生发布费用；C 默认范围限个人付款，企业付款另行核实并设计后开放。

## 功能边界和状态要求

| 场景 | B 的预期行为 |
|---|---|
| 公共商品无图 | 能看详情；生成需要图时提示补充本人商品图 |
| 链接解析失败 | 保留链接和已填内容，允许重试或手动补填 |
| 价格、佣金缺失 | 显示「暂无信息」，不能补成 0、免费或猜测比例 |
| 从商品库选中商品 | 拖入后随当前 doc 保存，仍在原画布；不会启动生成 |
| 创作中更换商品 | 明确提示旧脚本/画面不会自动更新，保留旧作品；后续显式请求使用当次选中的商品参考 |
| 成片合成中或失败 | 保留制作与恢复入口，不能伪装成可发布成片 |
| 没有矩阵账号 | 可保存草稿、选择意向平台并手动发布；B 如实提示绑定功能后续开放 |
| 账号过期 | 显示真实状态，保留用户选择痕迹并提示需重新授权，不当可用账号执行 |
| 保存发布草稿 | 发布任务和账本无新增，刷新可恢复，记录页显示草稿 |
| 修改成片后打开旧草稿 | 保留原视频；主动选择替换才更新草稿，真实发布历史不改 |
| 到达草稿意向发布时间 | 仍是草稿，不被调度器执行 |
| 用户手动发布 | 提供下载/复制，不依据点击下载就显示已发布 |

## 验收与文档同步任务

B 的产品验收使用只开通 aiavatar 的普通账号，检查商品选取、链接失败补填、图片归属、选中范围与商品参考实际生效、改稿预览采纳和并发保护、爆款复刻模板副本、成片来源、草稿创建/修改/返回/刷新恢复、账号空态与过期、手动下载复制、记录分页。重点断言：保存草稿前后 PublishJob 数量和发布费用均不变。

C 需追加真实账号绑定、取消/超时/验证交互、实际上传及商品挂载、跨天签名有效性、多账号独立结果、重复点击幂等、未知受理查原单、失败结算及按平台开放验收。不能只凭前端显示“已发布”判定成功。

开发完成后按仓库要求执行 `pnpm typecheck:all`、`pnpm typecheck:admin`、后端离线 compile、`pnpm check:api-contract`，并运行涉及路由归属、本人权限、草稿无派发、来源版本与幂等的定向测试。按变更范围构建应用并完成浏览器验收。文档阶段不运行这些开发测试，也不声称已通过。

进入实施时同步 `apps/web-aiavatar/PRODUCT.md`、`README.md`、`docs/INDEX.md`、`specs/openapi.yaml` 与 `BUSINESS_RULES.md`；如提取了共享能力，更新 celebrity 相应说明。独立新迁移编号需同时检查 SQL 与 Java migration 的最新编号，不能预占或修改已执行迁移。

## 已确认的架构与待实施选择

应用落点和一级导航已确认。命名、IP 合并三个前提及独立运营后的调整条件按定稿执行；本轮不启动业务代码开发。其余具体实现选择如下：

1. 场景工坊是模板画布的目的入口，剧情带货、爆款复刻、短剧、音乐并列；不做独立带货项目系统。
2. 剧情带货核心为商品参考 → 指定剧本范围 → 输入植入要求 → 预览与采纳。已有画布同样可用，不限制为一个主商品或一种创作路径；每次改稿明确本次引用即可。
3. 发行管理跨场景分发；草稿与真实发布任务保持独立，普通作品商品可空。
4. B 读取已有本人账号并提供手动发布准备；新增绑定与真实发布放 C，批量和运营增强另行排期。

以上均为设计及任务拆分，不代表批准开始业务代码开发或自动发布。
