# Studio 提示词分层架构

> 状态：**部分实施，第 1–4 步和编导部分已于 2026-11-01 生产发布**（`20261101-studio-prompt-library`，见 [`releases/studio-prompt-library-release-20261101.md`](releases/studio-prompt-library-release-20261101.md)；2026-10-31 初稿；2026-11-01 整合内容优化 §9；没做的见 §14.3）。
> 范围：Studio（`apps/web-aiavatar`：创作助手、AI 视频、AI 图片、画布、导演台）。短剧、带货、音乐、素材运营等产品线在后台「Prompt 管理」里的提示词不在本文范围。
> 相关真源：技能库 [`ip-studio-conversational-video-recreation-plan.md`](ip-studio-conversational-video-recreation-plan.md)（S3，V63）、对话路由 [`ip-studio-dialogue-intents.md`](ip-studio-dialogue-intents.md)、场景 [`studio-scene-creation.md`](studio-scene-creation.md)、导演台 [`ai-director-plan.md`](ai-director-plan.md)。
> 内容优化（§9）整合自 [`prompts/studio-video-scene-prompts.md`](prompts/studio-video-scene-prompts.md)（2026-11-01 版）的提示词正文：五段式方案卡、事实规则、21 个视频场景范式，以及它 §9 新增的四条写法。提示词原文尽量不动，只按层拆开，改动处逐条注明原因。该文件 §8 的参考站接口实测仍在原处，作对照参考。

## 0. 一句话

所有决定生成内容的文字（身份、工作规则、红线、做法、行业经验、场景拍法、出图描述）都放进一个提示词库，分四层：**底座、环节、方法、场景**。后台可改、每个版本不可变、每次生成记下用的是哪几版。代码只保留必须和代码一起改的四类：**输出格式、工具与动作协议、H3 改写、拼装与校验**。

这次重构同时提升内容质量：AI 视频的编导改用专门的提示词（五段式方案卡、事实规则、画面细节要求、时长钳制、改稿只改指定部分），21 个视频场景换成重写过的场景范式（§9）。结构先搬、内容后改，两件事分开上线，效果变化才说得清。

## 1. 现状与问题

### 1.1 提示词散在五处，生效规则各不相同

| 位置 | 内容 | 后台能改吗 | 版本与生效 |
|---|---|---|---|
| `resources/prompts/material/dap.ip_*.md` → 表 `prompt_template`（后台「Prompt 管理」） | Studio 10 份：对话主提示词、方案、检查、蒸馏、画布文字（通用助手）、剧本、复刻、出图包装、IP 形象、造型图 | 能 | 只有一个计数。改了文件要升 `PromptTemplateSeeder.SEED_VERSION`，而且那一行没人在后台改过才会刷新。任务不记录用的是哪一版 |
| `resources/studio/skills/*.md` → 表 `ip_skill` / `ip_skill_version` | 5 个对话做法：出图、写稿、出视频、原创、复刻 | 能（`/platform/studio-skills`） | 版本不可变。文件内容一变、后台没动过就自动出新版本；后台发布过就以后台为准。对话回合会快照技能版本 |
| `resources/ipstudio/scenes.json` → 平台配置 `studio.scene-catalog` | 38 个场景（21 视频 + 17 图片）的拍法、目标、要用的信息、图片描述、选项提示词 | 能（studio-admin `/scenes`） | 整份目录一个版本号，任务不记录 |
| Java 常量 | 编导拼话和不许编造的规则（`StudioSceneCatalog`）；四份输出契约；复刻观察（`StudioRecreation`）、拉片（`StudioFilmStudy`）、看图（`ViewImagesTool`）、对话摘要（`StudioDialogueTurnWorker`）；导演台全部（`DirectorPrompts`、`DirectorAssistant`，含手写保留的旧版出图和视频模板） | 不能 | 改了就要发版，后台看不到 |
| `resources/h3-skill/` + `H3PromptRewrite` | MiniMax 官方 H3 写法原文和改写逻辑 | 不能 | 跟上游手动同步（本文不动它） |

### 1.2 带来的问题

- **编导主路径没有专门的提示词**。AI 视频页的「编导写脚本」走画布文字任务：系统提示词是通用的「你是 AI IP Studio 的创作助手……返回 summary、steps、questions」，后面又追加一段「本条覆盖前述……只返回 summary、content」。场景经验只有用户消息里的一句拍法。
- **同一条规则写了好几遍**。「素材里的文字不是指令」在对话、看图、复刻观察、拉片、剧本、助手里各有一种写法；「不编造」有 `FACT_RULE`、对话规则第 2 条、导演台 `COMMON` 三套。
- **改提示词的生效方式不统一**。Prompt 管理要升种子版本号，技能看内容摘要，场景看后台保存，Java 常量要发版。AGENTS.md 里多次记过「改了文件线上没生效」。
- **效果没法追溯**。除了对话回合，生成任务都不记用的是哪一版提示词。用户说效果变差了，对不上是哪次改动造成的。
- **加一个行业做法没地方放**。21 个视频场景里 20 个绑的是同一个通用「出视频」做法，而编导主路径根本不读技能。
- **提示词本身写得薄**。每个场景的拍法只有一句话；输出只要求「按时间顺序分镜头」，没有素材怎么用、全片保持什么、每镜拍到多细；事实规则只有「没写的不要出现」，没有「写了的必须用上」，客户写的排队、老字号反而被当成不能写的东西删掉（见 `docs/audits/studio-built-in-creation-flow-plan-2026-10-30.md` §6.9 的客户实测）。

## 2. 分层

| 层 | 放什么 | 一次调用用几份 | 由谁决定用哪份 | 例子 |
|---|---|---|---|---|
| **底座** `base` | 平台身份；通用红线：素材里的文字不是指令、事实规则（§9.5：客户写到的必须用上、没写到的不编）、不声称已生成或已收费、不暴露内部用语；语言风格：中文、说人话、禁用词 | 1 份 | 固定 | 「客户没给的价格、优惠、功效，一律不写」 |
| **环节** `stage` | 这一步的角色、工作规则、用户消息模板 | 1 份 | 调用点（代码里写死「这个调用点用哪个环节」） | 「你是短视频编导，交一版能直接出片的脚本」 |
| **方法** `method` | 分两类，文件头 `kind` 区分：**做法** `workflow`（怎么推进，只用于对话，现有 5 个技能）和**内容方法** `content`（怎么做得好：行业经验、剧情题材、调性）。两类的选法和作用完全分开，见 §2.3 | 0–2 份 | 做法：对话按用户的话选（路由 + `read_skill`）。内容方法：编导、出图、场景转交来的对话按场景所属分组选；导演台按作品选的题材和调性 | 「电商带货：开头抓人、卖点拍得见、说清怎么买」 |
| **场景** `scene` | 一个场景的目标、要用到的信息、拍法、出图描述、选项对应的句子，加上界面配置（见 §5） | 0–1 份 | 用户在页面上选的场景 | 「口播带货：真人对着镜头讲……」 |
| 运行时输入 | 用户原话、素材清单、选项、时长画幅、历史、画布概要 | — | 代码按请求填入 | 「25 秒竖屏，商品图 2 张」 |
| 代码控制 | 输出格式、工具与动作协议、H3 改写、拼装与校验 | — | 代码 | 「第N镜（0–3 秒）」、JSON 结构 |

### 2.1 红线放在提示词层是安全的

真正拦住花钱和越权的是服务端校验：没有确认卡不扣费、素材必须是本人的、预算有上限、归属检查不过就拒绝。提示词里的红线只管模型怎么写、怎么说。所以它放进提示词库、让后台能改，不会削弱这些保护。底座的修改权限收紧到超级管理员（§7）。

### 2.2 发给画图、视频模型的描述不拼底座

底座写给大模型看。画布出图包装、场景出图描述、导演台的资产图和分镜图模板是直接交给画图或视频模型的，这类环节在文件头标 `target: image-model` / `video-model`，不拼底座。

### 2.3 做法和内容方法分开走

现在的 `read_skill` 读到一个新 key 就会把它绑成对话的制作方法，随之作废待确认卡、停止或暂停旧制作（`ReadSkillTool` → `bindSkill` → `switchMethod`）。读一份「电商经验」不该有这些后果，它也没有执行器要的 `operations` / `limits`。所以：

- **做法**（`kind: workflow`）：路由、`read_skill`、线程绑定、方案校验、执行器只认这一类，行为和现在完全一样。
- **内容方法**（`kind: content`）：只读加载，作为附加上下文拼进 `{{method}}`，不改变线程绑定、不影响确认卡和制作状态。第一版只由场景分组（和导演台的题材、调性）决定，不给模型提供自选内容方法的工具；以后确实需要再加一个只读工具。
- 场景转交来的对话：转交节点记下场景 id，服务端按场景找到内容方法，记在线程上；之后用户在对话里换做法，内容方法不变。

## 3. 拼装

### 3.1 用保留变量指定各层的位置

环节模板用保留变量说明其它层放在哪：`{{base}}`、`{{method}}`、`{{scene}}`，以及代码提供的输出格式 `{{format.<名>}}`（一个调用点可以有几段格式，比如编导有 JSON 外壳 `{{format.output}}` 和镜头行写法 `{{format.shots}}`，各放在该放的位置）。其余变量都是运行时输入。

不固定成「底座在最前、格式在最后」，原因是搬家阶段要逐字还原现在的提示词：比如现在技能正文在对话提示词 user 部分的中间（`{{skill}}`），动作输出写法在 system 部分中间。用占位就能先原样搬、再在第 5 步调整顺序。

一次调用拼出来的样子（编导写「口播带货」脚本，第 5 步之后，详见 §9.3）：

```
system ┬ {{base}}           ← 底座：通用红线、事实规则、语言风格
       ├ 环节 system 正文     ← stage-scene-script：资深短视频编导的角色
       ├ {{method}}         ← method-commerce：电商带货的经验（可以为空）
       └ {{format.output}}  ← 代码：只输出 {summary, content}
user   ┬ 环节 user 模板       ← 写一条 25 秒竖屏「口播带货」脚本……我的要求……参考素材……
       ├ {{scene}}          ← scene-ecom-talking：拍法、要用到的信息
       ├ 五段式写法           ← 环节正文（一、剧情概述 …… 五、保持与禁止）
       └ {{format.shots}}   ← 代码：镜头行开头、台词写法、时长钳制，带一个照抄就对的例子
```

### 3.2 发布前的校验（代码做，不过就不让发布）

- 调大模型的环节必须包含 `{{base}}`；调用点登记的每一段输出格式（`{{format.<名>}}`）都必须出现。
- 只能使用这个调用点登记过的变量；登记为必填的变量不能缺。变量清单由代码登记，后台只读展示。
- 底座、方法、场景的正文里不能出现保留变量。
- 模板语法能解析；示例输入能拼出非空的 system 和 user。

### 3.3 模板语法

现在 `PromptService.fill` 只认 `{{变量}}`。编导拼话和导演台模板里有大量条件：「用户写了要求才加这句」「有参考图才写编号」「单镜头和多镜头写法不同」。采用 Mustache 的无逻辑写法，只用三种：

- `{{变量}}` 替换；
- `{{#有}}……{{/有}}` 有值才输出，`{{^有}}……{{/有}}` 没值才输出；
- `{{#列表}}……{{/列表}}` 逐项输出。

判断和数值由代码算好再传进来（比如「镜头数下限」「是否单镜头」），模板里不做运算。库倾向 `com.samskivert:jmustache`（没有其它依赖；列表里可用 `-first` / `-last` 处理分隔符），实施时确认；关闭 HTML 转义。

### 3.4 受理时冻结版本，每次调用记一条

一个任务可能调用模型很多次：一轮对话会依次调用主对话、历史摘要、看图、方案规划，后一次的输入还依赖前一次的结果。所以分两部分记：

- **受理时冻结的版本集合**（`_exec.prompt.versions`）：这个任务可能用到的所有环节、方法、场景、底座，各记 key、版本、内容摘要。对话回合包括主对话、摘要、看图、方案规划；方案执行包括各步骤要调用的环节。之后每次调用都从这份集合里取，后台发布新版本不影响在途任务。现在 `ProposePlanTool` 执行时重新解析模板，改为读冻结的版本。
- **每次调用追加一条记录**（`_exec.prompt.calls`）：调用序号、环节 key、工具调用 id（有的话）、实际用的各层版本、拼出来的 system 和 user 的摘要、调用参数（`temperature`、`max_tokens`）。完整文本不进任务输入（对话每次几十 KB，一轮可能几十次），靠现有的上游调用日志（`[upstream-io] REQUEST`）留存。
- **中途换做法**：对话里 `read_skill` 换成另一个做法时，取那一刻的当前版本，追加进冻结集合；之后这个任务就一直用它。

对话回合现在的技能快照（`_exec.skill`）并入这套记录。

## 4. 存储与版本

### 4.1 表

沿用 `ip_skill` / `ip_skill_version`，新增一个迁移：`ip_skill` 加列 `layer`（`base` / `stage` / `method` / `scene`，现有 5 行回填 `method`），用于筛选和校验。其它按层不同的属性放在文件头 JSON（`frontmatter_json`）。迁移编号：仓库目前到 V72，实施时按线上 Flyway 最大值 +1（编号横跨 SQL 和 Java 两个目录）。

### 4.2 key 规则

- 现有 5 个对话做法的 key 不变（线程绑定、回合快照、执行器都引用它们）。
- 新条目按层加前缀：`base`、`stage-<名>`、`method-<名>`、`scene-<场景 id>`。正则沿用 `[a-z0-9][a-z0-9-]{0,63}`。

### 4.3 文件头按层不同

| 层 | 文件头字段 |
|---|---|
| 全部 | `key`、`name`、`version`、`status`、`layer`、`summary` |
| 环节 | `target`（`llm` / `image-model` / `video-model`，决定是否必须有 `{{base}}`）、`callPoints`（说明用在哪，展示用）、`params`（可选，见 §4.7）；变量清单由代码登记，不写在文件里 |
| 做法（`kind: workflow`） | 现有的 `operations`、`limits`、`checks`、`autoFixChecks`、`requiredCapabilities`、`triggers` 照旧必填，解析规则不变 |
| 内容方法（`kind: content`） | `usedBy`（可用于哪些环节）、`groups`（服务哪些场景分组）；没有 `operations` / `limits` / `triggers`，不参与路由 |
| 场景 | `sceneId`、`kind`（`image` / `video`）、界面配置（§5） |

### 4.4 仓库文件位置

`resources/studio/prompts/{base,stages,methods,scenes}/*.md`。现有 `resources/studio/skills/*.md` 移到 `methods/`，key 不变。

### 4.5 生效规则：全部按技能库现行规则

- 启动时库里没有就灌入。
- 后台没动过的条目，文件内容变了自动出新版本。
- 后台发布、回滚或改过状态之后，以库为准，文件不再覆盖。
- 每个版本写入后不再修改；缓存 60 秒，多节点自然收敛。
- **不再有 `SEED_VERSION`。**

### 4.6 切换时导入线上实际在用的内容

只用仓库文件给新条目灌种子，会把运营在后台改过的内容冲掉：`prompt_template` 是库里启用的行优先、空字段逐项回退到文件；`studio.scene-catalog` 可以被后台整份覆盖。代码层面的「逐字一致」测试比的是仓库新旧代码，发现不了这个问题。所以每个调用点切到新库之前：

1. **以旧路径实际生效的内容为准导入**：`prompt_template` 用 `PromptService.resolve` 的结果（含逐项回退，包括 `params_json`）；场景用当前生效的目录（后台保存过的平台配置优先）。导入的内容作为新条目的第一个版本。
2. **按内容标来源**：和仓库文件一样的记为种子，之后仍随文件更新；不一样的记为后台修改（`updatedBy` 不是 `seed`），之后仓库文件不再覆盖它。场景逐个比，不按整份目录算。
3. **幂等**：已导入过的条目跳过，重启或重复发布不会重复导入。
4. **发布前用线上库副本核对**：在只读副本上跑一遍导入，每个调用点用旧路径和新路径各拼一次，system、user 和调用参数（`temperature`、`max_tokens`、端点）都一致才发。
5. **回退**：旧表和平台配置不删不改，回退就是发回上一版。不做运行时的新旧切换开关。

### 4.7 调用参数

现在 `prompt_template.params_json` 里的 `temperature`、`maxTokens` 参与文字任务的调用和预算计算。迁移后放到环节文件头的 `params`，导入时从线上生效的 `params_json` 带过来。优先级和现在保持一致：

1. 环节的 `params`（没写就用调用点现在的做法：导演台各任务和 H3 改写读端点的默认输出上限，见 AGENTS「导演台与视频提示词优化输出预算」）；
2. 代码里和输出格式绑定的下限照旧：成片检查固定 0.1、资产提取输出至少 16384、复刻和方案规划至少 8192；
3. 最后按后台 Token 售价的输出上限、端点能力上限截断。

### 4.8 Prompt 管理

Studio 的 10 个键迁完后，`PromptService` 不再为 Studio 解析它们；旧行保留只读，页面标「已迁到提示词与技能」；`PromptTemplateSeeder` 停止为这些键灌库。其它产品线不变。

## 5. 场景整条进库（推荐）

现状：`scenes.json` 里同一个场景既有界面配置（要放几张图、时长档位、画幅、选项按钮），又有创作文字（拍法、目标、图片描述、每个选项对应的句子）。拍法既显示在页面「示例」里（`sceneSteps(scene.structure)`），又拼进提示词；「要用到的信息」既拼进提示词，又用于页面上的「还缺」检查（`scene.brief.facts`）。

**推荐**：每个场景一个场景条目。文件头放界面配置，包括选项按钮和每个选项对应的那句提示词、要用到的信息清单；正文放拍法或出图描述。场景目录（`studio.scene-catalog`）只保留分组、排序、上下架、首页卡片、封面和示例。`GET /api/v1/ip-studio/scenes` 的输出形状不变（由条目派生），场景列表这部分前端不用改；生成请求那部分要改，见 §5.1。studio-admin 的场景编辑器改为编辑场景条目（同一套接口），保存就是出新版本。

**备选**：场景配置不动，只把创作文字搬进条目。同一句话要在两处编辑，不推荐。

### 5.1 编导请求、场景出图和转交怎么接

现在 AI 视频页先调 `composeScene` 拿到整段文字，再把它当 `prompt` 用普通文字任务（`operation: "text"`）提交，服务端按 `operation` 选通用助手模板。只换拼装器的话，新的编导环节接不上，也查不到用的是哪一版场景。改为**服务端受理时拼装**：

- **编导写脚本**：生成请求带场景输入（场景 id、选项、时长、画幅、语言、素材标题、改稿意见，也就是现在 `composeScene` 的入参），换成专门的操作（如 `operation: "scene-script"`）。服务端受理时按场景输入拼装，固定用 `stage-scene-script`，冻结场景和各层版本。前端不再提交拼好的整段文字。画布里存的请求也存这份场景输入，「确认原任务」按原请求重交，同样不会重复扣费。
- **场景出图**：同样带场景输入提交，服务端拼装并冻结版本。
- **转交给助手**：拼出来的那段话会作为用户消息显示在对话里，所以仍在转交时拼好放进开始节点。`composeScene` 的返回里加上所用版本，开始节点一起记下，连同场景 id；第一条消息发出时，服务端核对场景 id，按 §2.3 找到内容方法记到线程上。
- `composeScene` 接口保留，供页面预览和转交使用。

## 9. 内容优化：AI 视频编导与 21 个场景

### 9.1 要解决什么、依据是什么

- **客户实测**（审计文档 §6.9）：效果好的那一单做对了三件事：客户写的事实（位置、价格、老字号）原样出现；结构完整，逐镜交代景别、机位、焦点、音效、台词、配乐；每张参考图「用什么、不用什么」说清楚。它暴露的问题：没有「客户写了的必须用上」，排队被当成不能写的删掉；堂食、打包这类服务细节被编出来；结尾缺领券入口。
- **参考站**（茂隆掌柜「超级编导」，原文 §8 的接口实测）：每个场景对应一个技能（如 `ecommerce-spoken-selling`），用户只写一句话，质量靠场景规则撑；产出就是五段式方案卡。这和本文「场景决定方法、规则放在系统这一侧」一致。
- **做法**：一套共用的编导提示词，加上 21 个场景范式；不逐场景重写整套长提示词。

### 9.4 镜头行写法 `{{format.shots}}`（代码）

```
每个镜头单独一行，像这样：
第1镜（0–3 秒）：画面：……；景别/机位/焦点：……；音效：……；店员说：「……」；BGM：……
第2镜（3–6 秒）：画面：……；景别/机位/焦点：……；音效：……；BGM：……
括号里只写起止秒数，第1镜从 0 秒开始，每一镜接着上一镜；所有镜头加起来正好 {{duration}} 秒，最后一个镜头补到 {{duration}} 秒整。
有人说话写「名字说：「台词」」，画面外的人说写「名字在画外说：「……」」，旁白写「旁白说：「……」」；没有台词就不写这一项。一句台词一个「」，台词里面不要再用「」。
```

放在代码里，原因有三：

- H3 改写认的就是这两种写法：镜头开头「第N镜（起 秒」、台词「名字说：「」（`H3PromptRewrite.SHOT_HEAD` / `LINE`）。认出来，镜头时间就固定，台词由代码原样填回；认不出，就交给模型重新分镜、重写台词。
- 原文用的是带占位的模板「第N镜（a–b 秒）」。2026-10-31 本地 Agnes 照「起–止」模板把这几个字原样抄进了括号，一镜都认不出（AGENTS §8.0.1 ⑦）。所以这里给一个照抄就对的例子；例子里的秒数由代码按时长算，短视频不超过总时长。
- 时长钳制句（原文 §9.4）和 H3 的时间核对是一对：镜头开始时间要递增、第一镜从 0 秒开始、都在总时长之内。

### 9.5 底座里的事实规则

原文照搬，替换现在的 `FACT_RULE`：

```
事实规则：
客户写到的位置、价格、招牌、活动、排队、老字号、使用场景等，必须原样出现在脚本里，作为画面和台词的真实依据。
客户没写到的价格、优惠、地址、品牌年限、检测测试次数、销量排名获奖、门店数用户数、功效数据，以及服务细节（堂食、打包、几人份、营业时间等），一律禁止编造；也不要写「有优惠」「限时」「十年老店」「上千次测试」这类话。
可以虚构人物和情节来讲故事，但不要写成品牌的真实经历，也不要给编出来的内容配上年份、次数、数量。
```

### 9.7 和已发布版本的差异、兼容要注意的地方

## 10. 迁移步骤：先搬家，后改内容

**原则**：第 1–4 步只搬地方、不改一个字。每搬一个调用点，都写一条「逐字一致」测试：同一组输入，新拼装器的输出和现在代码拼出来的完全相同。旧的拼装代码留在测试里作对照，这一步上线后删掉。内容改动只在第 5 步做，每项单独评测效果。

1. **结构**：迁移加 `layer`；解析器支持四层文件头和方法的 `kind`；拼装器（Mustache、保留变量、发布校验）；冻结版本和逐次调用记录（§3.4）；环节 `params`（§4.7）；导入程序（§4.6）；后台按层筛选和预览。不搬任何内容。
2. **场景与编导**（调用点 12–14）：38 个场景条目，编导、交给助手、场景出图三个环节；生成请求改为带场景输入、服务端受理时拼装（§5.1，前后端一起改）；导入线上生效的场景目录。编导先原样还原现在的拼法，包括借用的通用助手系统提示词，逐字一致后上线。
3. **画布与对话**（1–11、15、16）：导入线上生效的 `prompt_template`（含参数）；Studio 停读 Prompt 管理。

### 14.2 和设计的差异

| 设计 | 实际 | 原因 |
|---|---|---|
| §4.1 `ip_skill` 加 `layer` 列（新迁移） | 不加列，层级写在文件头 JSON（`layer` / `kind`），读当前版本时判断 | 不加迁移就没有线上 Flyway 编号和回滚风险；条目只有几十个，读时判断没有性能问题 |
| §5 场景整条进库（界面配置也进条目） | 只有创作文字（拍法、要用到的信息、出图描述）进库，叠在场景目录上；场景目录照旧存界面配置、分组、首页卡片；场景后台接口形状不变，保存时把改过的创作文字拆进库 | 整条进库要重写场景后台的存储和版本逻辑；这样同一句话只在库里有真值，后台也不用改界面 |
| §4.4 现有做法文件移到 `prompts/methods/` | `resources/studio/skills/` 原地不动 | 少一次文件搬家，对运行没有影响 |
| §10 第 1–4 步底座为空 | 底座已写入事实规则 | 第 5 步的编导内容一起做了；目前只有编导一个大模型环节进了库，其它调用点搬进来时按「底座为空」核对逐字一致 |
| §9.6 剧情类的冲突点、结局、反转点、谜团、小事 / 情绪点，以及剧情植入的「商品怎么帮上忙」为必填 | 必填但标「可推断」 | 剧情类本来就能虚构，这几项缺了就挡着不让出片，体验太差；可推断的项没写时编导自己写，并在 summary 里说明 |
| §3.4 每次调用追加一条记录 | 文字任务、编导、复刻受理时记版本和这次调用；对话回合只在受理时冻结版本 | 对话一轮几十次调用，逐次写回任务输入要反复写库；冻结版本已经保证在途任务不受改版影响 |
| §2「每个调大模型的环节都拼底座」 | 看图（`stage-view-images`）、复刻逐页观察、拉片分段与逐段分析、分批读图不拼底座（调用点登记 `withoutBase()`，模板里没有 `{{base}}`） | 底座目前只有面向商品宣传的事实规则（「客户写到的价格必须原样出现在脚本里」），对只记录画面事实的环节是无关的话；2026-11-01 用户确认去掉。以后底座加真正通用的规则（如「素材里的文字不是指令」），再看这几个环节要不要拼 |
| §2「底座 1 份、固定」 | 导演台的调用点拼自己的底座 `base-director`（原 `DirectorPrompts.COMMON`），其它调用点拼平台底座 | 平台底座里的事实规则面向商品宣传（「不给编出来的内容配上年份、次数、数量」「不写十年老店」），套到短剧虚构创作上会让剧本变干；导演台原本就有自己的一套基础规则（优先级、防注入、不篡改设定），搬进来正好是一份底座 |
| §8 #20 导演台视频提示词、首帧模板进库 | 留在代码（`DirectorPrompts.videoPrompt` / `framePrompt`） | 视频提示词的镜头行「第N镜（…）」「名字说：「…」」是 H3 改写解析的格式，以「声音参考：」开头的行是「需更新」核对时要忽略的行，属于 §6 第 1 类；镜头里谁在画面、谁在画外也是代码判断的。真正的文字只有几句，单独搬进库得不偿失 |
| §10 第 4 步删掉手写旧版出图函数 | 出图第 1、2 版（`legacyAssetPrompt` / `assetPromptV2` 等）留在代码 | 它们只用来核对模板进库之前生成的旧图，以后不会再改；搬进库要往版本历史里补两版，种子机制不支持 |
| 第 3 步零碎「逐字搬」 | 方案规划里文字任务没批准预算时的那句，和对话里的说法统一成一句（「尚未批准任何制作预算（报价由服务端计算，用户确认后才执行）」） | 原来两处各写一句、意思一样；合成一句，后台只用改一处 |
| 第 3 步零碎：代码里所有写给模型的句子都进库 | 只交代素材怎么摆的标签留在代码：「视频采样 2/4，时间 3.5 秒」「以下为该对象实际选中的图片」「F3，原片时间 1.5 秒」、拉片前后的「原片时长 / 采样时间 / 以下均为素材」等 | 它们是素材的编号和时间格式（模型据此引用证据），属于 §6 第 4 类拼装；告诉模型怎么看、怎么写的句子都进了库 |

| §9.3 编导环节照搬内容方案原文 | 2026-11-01 真模型验收后改了三处：素材行去掉尖括号占位、给例句；镜头规则加「价格、优惠、截止时间、数量放进台词，画面里不安排字幕、文字特效、价签、色块和图标」；加「必填信息没给的写【待补】，不要自己编」 | Qwen 照抄尖括号（6/9），促销转化让画面出字、H3 照画出来（第五段的禁止被改写丢掉）；改后 10 条脚本尖括号和画面出字都是 0 |
